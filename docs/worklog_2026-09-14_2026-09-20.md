### 4. USB 웹캠 입력 확인
**작업 내용**

- 자동 노출 기능이 실제 FPS에 영향을 주는지도 확인함

**검증 결과**
- 영상 입력 장치는 `/dev/video0`으로 확인됨
- 영상 형식은 YUYV이며 최대 640×480, 30 FPS를 지원함
- 실제 데이터 전송량은 약 18MB/s로 USB 2.0에서 충분히 처리 가능한 수준임
- 자동 노출 상태에서는 실제 약 25 FPS로 동작함
- 자동 노출을 끄자 약 30 FPS로 정상 동작함
- 시작 직후 약 1.3초의 준비 시간이 있었으며 이후에는 프레임 누락 없이 입력됨

**알게 된 점**
- 이 웹캠은 JPEG 압축 영상을 보내지 않기 때문에 JPEG 해제 과정 없이 YUYV 영상을 BGR로 변환하면 됨
- 자동 노출이 켜져 있으면 주변 밝기에 따라 실제 FPS가 달라질 수 있음
- 따라서 성능 측정 전에 자동 노출을 끄는 것이 필요함
- 카메라를 다시 연결하거나 재부팅하면 자동 노출 설정이 초기화되므로 프로그램에서 직접 설정해야 함
- 카메라 입력에서는 단순히 코드가 프레임을 처리하는 시간뿐 아니라, 카메라에서 촬영된 뒤 FCW 판단이 끝날 때까지 걸린 전체 지연시간도 중요함

### 2. TensorRT 백엔드 코드 작성

**작업 목적 — 기존 CPU 방식에 GPU 실행 방식 추가**

- 기존 프로그램은 OpenCV DNN으로 CPU에서 YOLO를 실행했음
- 여기에 TensorRT를 사용해 Jetson의 GPU에서 YOLO를 실행하는 코드를 추가함
- 이렇게 AI 계산을 담당하는 실행 방식을 백엔드라고 부름

* `tensorrt_fp32` — 32비트 실수 계산을 사용하는 방식
* `tensorrt_fp16` — 16비트 실수 계산을 활용하는 방식, 계산 정밀도를 낮추는 대신 속도 향상을 기대함
* INT8 — 8비트 정수 계산에 맞추는 기준 데이터와 보정 작업이 필요하므로 이번에는 구현하지 않음, 선택하면 아직 지원하지 않는다는 오류가 나도록 함

**코드 정리 — 앞뒤 작업은 공유하고 AI 실행 부분을 나눔**

- YOLO로 차량을 찾는 과정

```text
| 단계  | 하는 일                              | 담당                        |
| --- | --------------------------------- | ------------------------- |
| 전처리 | 영상 크기와 여백을 맞추고 AI가 받을 숫자 배열로 바꿈   | CPU                       |
| 추론  | YOLO 모델로 차량 등을 찾는 계산을 수행함         | 기존 방식은 CPU, TensorRT는 GPU |
| 후처리 | 출력된 숫자를 박스·종류·확률로 해석하고 중복 박스를 제거함 | CPU                       |
```

- 두 방식에서 영상 준비와 출력 해석을 같은 함수로 처리하도록 기존 코드를 분리함
- 그래야 결과를 비교할 때 전처리·출력 해석 방법이 달라서 생기는 차이를 없앨 수 있음

**추가·수정한 파일**

```text
| 파일                                   | 작업 내용                                                |
| ------------------------------------ | ---------------------------------------------------- |
| `YoloCommon.hpp/.cpp` — 새 파일 2개      | 영상 크기·여백을 맞추는 `letterbox`와 YOLO 출력 해석 코드를 공통 함수로 분리함 |
| `TensorRTBackend.hpp/.cpp` — 새 파일 2개 | TensorRT 10으로 GPU에서 YOLO를 실행하는 코드를 작성함               |
| `OpenCVDNNBackend.cpp`               | 공통 함수를 호출하도록 바꿔 125줄 → 46줄로 줄임                       |
| `InferenceBackendFactory.cpp`        | 주석만 있던 TensorRT 부분을 구현함. 실행 옵션에 따라 사용할 백엔드를 선택함      |
| 루트·`perception`의 `CMakeLists.txt`    | `ENABLE_TENSORRT` 옵션을 추가하고 필요한 TensorRT·CUDA를 찾도록 함  |
| `scripts/benchmark_harness.sh`       | `--backend`로 실행 방식을 선택하고, 그 방식에 맞춰 반복 측정하도록 수정함      |
| `RunOptions.hpp`                     | 프로그램 사용법 안내 문구를 수정함                                  |
| `.gitignore`                         | `models/*.engine`을 추가해 엔진 파일이 Git에 올라가지 않도록 함        |
```

- TensorRT 기능을 빼고 빌드했는데 TensorRT 실행을 요청하면, 사용할 수 없다는 안내가 나오도록 함

**실행 방식 선택**

- 백엔드 이름에 정밀도를 붙여 `tensorrt_fp32`, `tensorrt_fp16`으로 구분함
- 기존에 백엔드를 생성하는 함수의 입력 형태를 바꾸지 않고, 이름만으로 실행 방식과 정밀도를 함께 선택하려는 설계임

**엔진 파일 저장과 재사용**

- ONNX는 저장된 AI 모델이고, TensorRT 엔진은 그 모델을 해당 GPU에서 실행하기 좋게 준비한 파일임
- 준비된 엔진을 `models/yolov8n.fp16.engine` 같은 파일로 저장함, 다음 실행부터는 저장된 엔진을 재사용함
- 엔진이 없거나 ONNX 모델이 엔진보다 최근에 수정됐으면 다시 만듦
- 엔진 준비를 끝낸 뒤 성능을 측정함, 처음 엔진을 만드는 시간이 프레임 처리 시간에 섞이지 않도록 함

**시간 측정과 메모리 복사**

- 기존 OpenCV 방식과 비교할 수 있도록 시간을 나누는 기준을 맞춤

- **전처리 시간** — CPU에서 영상 크기·여백을 맞추고 입력 숫자 배열을 만드는 시간
- **추론 시간** — 입력을 GPU로 복사하고, GPU에서 계산한 뒤, 결과를 CPU로 가져오는 시간. GPU 계산뿐 아니라 왕복 복사 시간도 포함함.
- **후처리 시간** — 출력 숫자를 박스로 해석하고 중복 박스를 제거하는 시간

- CPU와 GPU 사이의 복사에 유리한 **pinned 메모리**를 사용함
- 다만 현재는 입력 숫자 배열을 만든 뒤 pinned 메모리로 옮기는 복사가 한 번 남아 있음
- 이 부분은 이후 **Q6 Memory Path에서 데이터 이동을 살펴보고 개선할 대상**으로 남김.

**결과 비교 방식**

- 반복 측정 스크립트에서 기기 아키텍처와 백엔드 조합별로 기준 결과 파일(golden)을 선택하도록 함
- 예를 들어 x86·OpenCV 결과와 Jetson·TensorRT 결과를 같은 기준 파일에 무조건 대조하지 않도록 한 것
- 해당 조합의 기준 파일이 없으면 결과 파일의 식별값인 MD5만 기록하고 비교는 생략함

#### 6. RideFlux 정상 주행 영상 (오경보용)

- 오경보 나기 쉬운 장면 위주
  - 선행차 감속 / 컷인 / 컷아웃
  - 커브, 합류, 야간, 악천후, 역광
- 라이다 거리로 실제 거리·접근속도·TTC 계산

#### 7. 평가 기준

- 사고 영상
  - 경고했는지
  - 충돌 몇 초 전에 첫 경고했는지
  - 컷인·교차 진입 놓쳤는지
- 정상 영상
  - 경고 + 실제 TTC ≤ 5초 → 정상 경고
  - 경고 + 실제 TTC > 5초 → 오경보
