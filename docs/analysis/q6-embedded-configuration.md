## 1. 선택 기준

계획서 Q6에서는 기능을 유지하면서 가장 효율적인 설정을 고르기로 했다. 그래서 FCW 기능 확인을 통과한 조합만 비교했다.

### 기능 확인을 통과한 항목

- Crop 288: 평가셋 21개 중 20개는 첫 경고 프레임까지 같았다. 04만 결과가 달랐고(640 놓침 → 288 경고), 원인은 Crop 검출이 아닌 TTC-P였다(9/24).
- FP16: FP32와 21개 영상의 판정·첫 경고 프레임이 같았다(9/27).
- GPU 전처리 v1·v2: 입력 텐서가 CPU 경로와 비트 단위로 같았고, 골든·FCW 결과도 유지됐다(10/7·10/8).
- GPU 후처리: 후보 목록이 CPU 경로와 비트 단위로 같았고, 골든·FCW 결과도 유지됐다(10/9).
- Power Mode 3개: 파일 9회에서 골든이 같았다. 모드에 따라 달라진 것은 속도와 전력이었다(10/8).
- 스레드 분리 켬/끔: 처리가 카메라 간격보다 빠르면 Frame Age·drop이 같았다(9/29). FCW 결과는 비교하지 않았다. 최종 설정은 동기 캡처이므로 이 비교가 최종 FCW 결과에 영향을 주지는 않는다.

### 최종 비교에서 제외한 항목

- INT8 Entropy: 당시에는 가장 빠른 설정이었지만(13.6 ms, GPU 전처리 기준), FP32가 신뢰도 0.4 이상으로 검출한 박스의 25.2%를 놓쳤다. 기능 손실이 있어 제외했다.
- INT8 MinMax: 놓침은 2.4%까지 회복했고 처리 시간은 14.0 ms였다. 하지만 박스 높이 흔들림(2px 넘는 짝 29%)이 TTC-P에 주는 영향을 확인하지 못했다. 문제가 확인돼서 버린 것이 아니라, 검증이 끝나지 않아 보류한 상태다.
- `turn` (자차 회전 보정, 10/9): x86에서는 01을 68프레임에 경고했지만, Jetson 41개에서는 12규칙과 판정이 모두 같았다. 01의 TTC가 2.56초여서 DANGER 기준에 도달하지 못했다. 이득은 0이고 비용은 프레임당 +9.2 ms여서 최종 조합에서 제외했다. 코드는 기본 꺼짐 상태로 남겼다(q1 10절).

### 지연 기준

계획서 목표는 15 FPS, 즉 프레임당 66.7 ms다(Q2). 카메라는 30fps로 들어오므로 33.3 ms 안에 처리해야 프레임이 밀리지 않는다(Q3). 최종 설정은 파일 11.2 ms, 카메라 9.5 ms로 두 기준을 모두 충족했다.

## 2. 구조·정밀도 (자세한 표는 q4·q5)

| | 속도 (Jetson 5회 p50) | 정확도 | 결정 |
| --- | --- | --- | --- |
| Crop 640 → 288 | 32.7 → 26.1 ms (−20%) | 멀리 있는 낮은 신뢰도의 박스 일부가 빠졌다. 21개 중 20개는 첫 경고가 같았다(04만 다름). | 채택 |
| FP32 → FP16 (288) | 31.1 → 26.1 ms (−16%) | 판정·첫 경고 같음, 높이 ≤1px 99.2% | 채택 |
| FP16 → INT8 Entropy | 26.1 → 23.9 ms (−8%) | 확실한 박스 25.2% 놓침 | 탈락 |
| FP16 → INT8 MinMax (10/8, GPU 전처리) | 16.7 → 14.0 ms (−16%) | 놓침 2.4%, 높이 흔들림 29% 미검증 | 보류 |

정밀도를 바꾸면 추론 시간만 달라진다. 당시 FP16 288의 추론 비중은 프레임 처리 시간의 34%였고, 나머지 약 17 ms(현재 기준 13 ms)는 정밀도와 관계없었다. 그래서 INT8보다 아래의 Memory Path, 즉 고정 비용을 줄이는 작업을 먼저 진행했다.

GPU 후처리를 적용한 뒤에는 상황이 달라질 여지가 있다. 현재 프레임 11.2 ms 중 추론이 7.7 ms로 69%를 차지한다. INT8에서 줄일 수 있는 추론 시간 약 2 ms는 이제 프레임의 약 18%다. 다만 MinMax 좌표 흔들림의 FCW 영향을 아직 확인하지 못했으므로 FP16을 유지했다.

## 3. Memory Path — 카메라에서 GPU 입력까지 복사가 몇 번인가

### 3-1. 복사 횟수 (10/2, 코드 기준, 카메라 640×480·FP16 288, CPU 경로, 한 프레임)

| 단계 | 하는 일 | 크기 | 종류 |
| --- | --- | ---: | --- |
| 커널 | USB 패킷 → 카메라 버퍼 | 0.61 MB | 줄일 수 없음 (USB 카메라 드라이버) |
| 캡처 | YUYV → BGR (`cvtColor`) | 0.92 MB | 변환 |
| Full | resize / pad / blob | 0.92 / 1.23 / 4.92 MB | 변환 |
| Full | blob → pinned `memcpy` / H2D / D2H | 4.92 / 4.92 / 2.82 MB | 순수 복사 |
| Crop | `clone` | 0.17 MB | 순수 복사 |
| Crop | resize / pad / blob | 0.46 / 0.55 / 2.21 MB | 변환 |
| Crop | blob → pinned `memcpy` / H2D / D2H | 2.21 / 2.21 / 1.27 MB | 순수 복사 |

앱이 새 버퍼에 쓰는 횟수는 프레임당 14번, 양은 29.7 MB다. 커널까지 포함하면 15번, 30.3 MB이며, 30fps에서는 초당 약 0.9 GB다. 이 가운데 계산 없이 데이터를 옮기기만 하는 순수 복사는 7번, 18.5 MB였다.

Orin은 CPU와 GPU가 같은 메모리를 사용한다. H2D(CPU → GPU)와 D2H(GPU → CPU)도 같은 메모리 안에서 데이터를 옮기는 것이므로, 원리상 없앨 수 있는 복사다.

### 3-2. 카메라 버퍼를 GPU가 직접 읽을 수 있나 (10/2, `dmabuf_probe`)

| 확인 | 결과 |
| --- | --- |
| 드라이버 / 버퍼 방식 | uvcvideo. MMAP·USERPTR·DMABUF를 모두 지원하며, EXPBUF로 버퍼를 다른 장치에 넘길 수 있다. |
| GPU 속성 | integrated=1, canMapHostMemory=1, hostRegisterSupported=1. CPU·GPU가 같은 메모리를 사용하며, 일반 메모리는 등록해야 GPU가 읽을 수 있다. |
| `cudaHostRegister(Mapped)` on MMAP 버퍼 | 성공. 현재 코드의 MMAP 버퍼를 그대로 등록하면 GPU가 복사 없이 읽을 수 있다. |

### 3-3. 메모리 종류별 속도 (10/7, `mem_probe`, 저장소 밖)

| GPU 읽기 (GPU ms) | device | pinned | registered | managed |
| --- | ---: | ---: | ---: | ---: |
| Full 입력 4.92 MB | 0.064 (76 GB/s) | 0.138 (36 GB/s) | 0.139 | 0.165 |
| YUYV 0.61 MB | 0.013 | 0.044 | 0.043 | 0.056 |

| 복사 (ms) | Full | Crop |
| --- | ---: | ---: |
| blob → pinned `memcpy` | 0.504 | 0.190 |
| H2D | 0.200 | 0.105 |
| D2H | 0.127 | 0.071 |

Orin에서 GPU가 pinned·등록 메모리를 읽을 때는 CPU 캐시와 데이터가 일치하도록 맞추면서(I/O coherent), GPU 쪽 캐시는 사용하지 않는다. 읽기 속도는 GPU 전용(device) 메모리의 절반이었고, managed가 가장 느렸다.

이 결과를 기준으로 GPU가 여러 번 읽는 큰 버퍼에는 device 메모리를, 한 번만 읽는 카메라 버퍼·프레임 입력에는 등록 메모리를 쓰는 것이 맞다고 봤다.

카메라 MMAP 버퍼를 직접 읽는 실험도 150프레임 진행했다. GPU 시간은 0.047 ms, 값은 150/150 일치했다. 복사한 뒤 읽는 방식과 시간이 같아서, 읽기 시간 증가 없이 복사 한 번(0.6 MB)을 없앨 수 있었다.

| ① blob을 pinned 버퍼에 바로 만들기 | `memcpy` 2번, 7.1 MB | 0.7 ms | CPU 경로의 보조 수단이다. GPU 경로에서는 이 복사가 없어 적용하지 않았다. |
| ② mapped pinned 입출력 | H2D·D2H 4번, 11.2 MB | CPU 경로 0.5 ms, GPU 경로 0.16 ms | 적용하지 않음 (pinned 읽기가 절반 속도) |
| ③ GPU 전처리 v1 (파일) | resize·pad·blob·memcpy·H2D를 커널 한 번으로 처리 | **프레임 −5.6 ms** (전처리 5.8 → 1.6) | **채택** |
| v2 카메라 버퍼 직접 읽기 | Full·Crop용 BGR 업로드 2번(1.09 MB) | 전처리 −0.2 ms | **채택** (카메라 전용) |
| GPU 후처리 | 후보 탐색을 커널로 옮기고, 출력 전체 대신 후보 기록만 내려받기 | **프레임 −5.5 ms** (후처리 5.02 → 0.05 ms) | **채택** |
| 프레임 버퍼 pinned 등록 | GPU 경로 업로드 720p 0.30 → 0.12, 1080p 0.67 → 0.24 ms | 0.2~0.4 ms | 후속 작업 |
| managed 메모리 | — | 가장 느림 | 사용하지 않음 |

복사 횟수와 양을 줄이는 것이 곧 같은 만큼의 시간 절감으로 이어지지는 않았다. 시간은 주로 `blobFromImage`(4.5 ms)와 후보 탐색(5 ms) 계산을 GPU 커널로 옮기면서 줄었다. 순수 복사는 memcpy 0.69 + H2D 0.31 + D2H 0.20으로, 모두 합쳐도 약 1.2 ms였다. 이것이 ①·②를 적용하지 않은 근거다.

### 3-5. GPU 전처리 — 설계와 검증

OpenCV 4.x의 8비트 선형 보간은 계수까지 정수로 계산한다. CPU와 같은 입력 텐서를 만들기 위해 아래 계산식을 그대로 CUDA 커널로 옮겼다.

- 좌표: `(d+0.5)·scale−0.5`
- 계수: `cvRound(f·2048)`
- 세로 합: `(((b0·(h0>>4))>>16)+((b1·(h1>>4))>>16)+2)>>2`
- 정확히 2배 축소할 때: `(a+b+c+d+2)>>2`
- `/255`: 256칸 표 사용

그 결과 입력 텐서가 CPU 경로와 비트 단위로 같았다. 새 골든을 만들 필요 없이 기존 골든과 평가셋 CSV로 검증할 수 있었다.

v2에서는 MMAP 버퍼 4장을 `cudaHostRegister(Mapped)`로 등록했다. 커널이 YUYV → BGR(BT.601 정수식)·letterbox·blob을 한 번에 처리하며, 버퍼는 다음 `read()`까지 보관한 뒤 카메라에 반환한다. `--camera`·`--gpu-preprocess`가 필요하고, `--threaded-capture`와는 함께 사용할 수 없다.

검증 기준은 코드를 작성하기 전에 정했다. 입력 텐서 차이 1~2, 박스 높이 차 1px 이하 99%, FCW 21개 판정 일치, harness 5회를 기준으로 삼았고, 실제 결과는 모두 완전히 일치했다.

`--gpu-preprocess-check`로 GPU 텐서·CPU 경로·CPU 기준 함수 셋을 비교했다. input.mp4 1252·03 150·02 150프레임의 Full·Crop이 전부 일치했다. 이를 통해 Jetson OpenCV가 다른 가속 구현인 Carotene HAL로 실행되는 것도 아님을 확인했다. 카메라 190프레임도 일치했다.

720p 파일의 프레임당 쓰기는 13회 28.9 MB에서 6회 14.5 MB로 줄었다. 카메라는 v1 → v2에서 13.23 → 12.14 MB로 줄었다.

### 3-6. GPU 후처리 — 설계와 검증 (10/9)

후처리 5 ms의 대부분은 후보를 훑는 데 쓰였다. 후보 8400 + 3780개마다 클래스 점수 80개 중 최댓값을 찾고, 기준값과 비교하는 작업이다. 출력이 (채널, 후보) 순서라 한 후보의 점수 80개가 메모리에서 후보 수만큼 떨어져 있다. 이 구조 때문에 CPU 캐시를 효율적으로 사용하지 못한 것으로 봤다. 구조를 바탕으로 한 추정이며, 원인별 시간을 따로 측정하지는 않았다.

GPU 커널에는 후보 하나당 스레드 하나를 배정했다. 최댓값을 찾고 기준값과 비교하는 작업만 옮겼다. 비교 연산만 수행하므로 반올림 차이가 생기지 않는다. 같은 값이 여럿이면 OpenCV `minMaxLoc`과 같이 앞 번호를 고르고, NaN은 건너뛴다.

좌표 복원과 NMS는 CPU에 남겼다. 두 작업은 0.04~0.05 ms였고, NMS가 후보 순서에 민감하므로 후보도 원래 번호 순서로 모았다.

내려받기(D2H)는 출력 전체인 Full 2.82 + Crop 1.27 = 4.09 MB 대신, 후보마다 남김 표시 1바이트와 후보 기록 28바이트만 가져오도록 바꿨다. 계산상 내려받기 양은 12,180개 × 29바이트 ≈ 0.35 MB다.

검증은 x86과 Jetson에서 진행했다. x86에서는 같은 값이 많은 경우를 포함해 CPU 기준 함수와 217가지 단위 비교를 했고, 평가 CSV 16/16이 같았다. Jetson에서는 `--gpu-postprocess-check`의 다른 값이 0이었고, 골든 `4681f432`·12규칙 골든도 같았다. 평가셋 41개 CSV 역시 82/82 일치했다.

10/9 밤 harness의 5회 가운데값은 프레임 16.7 → 11.2 ms(−33%), 검출 14.5 → 8.9 ms였다. GPU 커널과 내려받기는 0.09 ms였다. 10/9의 1회 값인 16.9 → 11.3 ms와도 0.1~0.2 ms 차이로 비슷했다.

코드를 바꾸지 않은 전처리 시간도 1.65 → 1.19 ms로 줄었다. 업로드가 없는 카메라 v2에서도 1.16 → 0.72 ms로 비슷하게 줄어, 업로드만으로는 설명되지 않는다. 카메라의 두 값은 날짜·빌드·규칙 수가 다른 조건에서 각각 한 번씩 측정했다. 커널 시작·대기 비용이 다른 측정 구간으로 옮겨간 것으로 보지만 원인은 확인하지 못했다. 따라서 효과는 프레임 전체 시간의 차이로 제시했다.

GPU 전처리에서는 Full·Crop 추론 시간이 각각 약 0.5 ms 줄었고, 5회 모두 같은 현상이 나왔다. GPU를 연속해서 사용하면서 시작 비용이 전처리 측정 구간으로 옮겨간 것으로 추정한다. 원인을 확인한 것은 아니다.

1080p(03)는 1회 측정했으며, CPU 23.8 → GPU 전처리 17.6 ms로 −26% 줄었다. 720p는 Full이 정확히 2배 축소되는 빠른 경로이고 Crop은 복사만 한다. 그래서 1080p보다 전처리가 1.2 ms 짧고, GPU 전처리의 이득도 상대적으로 작게 보인다.

10/7에 확인한 정정 사항도 있다. 9/27 정식 표의 26.1 ms에는 초록 도로 영역을 그리는 시간 약 3.7 ms가 포함돼 있었다. 같은 설정을 10/7 바이너리로 측정하면 22.2~22.3 ms다.

영상 파일은 다음 프레임을 기다리지 않고 바로 처리한다. 처리 속도가 빨라질수록 GPU가 쉬는 시간이 줄어 전력이 오른 것으로 봤다(전력 +8%, GPU 사용률 33 → 43%). 그래도 같은 작업을 더 짧은 시간에 끝내므로 프레임당 에너지는 226 → 180 mJ로 −20% 줄었다. CPU 경로와 비교하면 −35%다.

GPU 전처리의 10.6 W, 226 mJ는 10/8 Power Mode MAXN_SUPER 3회 측정값인 10.8 W, 231 mJ와도 약 2% 차이였다.

#### RAM

tegrastats의 RAM은 OS를 포함한 보드 전체 사용량이다. 표의 증가량은 기록 중 최대 − 최소로 계산한 근사치다. 최소값은 프로그램이 막 실행된 시점 또는 그 직전의 값이다.

경로 간 차이 5~20 MB는 15회 측정의 증가량 변동 범위인 367~432 MB 안에 있었다. 따라서 GPU 경로를 켜도 RAM은 늘어나지 않은 것으로 봤다. GPU 후처리에 추가한 후보 기록 버퍼 약 0.35 MB는 MB 단위 측정에서 드러나지 않았다.

#### CPU 사용률

세 경로의 CPU 사용률은 15회 모두 16.2~17.0%였다. 6코어 중 1코어가 가득 찬 값인 16.7%에 해당하는 것으로 추정한다. 처리 스레드가 계속 실행되고 GPU를 기다리는 동안에도 바쁘게 대기하므로, 파일 입력의 CPU%만으로는 CPU 작업이 얼마나 줄었는지 확인하기 어렵다.

카메라는 30fps가 상한이다. 따라서 GPU 전처리의 효과는 FPS보다 지연과 처리 여유에서 나타났다. Frame Age는 −6.1 ms 줄었고, 33.3 ms 중 남는 시간은 12.3 → 18.4 ms로 늘었다. v2가 v1보다 0.2 ms만 빠른 이유는 입력이 640×480이라, 원래 업로드하던 BGR도 1.09 MB로 작았기 때문이다.

10/10 최종 설정에서는 10/8 v2보다 처리 시간과 Frame Age가 모두 5.4 ms 줄었다. 예상했던 처리 약 10 ms·Frame Age 약 42 ms와 비슷했다. 주된 변경은 GPU 후처리였고, 규칙도 11 → 12로 늘었으며 빌드도 달라졌다. Frame Age − 처리는 32.2 ms로 같았으므로 줄어든 지연은 전부 처리 시간에서 나왔다.

10/8 카메라 CPU 경로와 비교하면 처리 시간은 −11.5 ms(−55%), Frame Age는 −11.5 ms(−22%) 줄었다. 남는 시간은 12.3 → 23.8 ms로 약 2배가 됐다. 카메라 간격의 71%가 남으므로, 처리가 지금보다 약 3.5배 느려져도 프레임을 놓치지 않는다.

측정 전 `camera_probe`로 확인한 간격 p50은 32.0 ms, Frame Age 하한은 32.2 ms였다. 측정 중 CPU 클럭은 1728 MHz로 고정됐고, 최고 온도는 54.1 °C였다.

전력은 −0.2 W(−2%)만 줄었다. 카메라는 30fps로 작업량이 고정되고 보드 기본 전력이 대부분이어서, 파일의 프레임당 에너지 −20%와 달리 전력 이득이 거의 없었던 것으로 추정한다.

전처리 코드는 그대로였지만 전처리 시간은 1.16 → 0.72 ms로 줄었다. 빌드·규칙 수는 달랐다. 3-6의 파일 측정과 비슷한 현상이며, 원인은 확인하지 못했다.

## 8. 한계

- 카메라는 조합마다 1회 측정했다. 입력은 640×480 YUYV로, 파일의 1280×720이나 실제 ADAS 카메라와 크기가 다르다. 카메라가 한때 25fps로 동작한 원인은 확인하지 못했고, 측정 전에는 `camera_probe`로 30fps를 확인했다. drop이 0이어서 촬영 시각 차이는 반영하지 않았다.
- 파일 측정은 720p 중심이다. 1080p는 GPU 전처리까지 1회 측정했으며, GPU 후처리는 측정하지 않았다.
- 카메라 최종 설정은 1회 측정값이고, 10/8의 세 경로와 바이너리·규칙 수(11 → 12)가 다르다.
- 계획서의 Memory는 복사 횟수(Memory Path)와 RAM 사용량으로 나눠 확인했다. RAM은 tegrastats가 기록한 보드 전체 사용량의 최대 − 최소로 구한 근사치다. 프로세스 단독 사용량은 측정하지 않았다.
- GPU를 기다리는 동안 CPU가 바쁘게 대기(spin)하므로, 파일 입력의 CPU%는 작업량을 보여 주지 못한다. 세 경로 모두 약 16.7%로 1코어에 해당했다.
- VDD_IN은 보드 전체 전력이다. 파일 평균에는 엔진을 불러오는 등 시작 1~2초가 포함돼 있고, 실행이 짧은 GPU 후처리(21초)에서는 이 구간의 비중이 조금 더 크다. 에너지는 평균 전력 ÷ FPS로 구한 대략값이다.
- GPU 전처리·후처리는 CUDA를 사용하므로 Jetson 전용이다. TOPST에는 CUDA가 없어 해당 보드의 전처리·후처리 경로를 다시 확인해야 한다.

## 9. 확인한 것

처리 시간은 출발점 237 ms에서 TensorRT FP16 288 26.1 ms(초록 영역 포함), GPU 전처리 16.7 ms, GPU 후처리 11.2 ms(5회)로 줄었다. 최종 처리 시간은 15 FPS 목표의 0.17배다. 카메라는 처리 9.5 ms·Frame Age 41.7 ms였다.

INT8로 정밀도를 낮춰 줄인 시간은 −2~3 ms였다. 정밀도와 관계없는 계산을 GPU로 옮겼을 때는 전처리 −5.6 ms, 후처리 −5.5 ms로 효과가 더 컸고 결과도 그대로 유지됐다.

GPU 전처리는 정수 보간식을 그대로 옮겼고, GPU 후처리는 비교 연산만 수행했다. 두 경로 모두 비트 일치를 얻어 새 골든 없이 기존 골든과 평가셋 CSV로 검증할 수 있었다.

복사는 횟수와 양을 각각 확인했다. 720p 파일의 쓰기 횟수는 13 → 6회였고, 카메라 CPU 경로는 14회였다. 파일의 쓰기 양은 28.9 → 14.5 MB, GPU 후처리의 내려받기는 4.09 → 0.35 MB로 줄었다. 시간 절감은 주로 blob 4.5 ms와 후보 탐색 5 ms의 계산을 커널로 옮긴 데서 나왔다. 순수 복사 시간은 모두 합쳐도 약 1.2 ms였다.

GPU 경로를 켜도 RAM은 늘지 않았고, 보드 전체 약 2.2 GB를 사용했다. 파일 프레임당 에너지는 276 → 180 mJ로 줄었다. 카메라 전력은 8.9 → 8.7 W로 차이가 거의 없었다.

Power Mode는 결과를 유지하면서 지연과 전력만 바꿨다. MAXN_SUPER를 최종 선택했고, 15W는 저전력 대안으로 남겼다.

최종 설정은 Full 640 + Crop 288, TensorRT FP16, GPU 전처리(파일 v1·카메라 v2)·GPU 후처리, 동기 캡처, LEAD 12규칙, MAXN_SUPER다. 파일 720p에서는 11.2 ms(63.4 FPS, 5회), 카메라에서는 9.5 ms(Frame Age 41.7 ms)를 기록했으며, FCW 결과는 CPU 경로와 비트 단위로 같았다.
