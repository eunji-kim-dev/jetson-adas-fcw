# Q2/Q3 — Jetson CPU 속도와 병목 확인

작성일: 2026-09-13 | 작성자: 김은지
관련 질문: Q2 — 현재 얼마나 빠른가 / Q3 — 어디에서 가장 오래 걸리는가

> **정정 (2026-09-24)** — 아래 수치는 9/13 측정값이다. 당시 빌드는 `CMAKE_BUILD_TYPE`이 비어 있어 Release 최적화가 적용되지 않았다. 9/14에 Release로 다시 측정한 Jetson CPU 기준값은 **p50 235.1~238.2ms (약 4.2 FPS)** 이고, harness의 golden도 이 측정을 기준으로 한다. YOLO 2회 추론이 병목이고 나머지는 최적화 대상이 아니라는 결론은 그대로다. 다만 목표까지 필요한 속도 향상은 5배가 아니라 **약 3.5배**다(237 / 66.7). 이 문서의 표와 본문은 Release 이전 값이므로 그대로 인용하면 안 된다. Release 기준 단계별 수치는 9/14 세션(`results/benchmark_sessions/`)의 `analyze_runs.py` 결과를 사용한다.

> **정정 (2026-10-09)** — 최종 값은 `q2-q3-speed-bottleneck.md`에 정리했다. 이후 변경 사항은 다음과 같다.
>
> ① 기준값은 9/14에 측정한 Release 빌드의 235.1~238.2 ms다.
>
> ② 5절의 Crop 288×640은 9/25에 채택했다. 처리 시간은 Jetson에서 −20%, x86에서 −27%였다.
>
> ③ TensorRT FP16 288에 GPU 전처리를 적용하면 16.7~16.8 ms, GPU 후처리까지 적용하면 11.1~11.2 ms다. 10/9 같은 밤에 연속 세션으로 각각 5회 측정했다. 병목은 YOLO 추론 → 전처리·후처리 → 다시 추론으로 옮겨 갔다.
>
> ④ 6절의 deadline은 harness에서 66.7 ms로 고정했다.
>
> ⑤ 7절에서 발열을 의심한 뒤로 tegrastats를 함께 기록했다. 이후 측정에서는 클럭 하락이 없었다.
>
> ⑥ 8절의 build type·클럭·warm-up은 harness가 검사하고 고정한다. Jetson에서 `run_summary.json`의 온도·`jetson_clocks` 칸이 null로 나오는 문제는 남아 있다. harness의 장비 기록 파일에는 값이 있다.

## 0. 결론

Jetson Orin Nano Super에서 현재 FCW 프로그램을 CPU 기반 OpenCV DNN으로 5회 실행해 기준 속도를 측정했다. 결과는 **프레임당 약 333ms, 약 3 FPS**였다. 목표는 15 FPS이므로 약 **5배** 빨라져야 한다.

시간이 가장 오래 걸리는 곳은 YOLO 추론이었다. 현재 한 프레임마다 전체 화면 Full과 관심 영역 Crop을 각각 한 번씩 추론한다. 두 추론에 걸린 시간은 합쳐서 약 314ms로, 전체 333ms의 **약 94%**였다. 전처리, 후처리, tracking, FCW 판단을 모두 합쳐도 20ms가 되지 않았다.

따라서 병목은 **YOLO 추론 자체**다. 목표 15 FPS에 도달하려면 추론 연산량을 줄이면서 TensorRT GPU 가속도 함께 적용해야 한다. 연산량을 줄이는 방법으로는 Crop 입력의 letterbox 여백을 제거한 288×640 모델을 검토하고 있다. 실제 효과는 Q4에서 측정한다.

| 항목 | 내용 | | 항목 | 내용 |
|---|---|---|---|---|

| 전력 모드 | MAXN_SUPER | | 프레임 수 | 1252 |
| JetPack / OpenCV | 7 / 4.8.0 | | 모델 | yolov8n.onnx |

같은 영상과 모델로 5회 연속 실행했다. 입력 영상과 모델의 해시가 5회 모두 같았으므로 실행마다 입력 조건이 바뀌지는 않았다.

## 2. 실제 속도

| Run | Full 추론 | Crop 추론 | 전체 p50 | 전체 p95 |
|---|---:|---:|---:|---:|
| r01 | 166.8ms | 154.1ms | 338.8ms | 394.9ms |
| r02 | 160.9ms | 150.6ms | 331.3ms | 369.2ms |
| r03 | 161.5ms | 149.4ms | 328.5ms | 377.2ms |
| r04 | 159.7ms | 151.8ms | 332.8ms | 390.9ms |
| r05 | 161.7ms | 151.8ms | 332.7ms | 390.0ms |
| **평균** | **162.1ms** | **151.5ms** | **332.8ms** | **384.4ms** |

평균 약 333ms이므로 처리 속도는 `1000 / 333 ≈ 3 FPS`다. Jetson CPU만 사용하면 초당 약 3장을 처리할 수 있다.

**p50과 p95를 읽는 법**

p50은 평소 처리 속도, p95는 느린 경우까지 포함한 속도로 보면 된다. 평균 p50은 약 333ms, p95는 약 384ms로 두 값의 차이가 크지 않았다. 특정 프레임에서 처리 시간이 몇 배씩 튀는 형태는 아니었다.

---

## 3. 5회 반복 결과가 일정했는가

각 run의 전체 처리 p50은 `328.5ms ~ 338.8ms` 범위였다. 차이는 약 10ms, 비율로는 **약 3.1%**다. 5번 실행한 결과가 거의 비슷했다.

| 환경 | 전체 처리 p50 |
|---|---:|
| x86 WSL2 | 약 226ms |
| Jetson | 약 333ms |

평균적으로는 x86이 더 빨랐다. 다만 x86은 실행마다 차이가 컸고, 한 run은 약 375ms까지 느려졌다. Jetson은 5회 결과가 비교적 일정했다. 앞으로 Jetson에서 CPU / TensorRT FP32 / FP16 / INT8을 비교할 때 이번 측정을 기준값으로 사용할 수 있다.

x86과 Jetson은 OpenCV 버전, 실행 환경, warm-up 조건이 다르다. 따라서 이번 x86 값은 참고용이며, “x86 CPU가 Jetson CPU보다 1.47배 빠르다”와 같은 순수 CPU 성능 비교로 해석하면 안 된다.

---

## 4. 가장 중요한 부분 — 어디에서 느린가

r01을 기준으로 한 프레임의 처리 시간을 단계별로 나눴다.

| 처리 단계 | 시간 | 전체 비중 |
|---|---:|---:|
| Full YOLO 추론 | 166.8ms | 49% |
| Crop YOLO 추론 | 154.1ms | 45% |
| 전처리 | 약 10ms | 3% |
| 후처리 | 약 8ms | 2% |
| 영상 읽기 | 2.7ms | 약 1% |
| Tracking | 0.1~0.3ms | 거의 0% |
| 결과 Merge | 0.03ms | 거의 0% |

run 평균으로 보면 두 추론을 합쳐 약 314ms이며, **전체의 약 94%**다. 현재 프로그램이 느린 이유는 거의 전적으로 YOLO를 한 프레임에서 두 번 실행하기 때문이다. tracking, TTC 계산, 후처리가 주된 원인은 아니었다.

전체 화면을 추론한 뒤, 원거리의 작은 객체를 잡기 위해 관심 영역 Crop을 잘라 한 번 더 추론한다. 여기서 Crop 영역이 작아도 추론 시간은 거의 줄지 않았다. Full은 약 162ms, Crop은 약 152ms로 차이가 10ms뿐이었다. 모델 입력 크기가 같으면 Crop 영역이 작아도 연산량은 같기 때문이다. Q3에서 확인하려던 “Full+Crop 2회 추론이 병목인가”라는 가설이 수치로 확인됐다.

나머지를 최적화해도 효과는 작다. tracking은 현재 약 0.2ms인데, 이 시간을 0으로 줄여도 333ms가 332.8ms가 될 뿐이다. FCW 위험 판단과 TTC 계산도 전체 시간에서 거의 보이지 않는 수준이다. 따라서 Q1에서 TTC를 호모그래피 방식으로 바꿔도 **성능에는 영향이 없다.**

## 5. 목표 15 FPS까지

15 FPS를 내려면 한 프레임에 `1초 / 15 = 66.7ms`까지 쓸 수 있다. 현재는 약 333ms이므로 `333 / 66.7 ≈ 5`, 즉 **약 5배** 빨라져야 한다.

전체 시간의 94%가 추론에 쓰이므로 줄여야 할 부분도 추론이다. 접근 방법은 서로 독립적인 두 가지다.

**Crop 입력 해상도로 연산량 줄이기**

현재 Crop 추론은 입력을 정사각형으로 맞추면서 letterbox 회색 여백이 크게 생긴다. 정보가 없는 여백에도 연산이 들어간다. 이 여백을 제거한 `yolov8n_288x640.onnx`를 후보로 준비했다. 입력 픽셀 수가 640×640의 약 45% 수준이므로 Crop 추론 시간이 줄어들 것으로 예상한다. 다만 **아직 x86·Jetson 어느 쪽에서도 측정하지 않았다.** 정확도 손실 없이 연산량만 줄이는 변경이므로, 해상도를 낮춰 정확도와 속도를 맞바꾸는 방식과는 성격이 다르다.

**TensorRT로 GPU 가속 적용하기**

CPU OpenCV DNN 대신 Jetson GPU를 쓰면 추론 시간을 크게 줄일 수 있다. 특히 FP16과 INT8에서는 GPU와 Tensor Core를 활용할 수 있다.

두 방법의 효과는 Q4에서 각각 측정한다. 입력과 코드를 같게 두고 구조별·정밀도별 수치를 따로 비교해야 어느 변경이 더 효과적이었는지 구분할 수 있다.

현재 단계에서 특정 배속을 확정하지는 않았다. 다만 5배라는 격차를 한 가지 변경만으로 메우기는 어렵고, 구조와 하드웨어 양쪽의 변경이 필요하다고 판단했다.

```
현재 (Full 640 + Crop 640, CPU)   약 333ms / 약 3 FPS
  ↓ Crop 입력 288×640 적용          → Q4에서 측정
  ↓ TensorRT FP16 / INT8            → Q4에서 측정
목표                               66.7ms 이하 / 15 FPS 이상
```

9/28 구조 결정에서는 288×640 Crop 모델의 채택 여부를 판단한다. 640 대비 속도 이득과 검출 결과 변화를 같은 조건에서 비교해야 한다. 계획서대로 x86과 Jetson 양쪽에서 실행한 뒤 결정한다.

## 6. harness의 deadline 값 문제

현재 harness의 deadline은 `33.367ms`로 설정되어 있다. 입력 영상이 29.97 FPS라서 나온 값이다. 영상의 원래 FPS를 실시간으로 따라가려면 33ms 안에 처리해야 한다는 뜻이다.

계획서의 목표는 15 FPS이고, 이에 해당하는 deadline은 66.7ms다. 현재는 두 기준이 섞여 있다.

앞으로 `deadline miss`를 성능 지표로 사용하려면 **15 FPS 기준인 66.7ms로 맞춰야 한다.** 원본 영상의 FPS는 입력 특성으로 따로 기록하면 된다.

## 7. 측정 중 발견된 이상 구간

**추론 시간이 잠깐 늘어난 구간**

첫 번째 run의 프레임 827~843에서 추론 시간이 잠깐 증가했다. 평소에는 Full 약 160ms / Crop 약 150ms였지만, 이 구간에서는 두 추론이 동시에 약 205ms까지 올라갔다. 둘 다 느려졌으므로 특정 이미지나 모델보다 시스템 전체 상태의 영향으로 보인다. 발열에 따른 클럭 변화가 유력하지만, 이번에는 온도와 클럭을 기록하지 않아 확인하지 못했다. 다음 측정에서는 `tegrastats`를 함께 기록해 확인할 예정이다.

**영상 저장 시간 증가**

`output_ms`는 run이 진행되는 동안 약 21ms에서 27ms로 늘어났다. 결과 영상을 microSD에 저장하고 있어 쓰기 속도나 버퍼의 영향일 수 있다. 이 시간은 `total_processing_ms`에 포함되지 않는다. 실제 차량에서 FCW만 실시간으로 동작시킬 때는 결과 AVI를 저장할 필요도 없으므로 현재의 핵심 병목으로 보지 않았다. 추후 저장 경로를 SSD로 옮겨 차이를 확인할 수 있다.

## 8. 다음 측정에서 추가할 것

이번 측정에서 빠진 항목을 정리했다.

| 항목 | 현재 | 조치 |
|---|---|---|
| 온도 | `temperature_start_c / end_c = null` | `tegrastats`로 시작·종료 온도를 기록한다. 7절의 원인 확인에 필요하다 |
| Jetson 클럭 | `jetson_clocks = null` | 클럭 고정 여부를 기록한다. 상태가 다르면 같은 코드도 처리 시간이 달라진다 |
| Build Type | `build_type = ""` | `CMAKE_BUILD_TYPE=Release`를 명시해 조건을 고정한다 |
| Warm-up | 제외 없이 전체 프레임 사용 | x86은 처음 15프레임을 제외했다. 양쪽 조건을 맞춘다 |
| Run 사이 대기 | 5회 연속 실행 | 뒤쪽 run에 열이 누적될 수 있으므로 harness 대기 조건을 일정하게 유지한다 |

## 9. 이번 측정으로 확인한 것

- Jetson CPU에서 현재 프로그램은 약 **3 FPS**로 동작한다.
- 5번 반복했을 때 전체 처리 속도 차이는 약 **3.1%**로 비교적 일정했다. 기준값으로 사용할 수 있다.
- 전체 시간의 약 **94%가 YOLO Full + Crop 추론 두 번**에 쓰인다. tracking이나 TTC 코드를 먼저 수정할 이유는 없다.
- 목표까지 약 **5배**의 격차가 있다. Q4에서 Crop 입력 해상도 축소(288×640)와 TensorRT 가속을 각각 측정해 두 변경의 효과를 따로 확인해야 한다.

Jetson이 느린 원인은 전적으로 YOLO 추론이다. 15 FPS를 내려면 추론 연산량 축소와 TensorRT 가속을 함께 적용해야 한다.
