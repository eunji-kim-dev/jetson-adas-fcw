# Q2/Q3 — Jetson CPU 속도와 병목 확인

작성일: 2026-09-13 | 작성자: 김은지
관련 질문: Q2 — 현재 얼마나 빠른가 / Q3 — 어디에서 가장 오래 걸리는가

> **정정 (2026-09-24)** — 아래 수치는 9/13 측정값이고, 그 빌드는 `CMAKE_BUILD_TYPE`이 비어 있어 Release 최적화가 안 된 상태였음. 9/14 Release로 다시 잰 Jetson CPU 기준값은 **p50 235.1~238.2ms (약 4.2 FPS)** 이고, harness의 golden도 그 값 기준임. 결론(병목은 YOLO 2회 추론, 나머지는 최적화 대상 아님)은 그대로 유효하지만, 목표까지의 배율은 5배가 아니라 **약 3.5배**임 (237 / 66.7). 이 문서의 표와 본문 숫자는 Release 이전 값이므로 그대로 인용하지 말 것. Release 기준 단계별 수치는 9/14 세션(`results/benchmark_sessions/`)의 `analyze_runs.py` 결과를 씀.

## 0. 결론

Jetson Orin Nano Super에서 현재 FCW 프로그램을 CPU 기반 OpenCV DNN으로 5회 실행해 기준 속도를 측정함. 결과는 **프레임당 약 333ms, 약 3 FPS**임. 목표가 15 FPS이므로 약 **5배** 빨라져야 함.

어디에서 시간이 걸리는지 확인해보니 원인은 명확했음. 현재 한 프레임마다 YOLO 추론을 두 번(전체 화면 Full + 관심 영역 Crop) 수행하는데, 두 추론에 걸리는 시간이 합쳐서 약 314ms임. 전체가 333ms이므로 **약 94%가 YOLO 추론임.** 반면 전처리, 후처리, tracking, FCW 판단은 모두 합쳐도 20ms가 안 됨.

따라서 병목은 다른 코드가 아니라 **YOLO 추론 자체**임. 목표 15 FPS에 도달하려면 추론 연산량을 줄이는 것과 TensorRT GPU 가속을 **같이** 적용해야 함. 연산량 축소는 Crop 입력에서 letterbox 여백을 제거한 288×640 모델을 후보로 두고 있으며, 실제 효과는 Q4에서 측정함.

## 2. 실제 속도

| Run | Full 추론 | Crop 추론 | 전체 p50 | 전체 p95 |
|---|---:|---:|---:|---:|
| r01 | 166.8ms | 154.1ms | 338.8ms | 394.9ms |
| r02 | 160.9ms | 150.6ms | 331.3ms | 369.2ms |
| r03 | 161.5ms | 149.4ms | 328.5ms | 377.2ms |
| r04 | 159.7ms | 151.8ms | 332.8ms | 390.9ms |
| r05 | 161.7ms | 151.8ms | 332.7ms | 390.0ms |
| **평균** | **162.1ms** | **151.5ms** | **332.8ms** | **384.4ms** |

평균 약 333ms이므로 처리 속도는 `1000 / 333 ≈ 3 FPS`임. 즉 Jetson CPU만 사용하면 초당 약 3장을 처리할 수 있음.

**p50과 p95란** — 쉽게 말해 p50은 평소 속도, p95는 느린 경우까지 포함한 속도임. 평균 p50이 약 333ms이고 p95가 약 384ms인데, 두 값 차이가 크지 않음. 특정 프레임에서 처리 시간이 몇 배씩 튀는 형태는 아니었음.

## 3. 5회 반복 결과가 일정했는가

각 run의 전체 처리 p50은 `328.5ms ~ 338.8ms` 범위였음. 차이가 약 10ms, 비율로는 **약 3.1%**임. 5번 실행해도 결과가 거의 비슷하게 나왔음.

| 환경 | 전체 처리 p50 |
|---|---:|
| x86 WSL2 | 약 226ms |
| Jetson | 약 333ms |

x86이 평균적으로는 더 빨랐음. 다만 x86은 실행마다 차이가 컸고 한 run은 약 375ms까지 느려졌음. Jetson은 5회가 비교적 일정했으므로, 앞으로 Jetson 내부에서 CPU / TensorRT FP32 / FP16 / INT8을 비교할 때 이번 값을 기준값으로 쓸 수 있음.

단, x86과 Jetson은 OpenCV 버전, 실행 환경, warm-up 조건이 다름. "x86 CPU가 Jetson CPU보다 1.47배 빠르다"처럼 순수 CPU 성능 비교로 해석하면 안 됨. 이번 x86 값은 참고용임.

## 4. 가장 중요한 부분 — 어디에서 느린가

한 프레임 처리 시간을 단계별로 나눠봄 (r01 기준).

| 처리 단계 | 시간 | 전체 비중 |
|---|---:|---:|
| Full YOLO 추론 | 166.8ms | 49% |
| Crop YOLO 추론 | 154.1ms | 45% |
| 전처리 | 약 10ms | 3% |
| 후처리 | 약 8ms | 2% |
| 영상 읽기 | 2.7ms | 약 1% |
| Tracking | 0.1~0.3ms | 거의 0% |
| 결과 Merge | 0.03ms | 거의 0% |

두 추론이 합쳐 약 314ms(run 평균 기준)로 **전체의 약 94%**임. 현재 프로그램이 느린 이유는 tracking이나 TTC 계산이나 후처리가 아니라, 거의 전적으로 **YOLO를 한 프레임에서 두 번 실행하기 때문**임.

**왜 두 번 돌리는가** — 전체 화면을 한 번 추론하고, 원거리 소형 객체를 잡기 위해 관심 영역 Crop을 잘라 한 번 더 추론함. 주목할 점은 Crop이라고 해서 추론 시간이 거의 줄지 않는다는 것임. Full 약 162ms, Crop 약 152ms로 차이가 10ms뿐임. Crop 영역이 작아도 모델 입력 크기가 같으면 연산량이 같기 때문임. **Q3에서 확인하려던 "Full+Crop 2회 추론이 병목인가" 가설이 수치로 확인됨.**

**나머지를 최적화해도 효과가 작은 이유** — tracking이 현재 약 0.2ms인데, 이걸 0으로 만들어도 333ms가 332.8ms가 될 뿐임. FCW 위험 판단과 TTC 계산도 전체에서 거의 보이지 않는 수준임. 따라서 Q1에서 TTC를 호모그래피 방식으로 바꿔도 **성능에는 영향이 없음.**

## 5. 목표 15 FPS까지

15 FPS면 한 프레임에 `1초 / 15 = 66.7ms`가 허용됨. 현재는 약 333ms이므로 `333 / 66.7 ≈ 5`, 즉 **약 5배** 빨라져야 함.

전체의 94%가 추론이므로, 줄일 수 있는 건 추론뿐임. 방향은 두 가지고 서로 독립적임.

**연산량 축소 — Crop 입력 해상도** — 현재 Crop 추론은 정사각형 입력에 맞추면서 letterbox 회색 여백이 크게 생기는 형태임. 이 여백은 원래 정보가 없는 영역인데 연산은 그대로 들어감. 여백을 제거한 `yolov8n_288x640.onnx`를 후보로 준비해 둠. 입력 픽셀 수가 640×640 대비 약 45% 수준이라 Crop 추론 시간이 줄어들 것으로 예상되나, **아직 x86·Jetson 어느 쪽에서도 측정하지 않았음.** 정확도 손실 없이 연산량만 줄이는 변경이라는 점에서, 해상도를 낮춰 정확도와 속도를 맞바꾸는 것과는 성격이 다름.

**하드웨어 가속 — TensorRT** — CPU OpenCV DNN 대신 Jetson GPU를 쓰면 추론 시간을 크게 줄일 수 있음. 특히 FP16과 INT8에서는 GPU와 Tensor Core를 활용할 수 있음.

두 방향의 효과는 Q4에서 각각 측정함. 같은 입력·같은 코드로 구조별·정밀도별 수치를 따로 봐야 어느 변경이 실제로 효과가 컸는지 구분할 수 있음.

현재 단계의 결론은 특정 배속을 확정하는 게 아니라, **5배라는 격차를 한 가지 변경만으로 메우기는 어렵고 구조와 하드웨어 양쪽이 필요하다**는 것임.

```
현재 (Full 640 + Crop 640, CPU)   약 333ms / 약 3 FPS
  ↓ Crop 입력 288×640 적용          → Q4에서 측정
  ↓ TensorRT FP16 / INT8            → Q4에서 측정
목표                               66.7ms 이하 / 15 FPS 이상
```

**9/28 구조 결정에서 판단할 것** — 288×640 Crop 모델을 채택할지 여부임. 640 대비 속도 이득과 검출 결과 변화를 같은 조건에서 비교해야 함. 계획서대로 x86과 Jetson 양쪽에서 실행한 뒤 판단함.

## 6. harness의 deadline 값 문제

현재 harness의 deadline이 `33.367ms`로 설정되어 있음. 입력 영상이 29.97 FPS라서 나온 값으로, 영상의 원래 FPS를 실시간으로 따라가려면 33ms 안에 처리해야 한다는 뜻임.

하지만 계획서의 목표는 15 FPS이고, 그 기준 deadline은 66.7ms임. 지금은 두 기준이 섞여 있음.

앞으로 `deadline miss`를 성능 지표로 쓴다면 **15 FPS 기준인 66.7ms로 맞출 필요가 있음.** 원본 영상 FPS는 입력 특성으로 따로 기록하면 됨.

## 7. 측정 중 발견된 이상 구간

**추론 시간 증가** — 첫 번째 run에서 프레임 827~843 구간에 추론 시간이 잠깐 증가했음. 평소 Full 약 160ms / Crop 약 150ms인데 이 구간은 두 추론이 **동시에** 약 205ms까지 올라갔음. 한쪽만이 아니라 둘 다 느려졌으므로 특정 이미지나 모델 문제라기보다 시스템 전체 상태의 영향으로 보임. 발열에 따른 클럭 변화가 유력하지만, 이번에는 온도와 클럭을 기록하지 않아 확인된 것은 아님. 다음 측정에서 `tegrastats`를 같이 기록해 확인할 예정임.

**영상 저장 시간 증가** — `output_ms`가 run 진행 중 약 21ms에서 27ms로 늘어남. 결과 영상을 microSD에 저장하고 있어서 쓰기 속도나 버퍼 영향일 가능성이 있음. 다만 이 시간은 `total_processing_ms`에 포함되지 않고, 실제 차량에서 FCW만 실시간 동작시킬 경우 결과 AVI를 저장할 필요도 없음. 현재 핵심 병목으로 보지 않음. 추후 저장 경로를 SSD로 옮겨 차이를 확인할 수 있음.

## 9. 이번 측정으로 확인한 것

- Jetson CPU에서 현재 프로그램은 약 **3 FPS**로 동작함.
- 5번 반복했을 때 전체 처리 속도 차이는 약 **3.1%**로 비교적 일정했음. 기준값으로 쓸 수 있음.
- 전체 시간의 약 **94%가 YOLO Full + Crop 추론 두 번**에서 발생함. tracking이나 TTC 코드를 먼저 손댈 이유는 없음.
- 목표까지 약 **5배** 격차가 있음. Crop 입력 해상도 축소(288×640)와 TensorRT 가속을 Q4에서 각각 측정해, 두 변경의 효과를 따로 확인해야 함.

**한 줄 정리** — Jetson이 느린 원인은 전적으로 YOLO 추론이며, 15 FPS를 만들려면 추론 연산량 축소와 TensorRT 가속을 함께 적용해야 함.
