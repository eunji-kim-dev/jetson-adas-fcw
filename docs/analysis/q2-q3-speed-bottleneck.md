## 0. 결론

**Q2 — 얼마나 빠른가**

- 출발점은 Jetson CPU에서 OpenCV DNN을 Release 빌드로 실행한 결과다. 프레임당 p50은 **235.1~238.2 ms (약 4.2 FPS)** 로, 목표 15 FPS(66.7 ms)의 3.5배였다.
- 현재 정식 값은 TensorRT FP16 + Crop 288 + GPU 전처리 + GPU 후처리의 **11.1~11.2 ms (63.2~63.5 FPS, 5회)** 다. 처리 시간은 목표의 0.17배다.
- 같은 밤에 같은 빌드로 연이어 측정한 결과, CPU 전처리 22.2~22.3 ms → GPU 전처리 16.7~16.8 ms → GPU 후처리 11.1~11.2 ms로 줄었다. CPU 전처리 경로의 거의 절반이다(−11.1 ms).
- Deadline Miss는 66.7 ms를 넘긴 프레임의 비율이며, 100%에서 0%로 줄었다.
- 같은 조건으로 5회 반복했을 때 변동은 0.2~1.8%였다. 결과 파일의 MD5도 매번 같아 수치와 결과가 재현됐다.

**Q3 — 어디서 느린가**

- 병목은 세 번 옮겨 갔다. 처음에는 **CPU의 YOLO 추론**, 다음은 **정밀도와 무관한 고정 비용인 전처리 blob·후처리**였고, 지금은 **다시 추론**이다.
- 현재 GPU 후처리 경로의 11.2 ms 중 추론은 7.7 ms(69%)다. 나머지는 전처리 1.2 ms와 추적·판정 등 CPU 작업 약 2.3 ms다.
- 카메라 입력의 Frame Age는 촬영부터 판정이 끝날 때까지 걸린 시간이다. **카메라 자체 지연 약 32 ms에 처리 시간을 더한 값**이며, 앞의 32 ms는 코드로 줄일 수 없다.
- 최종 설정의 카메라 처리 시간은 **9.5 ms**, Frame Age는 **41.7 ms**다. 10/10에 1회 측정했으며, 프레임 간격 33.3 ms 중 23.8 ms가 남는다.
- 처리 시간이 카메라 간격 33.3 ms보다 짧으면 동기 캡처로 충분하고 drop은 0이다. 캡처 스레드 분리는 처리가 느려질 때를 대비한 기능으로, 기본값은 꺼짐이다.

- 9/13에 측정한 333 ms는 빌드 설정이 비어 있어 최적화가 적용되지 않은 값이다. Release로 다시 측정하니 237 ms로, 1.4배 차이가 났다. 이후에는 harness가 빌드 종류를 먼저 검사한다.
- 9/29 이전의 Jetson 값(FP32 640 ~ FP16 288 26.1 ms)에는 화면에 초록 도로 영역을 그리는 시간 약 3.7 ms가 포함되어 있다. 9/29에 그리기를 제거했고, 같은 설정을 10/7 바이너리로 측정하면 22.2~22.3 ms다. 이전 값들은 서로의 상대 비교에만 사용한다(q4 문서).
- 마지막 세 줄은 같은 빌드로 같은 밤의 연속 세 세션(17:32~20:40)에서 측정했다. 실행 기록의 코드는 `71c8c9e`, harness HEAD는 `4d979f8`이다. `4d979f8`은 골든 CSV만 추가한 커밋이며 수정 파일은 없다. 15회 모두 골든 `4681f432`·배너 `e1a66eaf`로 같았다.
- 10/7 밤 5회 측정(`b75fc7c`)의 CPU 22.2~22.3·GPU 전처리 16.7~16.9 ms가 다시 재현됐다. 그 사이 추가된 카메라 v2·`rawconfirm`·`turn`·GPU 후처리 코드는 옵션을 끈 경로의 속도에 영향을 주지 않았다. 10/9에 1회 측정한 GPU 후처리 11.3 ms도 5회 측정값 11.1~11.2 ms와 0.1~0.2 ms 차이로 거의 같았다.
- x86 노트북과 Jetson CPU의 차이는 약 4%였다. OpenCV 버전과 빌드 조건이 달라 CPU 성능 비교로 해석하지는 않는다.
- 5회 반복 변동은 CPU 1.3%, TensorRT 0.2~0.6%였다. 결과 MD5는 모든 세션에서 5/5 같았으므로 반복 측정의 기준값으로 사용할 수 있다.
- Jetson CPU를 5회 측정하는 동안 최고 온도는 59.4 °C, 평균 전력은 약 11 W였으며 클럭 하락은 없었다.

**계획서 Q2에서 앞 표에 담지 못한 항목**

**전력·메모리 (10/9 밤 연속 세션 tegrastats, 5회 가운데값)**

| | CPU 전처리 | GPU 전처리 | GPU 전처리 + 후처리 |
| --- | ---: | ---: | ---: |
| 평균 전력 (VDD_IN, 보드 입력) | 10.2 W | 10.6 W | 11.4 W |

| RAM 보드 전체 최대 | 2168 MB | 2158 MB | 2155 MB |

- 영상 파일은 다음 프레임을 기다리지 않고 바로 처리한다. 처리 속도가 빨라질수록 GPU가 쉬는 시간이 줄어 전력(W)이 오른 것으로 보인다(+8%, GPU 사용률 33 → 43%). 같은 일을 더 짧게 끝내므로 **프레임당 에너지는 −20%**(226 → 180 mJ)였고, CPU 경로 대비로는 −35%였다.
- GPU 전처리의 10.6 W, 226 mJ는 10/8 Power Mode MAXN_SUPER 3회 측정값인 10.8 W, 231 mJ와 약 2% 차이로 일치했다.
- tegrastats의 RAM은 OS를 포함한 보드 전체 사용량이다. “증가”는 기록 중 최대 − 최소로 계산한 근사치다. 최소값은 프로그램이 막 시작한 시점 또는 그 직전의 값이다. 경로 간 차이인 5~20 MB는 회차 간 변동 범위인 15회 367~432 MB 안에 있으므로, **GPU 경로를 켜도 RAM 사용량은 늘어나지 않았다.** GPU 후처리가 추가로 사용하는 후보 기록 버퍼 약 0.35 MB는 MB 단위 기록에 드러나지 않는다.
- 보드 전체 사용량은 약 2.2 GB였다. 보드의 RAM 용량은 8 GB다.
- CPU 사용률은 세 경로 모두 16.2~17.0%(15회)로 같았다. 6코어 중 1코어(16.7%)가 꽉 찬 값으로 추정했다. 처리 스레드 하나가 GPU를 기다리는 동안에도 바쁘게 대기(spin)하며 계속 돌기 때문에, 파일 입력의 CPU%만으로는 작업량이 얼마나 줄었는지 알 수 없다.

## 3. Q3 — 어디서 느린가 (파일 입력)

### 3-1. 병목이 옮겨 간 순서

| 시점 | 설정 | 프레임 | 가장 오래 걸린 단계 | 추론 비중 | 이후 작업 |
| --- | --- | ---: | --- | ---: | --- |
| 9/13~14 | Jetson CPU OpenCV DNN | 237 ms | YOLO 추론 2회 (Full + Crop) | 약 94% (9/13 최적화 없는 빌드 기준) | TensorRT로 옮기고 Crop 크기를 줄였다 |
| 9/17 | TensorRT FP16, Crop 640 (첫 실행) | 41.2 ms | 추론 16.3 / 나머지 약 25 ms | 약 40% | Crop 288 |
| 9/27 | TensorRT FP16, Crop 288 | 26.1 ms | 고정 비용 약 17 ms (전처리 5.7·후처리 5.3·추적·판정 5.9) | 34% | 추적·판정 5.9 ms 중 판정이 4.62 ms였다. 대부분인 약 3.7 ms가 초록 영역 그리기였고, 9/29에 제거했다 |
| 10/7 | CPU 전처리 | 22.3 ms | 전처리 5.8 ms (그중 blob 4.5) + 후처리 5.2 ms | 40% | GPU 전처리 |
| 10/7 | GPU 전처리 | 16.7 ms | 후처리 5.0 ms | 47% | GPU 후처리 |
| **10/9** | **GPU 전처리 + 후처리** | **11.2 ms** | **추론 7.7 ms** | **69%** | — |

- 10/7·10/9 행의 수치는 10/9 밤 연속 세션 5회의 가운데값으로 바꿔 적었다. 날짜는 각 경로를 처음 사용한 날이다.
- 9/13의 추론 비중 94%는 최적화 없는 빌드에서 나온 값이다. 전체 333 ms 중 추론이 314 ms였다. Release의 단계별 값은 문서에 옮기지 않았다. 9/17 참고값인 추론 1회 약 100 ms로 보면, 2회 약 200 / 237 ms로 여전히 대부분을 차지했다.
- 9/17의 “위험 판정 5.5 ms”와 9/27의 “추적·판정 5.9 ms”에서 판정 시간이 컸던 이유는 판정 단계 안에서 초록 도로 영역을 그렸기 때문이다. 이때 세부 시간은 장면 감지 1.22 + 추적 0.07 + 판정 4.62였고, 그리기에 약 3.7 ms가 걸렸다. 그리기를 제거한 뒤 판정은 0.94 ms로 줄었다.

### 3-2. 최종 경로 단계별 시간 (Jetson FP16 288, input.mp4)

| 단계 (10/9 밤 연속 세션, 각 5회) | CPU 전처리 | GPU 전처리 | GPU 전처리 + 후처리 |
| --- | ---: | ---: | ---: |
| 프레임 p50 | 22.2~22.3 ms | 16.7~16.8 ms | **11.1~11.2 ms** |
| 검출 (전처리 + 추론 + 후처리) | 20.0~20.1 ms | 14.4~14.5 ms | 8.9 ms |
| 전처리 (Full + Crop) | 5.74~5.76 ms | 1.63~1.67 ms | 1.17~1.21 ms |
| └ CPU 세부: resize · pad · blob · pinned 복사 · Crop clone | 0.37 · 0.15 · **4.49** · 0.71 · 0.10 | — | — |
| Full 추론 / Crop 추론 | 5.8~5.9 / 3.0~3.1 ms | 5.3~5.4 / 2.5 ms | 5.2 / 2.5 ms (GPU 후처리 커널 + 내려받기 0.08~0.10 ms 포함) |
| 후처리 (Full + Crop) | 5.19~5.25 ms | 4.99~5.10 ms | **0.04~0.05 ms** |
| 추적·판정 등 (전체 − 검출) | 약 2.3 ms (장면 감지 1.22 · 추적 0.07 · 판정 0.94) | 약 2.2 ms | 약 2.3 ms |
| 결과 MD5 | `4681f432` 5/5 | `4681f432` 5/5 | `4681f432` 5/5 |

- GPU 경로의 “추론” 시간에는 CPU↔GPU 복사와 GPU 후처리 커널이 함께 포함되어 있다.
- 단계별로 줄어든 시간을 그대로 더하면 안 되는 경우가 두 군데 있다. GPU 전처리를 적용했을 때 Full·Crop 추론이 각각 0.5 ms 줄었다. GPU 후처리를 적용했을 때는 수정하지 않은 전처리가 1.65 → 1.19 ms로 줄었다. 이는 5회 측정값이며, 10/9에 1회 측정한 1.67 → 1.20과도 같다. 업로드가 없는 카메라 v2에서도 1.16 → 0.72 ms로 비슷하게 줄었으므로 업로드만으로는 설명되지 않는다. 다만 카메라의 두 값은 날짜·빌드·규칙 수가 다른 1회씩의 측정이다. GPU를 쉬지 않고 이어서 사용하면서 커널 시작·대기 비용이 다른 측정 구간으로 옮겨 간 것으로 추정하지만, 확인하지는 못했다. 따라서 최적화 효과는 프레임 전체 p50의 차이인 −5.6 ms, −5.5 ms로 기록한다.

### 3-3. 각 단계가 느렸던 이유

| 단계 | 원인 | 적용한 변경 |
| --- | --- | --- |
| CPU 추론 (Full 162 · Crop 152 ms, 9/13) | Crop 영역이 작아도 640×640에 회색 여백을 채워 넣어 연산량이 Full과 같았다 | TensorRT, Crop 288×640 (q4) |
| blob 4.5 ms | `blobFromImage`에서 0~255 정수 → 0~1 실수 변환, 색 순서 변경, 픽셀 배치 변경(HWC → CHW)을 수행한다. 이때 Full 4.92 + Crop 2.21 = 7.13 MB를 새로 쓴다 | GPU 전처리 커널 (q6) |
| 후처리 5 ms | 후보 8400 + 3780개마다 클래스 점수 80개 중 최댓값을 찾는다. 출력이 (채널, 후보) 순서라 후보 하나의 점수 80개가 메모리에서 8400칸씩 떨어져 있어 캐시를 잘 활용하지 못하는 것으로 추정했다. 이는 구조를 보고 판단한 이유이며, 시간을 따로 나눠 측정하지는 않았다. 책 80권에서 같은 쪽만 골라 읽느라 매번 책을 바꿔 드는 것과 같다 | 후보 하나에 GPU 스레드 하나를 배정한 커널로 0.08~0.10 ms까지 줄였다. 내려받기를 포함한 시간이다. 좌표 복원·NMS는 0.04~0.05 ms이므로 CPU에서 처리한다 (q6) |
| "추적·판정 5.9 ms" (9/27) | 판정 4.62 ms 중 약 3.7 ms는 측정 구간 안에서 초록 도로 영역을 그리는 데 쓰였다 | 9/29 제거 |

### 3-4. 다음 후보

- 추론 7.7 ms(69%): 정밀도(INT8)나 모델 크기를 조정하는 방법이 후보이다. INT8의 추론 이득 약 2 ms는 이제 프레임의 약 18%에 해당하지만, 정확도 근거가 없어 보류하고 있다(q5).
- 장면 감지 1.2 ms (CPU): 남아 있는 CPU 작업 중 가장 오래 걸린다. 아직 검토하지 않았다.
- 프레임 업로드: pinned 메모리 등록으로 720p 0.30 → 0.12 ms (q6, 후속).

## 4. Q3 — 카메라 입력

### 4-1. 카메라와 측정 항목

- 카메라는 삼성 SPC-A1200MB이며, YUYV 640×480 30fps에 V4L2 MMAP 버퍼 4장을 사용한다. YUYV만 지원하므로 압축 해제(decode) 단계는 없다.
- 자동 노출을 켜면 약 25 fps로 떨어진다. 카메라를 열 때마다 수동으로 바꾸고 설정값을 다시 읽어 확인했다.
- 측정 전에 `camera_probe`로 프레임 간격 p50이 32~33 ms인지 확인했다. 9/27에 한때 25 fps로 동작한 원인은 찾지 못했다.
- 준비 구간 40프레임을 제외하고 900프레임을 측정했다. 촬영 시각은 CLOCK_MONOTONIC을 기준으로 한다.
- **Frame Age**는 카메라가 촬영한 시각부터 해당 프레임의 판정이 끝난 시각까지다.
- **카메라 자체 지연**은 노출 시작부터 프로그램에 프레임이 전달될 때까지로, 약 32.6 ms다. 코드를 아무리 빠르게 해도 이 앞부분은 줄일 수 없다.
- drop은 카메라 쪽과 프로그램 쪽으로 나눠 센다. 카메라 쪽은 버퍼 4장이 차서 드라이버가 버린 프레임이고, 프로그램 쪽은 캡처 스레드를 분리했을 때 오래되어 버린 프레임이다.
- 색 변환(YUYV → BGR)은 캡처 단계 안에서 수행하며, 시간을 따로 나눠 측정하지는 않았다.

### 4-2. 동기 캡처 vs 캡처 스레드 분리 (9/29, 클럭 고정, 옛 바이너리·규칙 없음)

| | FP32 640 동기 | FP32 640 분리 | FP16 288 동기 | FP16 288 분리 |
| --- | ---: | ---: | ---: | ---: |
| 처리 p50 / p95 | 35.5 / 36.0 ms | 35.5 / 35.7 ms | 22.9 / 23.1 ms | 22.7 / 22.8 ms |
| Frame Age p50 / p95 / max | **163 / 178 / 181 ms** | **84 / 99 / 104 ms** | 55.1 / 55.3 / 55.6 ms | 54.9 / 55.1 / 55.4 ms |
| drop 카메라 / 프로그램 | **72 / 0** | **0 / 64** | 0 / 0 | 0 / 0 |
| 33.3 ms 마감 초과 | 100% | 100% | 0% | 0% |

- 처리 시간 35.5 ms가 카메라 간격 33.3 ms보다 길면, 동기 방식에서는 버퍼 4장에 프레임이 쌓인다. 한참 전의 장면을 처리하게 되어 Frame Age가 163 ms까지 늘었다.
- 캡처 스레드를 분리하면 항상 가장 최근 프레임을 가져오므로 Frame Age가 84 ms로 줄었다. 대신 처리하지 못한 프레임 64장을 프로그램이 버렸다.
- 편지에 비유하면, 동기는 밀린 편지를 도착 순서대로 모두 읽는 방식이다. 스레드 분리는 쌓인 편지를 버리고 맨 위의 편지만 읽는 방식이다. 버리는 양은 비슷하며 누가 버리는지가 다르다.
- 처리 시간 22.9 ms가 카메라 간격보다 짧으면 두 방식의 차이가 없다. Frame Age 55 ms는 카메라 33 + 처리 23으로 구성된다.
- 9/27 첫 측정의 처리 31.5 ms, Frame Age 64.0 ms는 클럭을 고정하지 않은 값이므로 사용하지 않는다.

**결론 (10/1 마감)**: 최종 설정은 처리 시간이 카메라 간격보다 짧으므로 **동기 캡처를 사용하고, 캡처 스레드 분리는 기본으로 꺼 둔다.** 스레드 분리는 처리가 느려질 때를 대비해 남겼다.

### 4-3. 최종 설정의 카메라 값 (동기, 900프레임, 각 1회)

| | CPU 전처리 (10/8) | GPU 전처리 v1 (10/8) | GPU 전처리 v2 (10/8) | **v2 + GPU 후처리 (최종, 10/10)** |
| --- | ---: | ---: | ---: | ---: |
| 바이너리 · 규칙 | `7fa2586` · 11규칙 | 같음 | 같음 | `71c8c9e` · 12규칙 |
| 처리 p50 / p95 | 21.0 / 21.1 ms | 15.1 / 15.1 ms | 14.9 / 15.0 ms | **9.5 / 9.6 ms** |
| Frame Age p50 / p95 / max | 53.2 / 53.3 / 53.5 ms | 47.3 / 47.3 / 47.5 ms | 47.1 / 47.2 / 47.6 ms | **41.7 / 41.8 / 42.2 ms** |
| Frame Age − 처리 | 32.2 ms | 32.2 ms | 32.2 ms | 32.2 ms |
| 33.3 ms 중 남는 시간 | 12.3 ms | 18.2 ms | 18.4 ms | **23.8 ms** |
| 전처리 / 후처리 (CPU 쪽) | 6.01 / 4.88 ms | 1.35 / 4.76 ms | 1.16 / 4.78 ms | 0.72 / 0.02 ms (+ GPU 0.09) |
| FPS / drop / 마감 초과 | 29.93 / 0 / 0% | 같음 | 같음 | 같음 |

- “Frame Age − 처리”는 네 경우 모두 32.2 ms로 같았다. 프레임이 밀리지 않았고, 남은 지연은 전부 카메라 자체에서 발생했다.
- 카메라의 상한은 30fps이므로 GPU 전처리의 효과는 FPS 대신 지연과 여유 시간에 나타난다. Frame Age 변화는 −6.1 ms였고, 남는 시간은 12.3 → 18.4 ms로 늘었다.
- 9/29 값인 22.9 / 55.1과는 바이너리·규칙이 달라 직접 비교하지 않는다. 10/8의 CPU 경로를 새 카메라 기준값으로 사용한다.
- Power Mode 3개(15W·25W·MAXN_SUPER) 모두 처리 p95 < 33.3 ms, drop 0이었다. 따라서 동기 캡처를 사용한다는 결론은 그대로다(q6 6절).
- 최종 설정(10/10)은 10/8 v2보다 처리 시간과 Frame Age가 각각 5.4 ms 줄었다. 주된 차이는 GPU 후처리이며, 규칙 수도 11 → 12로 바뀌고 빌드도 달라졌다. Frame Age − 처리는 32.2 ms 그대로였으므로 지연이 줄어든 부분은 전부 처리 시간이다.
- 10/8 카메라 CPU 경로 대비 처리 시간은 −11.5 ms(−55%), Frame Age는 −11.5 ms(−22%)였다. 남는 시간은 12.3 → 23.8 ms로 약 2배가 됐다. 프레임 간격의 71%가 남으므로 처리가 지금보다 약 3.5배 느려져도 프레임을 놓치지 않는다.
- 측정 전 `camera_probe`의 간격 p50은 32.0 ms, Frame Age 하한은 32.2 ms였다. 측정 중 CPU 클럭은 1728 MHz로 고정됐으며 최고 온도는 54.1 °C였다.
- 전력은 10/8 v2의 Power Mode 측정 당시 8.9 W에서 8.7 W로, −2%에 그쳤다. 카메라는 30fps로 처리량이 정해져 있고 보드 기본 전력이 대부분이어서, 프레임당 에너지가 −20%였던 파일 입력과 달리 전력 이득이 거의 없는 것으로 추정한다.
- RAM은 보드 전체 최대 2107 MB, 증가량은 +373 MB였다. 증가량은 최대 − 최소로 계산한 근사치다. 파일 입력의 2155 MB, +411 MB와 비슷한 수준이었다. 카메라는 tegrastats를 프로그램보다 2초 먼저 켰으므로 최소값은 프로그램 시작 전의 값이다.

## 5. 한계

- 카메라 측정은 조합마다 1회다. 입력 크기가 640×480으로 파일의 1280×720 및 실제 ADAS 카메라와 다르므로, 카메라 처리 시간과 파일 처리 시간을 직접 비교하지 않는다.
- drop이 0이므로 촬영 시각의 차이를 반영해 추적·TTC를 실제 시각 간격으로 계산하지는 않았다. 처리 시간이 33 ms를 넘는 TOPST 등의 장비에서 다시 검토한다.
- RAM은 tegrastats의 보드 전체 값에서 최대 − 최소로 계산한 근사치다. 프로세스 단독 사용량은 측정하지 않았다. 파일 입력의 CPU 사용률은 작업량을 보여 주지 못한다(2절).
- 최종 설정의 카메라 측정은 1회이며, 10/8의 세 경로와 바이너리·규칙 수가 다르다.
- GPU 경로의 단계별 시간에는 시작 비용이 측정 구간 사이를 옮겨 다니는 효과가 섞여 있다(3-2).
- 1080p 파일은 1회만 측정했다. CPU 23.8 → GPU 전처리 17.6 ms였으며, GPU 후처리는 측정하지 않았다. 720p는 Full이 정확히 2배 축소되는 빠른 경로이고 Crop은 복사이므로, 전처리가 1080p보다 1.2 ms 짧다.

## 6. 확인한 것

- 출발점은 237 ms(4.2 FPS)였고, GPU 전처리를 적용해 16.7 ms(46.8 FPS), GPU 후처리까지 적용해 11.2 ms(63.4 FPS)가 됐다. 세 경로를 같은 밤에 같은 빌드로 연이어 5회씩 측정했다. 15 FPS 목표는 TensorRT FP32에서 이미 넘었다.
- 같은 조건에서는 5회 측정 수치와 결과 MD5가 재현됐다. 빌드 종류, 클럭, 그리기 코드가 수치를 크게 바꾼다는 점도 확인했다. 빌드 변경으로 333 → 237 ms, 카메라 클럭 고정 전후로 64 → 55 ms가 됐고, 초록 영역을 그리는 데 3.7 ms가 들었다.
- 병목은 “YOLO 2회”에서 “고정 비용”으로, 다시 “추론”으로 옮겨 갔다. 현재 추론을 제외한 시간은 전처리 1.2 + 추적·판정 등 2.3을 합친 약 3.5 ms다.
- GPU 경로를 켜도 RAM 사용량은 늘어나지 않았고, 보드 전체 사용량은 약 2.2 GB였다. 파일 기준 프레임당 에너지는 276 → 180 mJ로 줄었다.
- 카메라 경로의 지연은 카메라 자체 32 ms에 처리 시간을 더한 값이다. 처리가 프레임 간격보다 빠른 한 동기 캡처로 충분하다. 최종 설정의 처리 시간은 9.5 ms, Frame Age는 41.7 ms다.

Jetson CPU의 237 ms에서 시작해 GPU 전처리 16.7 ms, GPU 후처리 11.2 ms까지 줄였다. 각 5회 측정한 결과다. 병목은 YOLO 추론 → 전처리·후처리 → 다시 추론으로 옮겨 갔다. 카메라 입력의 지연은 카메라 자체 32 ms에 처리 시간을 더한 값이며, 최종 설정에서는 41.7 ms였다.
