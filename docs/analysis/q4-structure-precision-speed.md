# Q4 — 무엇을 바꾸면 빨라지는가 (HW 가속·구조·정밀도)

작성일: 2026-10-09 (10/10 수정: GPU 전처리·후처리 수치를 10/9 밤 연속 세션 5회 측정값으로 갱신) | 작성자: 김은지

관련 질문: Q4 — 구조별·정밀도별 P50/P95/FPS를 비교한다. 같은 입력·같은 코드로 Jetson CPU와 TensorRT FP32/FP16/INT8을 측정하고, 구조 변경과 HW 가속·정밀도 변경의 효과를 구분했다.

관련 문서: q2-q3-speed-bottleneck.md (기준값·병목), q5-precision-accuracy.md (같은 변경의 정확도), q6-embedded-configuration.md (Memory Path·최종 선택)

## 0. 결론

Jetson Orin Nano Super에서 `input.mp4`를 사용해 한 번에 하나씩 설정을 바꿨다. 아래는 harness로 5회 측정한 p50을 변경 순서대로 정리한 표다.

| 순서 | 바꾼 것 | 종류 | 프레임 p50 | 바로 앞 대비 | 채택 |
| --- | --- | --- | ---: | ---: | --- |
| 0 | Jetson CPU, OpenCV DNN, Crop 640 (출발점) | — | 235.1~238.2 ms | — | — |
| 1 | TensorRT FP32 | HW 가속 | 38.7 ms | **−198 ms (약 6.1배 빠름)** | 중간 단계 |
| 2 | TensorRT FP16 | 정밀도 | 32.3 ms | −6.4 ms (−16.5%) | **채택** |
| 3 | Crop 입력 640×640 → 288×640 | 구조 | 26.1 ms | −6.6 ms (−20%, 같은 주 640 값 32.7 ms 대비) | **채택** |
| 4 | INT8 (Entropy calibration) | 정밀도 | 23.9 ms | −2.2 ms (−8%) | 탈락 (검출 손실, q5) |
| 4' | INT8 (MinMax calibration, 10/8 GPU 전처리 기준) | 정밀도 | 14.0 ms (FP16 16.7) | −2.7 ms (−16%) | 보류 (좌표 잡음 미검증, q5) |

가장 큰 효과는 TensorRT(GPU) 가속에서 나왔다. YOLO 추론 1회가 CPU 약 100 ms에서 TensorRT FP16 8.1 ms로 줄어 약 12배 빨라졌다.

Crop 288 구조 변경은 처리 시간을 −20% 줄여, FP32 → FP16 변경(−16.5%)보다 효과가 컸다. Crop 입력을 줄이면서 추론뿐 아니라 전처리·후처리 시간도 함께 줄었기 때문이다.

INT8의 효과는 −8%에 그쳤다. FP16에서 추론은 이미 프레임 처리 시간의 34%뿐이었고, 정밀도와 관계없는 고정 비용 약 17 ms가 남아 있었다. 그래서 다음에는 고정 비용을 줄이는 Memory Path를 살펴봤다. 이후 GPU 전처리로 −25%, GPU 후처리로 −33%를 줄였다(q6).

## 1. 비교 원칙

한 번에 하나의 조건만 바꿨다. 두 조건을 함께 바꾸면 무엇 때문에 달라졌는지 구분하기 어렵기 때문이다. 입력은 `input.mp4` 1252프레임으로 통일했고, harness 조건도 Release 빌드·클럭 고정·영상 저장 끔·5회 측정으로 맞췄다.

정밀도 변경의 효과는 TensorRT FP32를 기준으로 비교했다. OpenCV DNN과 TensorRT는 같은 FP32라도 계산 커널이 달라 결과에 차이가 생긴다(q5). 구조 변경은 같은 정밀도인 FP16에서 비교했다.

9/29 전 측정에는 판정 단계에서 초록 도로 영역을 그리는 시간 약 3.7 ms가 포함돼 있다. 따라서 이 문서의 9/14~9/27 값은 당시 값끼리의 상대 비교에만 사용한다. 현재 기준의 절대값은 FP16 288 CPU 경로 22.2~22.3 ms(10/7)다.

## 2. HW 가속 — CPU → TensorRT

| (Jetson, Crop 640) | CPU OpenCV DNN | TensorRT FP32 | TensorRT FP16 |
| --- | ---: | ---: | ---: |
| 프레임 p50 | 237 ms | 38.7 ms | 32.3 ms |
| 66.7 ms 대비 | 3.5배 초과 | 0.6배 | 0.5배 |
| Deadline Miss | 100% | 0% | 0% |
| 5회 변동 | 1.3% | 0.2% | 0.7% |
| 측정 | 9/14 | 9/18 | 9/17 |

9/17 첫 실행에서 얻은 50프레임 참고값은 추론 1회 약 100 ms → 8.1 ms(약 12배), 프레임 237 → 41.2 ms(약 5.8배)였다.

추론은 12배 빨라졌지만 프레임 전체는 6배 정도 빨라졌다. 전처리 9.0 · 후처리 8.1 · 판정 5.5 ms 등, 추론 밖에서 CPU가 처리하는 시간이 그대로 남았기 때문이다.

이 단계에서 이미 목표 15 FPS(66.7 ms)를 넘었다. 이후에는 지연을 더 줄이고 처리 여유를 확보하는 데 집중했다.

## 3. 구조 — Crop 입력 640×640 → 288×640 (9/25 확정)

### 변경 내용

프레임마다 YOLO를 2번 실행한다. 전체 화면(Full)을 한 번 보고, 먼 차를 확대해서 보는 영역(Crop)을 한 번 더 본다.

Crop 영역은 화면 가로 50% × 세로 36%다. 이 영역을 640×640 입력에 넣으면 위아래 회색 여백이 절반 넘게 차지한다. 288×640 모델에는 같은 그림을 같은 배율(0.667)로 넣고 여백만 제거했다. 따라서 검출기가 보는 차의 크기는 같다.

| 단계 (Jetson FP16, 5회 p50) | Crop 640 | Crop 288 | 변화 |
| --- | ---: | ---: | ---: |
| 프레임 p50 / p95 | 32.7 / 33.9 ms | 26.1 / 27.3 ms | **−20%** |
| FPS | 28.1 | 34.5 | +23% |
| Crop 추론 | 5.8~5.9 ms | 3.1 ms | −47% |
| Full 추론 | 5.8~5.9 ms | 5.8 ms | 같음 |
| 전처리 (Full + Crop) | 7.8 ms | 5.7 ms | −2.1 ms (blob 픽셀 45%) |
| 후처리 (Full + Crop) | 7.0 ms | 5.3 ms | −1.7 ms (후보 8400 → 3780개) |

| x86 센터 PC (i7-9700, OpenCV DNN, 5회) | Crop 640 | Crop 288 | 변화 |
| --- | ---: | ---: | ---: |
| 프레임 p50 (5회 중앙) | 102.6 ms | 75.4 ms | **−27%** |
| Crop 추론 | 44.0~44.5 ms | 20.9~21.1 ms | −52% |
| Full 추론 | 44.5~45.0 ms | 44.3~45.1 ms | 같음 |
| FPS | 9.3~9.5 | 12.5~13.0 | +37% |

9/24 Jetson 1회 측정에서 Crop 경로만 보면 전처리 3.75 → 1.98 · 추론 5.83 → 3.10 · 후처리 3.49 → 1.86 ms로 줄었다. 합계는 13.07 → 6.94 ms(−47%)다. 구조 변경의 효과가 Crop 경로 전체에서 나타났다.

정확도 결과는 q5에 정리했다. 288에서 사라진 박스는 주로 높이 20px 이하인, 신뢰도가 낮은 먼 물체였다. 경고에 사용하는 최소 박스 높이 54px보다 훨씬 작았다. 평가셋 21개 중 20개는 첫 경고 프레임까지 같았고, 04만 달랐다(640 놓침 → 288 경고).

## 4. 정밀도 — FP32 / FP16 / INT8 (Crop 288 구조)

| (Jetson, 9/27 밤 5회 p50, 같은 세션) | FP32 | FP16 | INT8 (Entropy) |
| --- | ---: | ---: | ---: |
| 프레임 p50 / p95 | 31.1 / 32.4 ms | **26.1 / 27.3 ms** | 23.9 / 24.8 ms |
| FPS | 29.4 | 34.5 | 37.4 |
| Full 추론 (640×640) | 9.1 ms | 5.8 ms | 4.3 ms |
| Crop 추론 (288×640) | 5.0 ms | 3.1 ms | 2.5 ms |
| 전처리 (Full + Crop) | 5.7 ms | 5.7 ms | 5.8 ms |
| 후처리 (Full + Crop) | 5.3 ms | 5.3 ms | 5.4 ms |
| 추적·판정 (전체 − 검출) | 6.0 ms | 5.9 ms | 5.9 ms |
| GPU 추론 비중 | 45% | 34% | 28% |
| 결과 MD5 | `33cd6fbf` 5/5 | `4681f432` 5/5 | `8601b468` 5/5 |

FP32 → FP16은 −5.0 ms(−16%), FP16 → INT8은 −2.2 ms(−8%)였다.

정밀도를 바꿔도 줄어드는 것은 추론 시간뿐이다. 전처리·후처리·추적·판정에 쓰는 약 17 ms는 세 정밀도에서 같았다. 이 값에는 초록 영역을 그리는 3.7 ms도 포함돼 있다. 당시 구조에서는 INT8 추론을 더 빠르게 해도 약 17 ms가 남는다.

9/25에 적은 INT8 이득 3.6 ms(−13%)는 1회 평균값이었다. 5회 p50 기준 정식 값은 2.2 ms다.

### INT8 엔진 구성

calibration에는 평가셋과 영상 내용이 겹치지 않는 교통사고 영상 25개를 사용했다. 주간 18·야간 7·이륜차 포함 3개이며, 영상당 10프레임을 뽑아 Full용 250장과 Crop용 250장을 만들었다. AI Hub에는 파일 이름이 달라도 같은 촬영본이 있어, 이름 대신 영상 내용을 확인해 구분했다.

TensorRT는 층마다 정밀도를 선택한다. 288 모델은 약 66%, 640 모델은 약 65%가 INT8이다. 검출 헤드 끝의 마지막 Conv·DFL·좌표 계산·Sigmoid는 288 모델에서 FP32, 640 모델에서 FP16으로 남았다.

### MinMax 속도 (10/8, GPU 전처리, 규칙 없음, 각 3회 가운데)

| | FP16 | INT8 Entropy | INT8 MinMax |
| --- | ---: | ---: | ---: |
| 프레임 p50 / p95 | 16.7 / 17.9 ms | 13.6 / 14.8 ms (−19%) | 14.0 / 15.9 ms (−16%) |
| FPS | 46.6 | 54.5 | 53.2 |
| 추론 Full + Crop | 7.8 ms | 5.7 ms | 5.9 ms |
| GPU 전처리 | 1.66 ms | 0.81 ms | 0.83 ms |
| 후처리 | 5.05 ms | 4.99 ms | 5.04 ms |

같은 정밀도로 3회 측정한 값의 차이는 0.1 ms 안이었다. 추론에서 줄어든 약 2 ms는 9/27의 8.9 → 6.8 ms와 비슷했다.

감소율이 9/27의 −8%에서 −16~19%로 커진 이유는 FP16 처리 시간이 16.7 ms까지 줄어, 같은 2 ms가 차지하는 비중이 커졌기 때문이다. GPU 전처리 시간도 −0.85 ms 줄었지만, 전처리는 정밀도와 무관한 계산이어서 원인을 확인하지 못했다. 따라서 이 차이를 단계별 원인으로 나눠 설명하지는 않았다.

Entropy가 MinMax보다 조금 빠른 이유는 박스를 25% 덜 검출하기 때문일 수 있다. 이 부분은 추정이다.

최종 선택은 FP16 유지다. MinMax가 더 빠르지만, 정확도를 확인할 근거가 아직 없다(q5 4절).

## 5. 효과 정리

| 바꾼 것 | 종류 | 줄어든 시간 | 결과 변화 (q5) | 결정 |
| --- | --- | --- | --- | --- |
| TensorRT | HW 가속 | 237 → 38.7 ms (약 6배) | 박스 소수점은 달라졌지만 input.mp4 한 편에서 경고 판정은 같았다. | 채택 |
| FP16 | 정밀도 | −16.5% (640) | FP32와 21개 영상의 판정·첫 경고가 같았다. | **채택** |
| Crop 288×640 | 구조 | −20% (x86 −27%) | 작고 먼 박스 일부가 빠졌다. 21개 중 20개는 첫 경고가 같았다(04만 다름). | **채택** |
| INT8 Entropy | 정밀도 | −8% | FP32가 확실히 검출한 박스의 25.2%를 놓쳤다. | 탈락 |
| INT8 MinMax | 정밀도 | −16% (10/8 기준) | 놓침 2.4%, 박스 높이가 2px 넘게 다른 짝 29%. FCW 영향은 검증하지 않았다. | 보류 (TOPST에서 재검증) |
| 초록 도로 영역 그리기 제거 (9/29) | 측정 구간 정리 | 약 −3.7 ms | 없음 (표시만 변경) | — |
| GPU 전처리 | Memory Path (q6) | −25% (22.3 → 16.7 ms) | 비트 단위로 같음 | **채택** |
| GPU 후처리 | Memory Path (q6) | −33% (16.7 → 11.2 ms) | 비트 단위로 같음 | **채택** |

마지막 두 줄은 10/9 밤 연속 세션에서 5회 측정한 가운데값이다(q2-q3 2절).

구조·HW 가속·정밀도를 선택한 뒤에도 프레임 처리 시간의 2/3는 정밀도와 관계없는 CPU 작업이었다. 이 가운데 전처리와 후처리를 GPU로 옮기자 결과를 바꾸지 않으면서도 INT8보다 시간을 더 많이 줄일 수 있었다.

## 6. 한계

- 정밀도 표(9/27)와 구조 표(9/24~27)는 초록 영역을 그리는 3.7 ms가 포함된 과거 측정값이다. 당시 값끼리의 상대 비교에만 사용한다.
- FP16 640은 9/17 harness에서 32.3 ms, 9/24 harness에서 32.6~32.8 ms로 세션마다 조금 달랐다. 단계별 비교에는 같은 주에 측정한 값을 사용했다.
- INT8 헤드 FP32 보호 엔진(`fp32head` 계열)의 속도는 측정하지 않았다.
- 1080p 입력에서는 정밀도·구조를 비교하지 않았다. GPU 전처리만 1회 비교했다.
- INT8 엔진에서 GPU 전처리 시간이 줄어든 원인(−0.85 ms)은 확인하지 못했다.

## 7. 확인한 것

가장 큰 효과는 HW 가속(TensorRT)에서 나왔다. 약 6배 빨라졌고, 이 단계에서 목표 15 FPS를 넘었다.

Crop 288은 같은 그림을 여백 없이 넣는 구조 변경이다. 21개 중 20개의 경고 결과를 유지하면서 −20%를 줄여, FP16 정밀도 변경보다 효과가 컸다.

이후 FP16보다 정밀도를 더 낮췄을 때의 이득은 고정 비용에 막혔다. 이것이 GPU 전처리·후처리로 방향을 바꾼 근거다. CPU 237 ms에서 TensorRT로 38.7 ms, FP16으로 32.3 ms, Crop 288로 26.1 ms까지 줄였지만, INT8은 추론 밖 고정 비용 17 ms 때문에 −8%에 그쳤다. INT8을 보류하고 고정 비용을 줄이는 작업(q6)으로 넘어갔다.
