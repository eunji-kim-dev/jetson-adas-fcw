>

>
> ⑤ "평가셋 40개"는 21개 → 본 세트 16 + 이륜차 5 + 음성 10 + 홀드아웃 10으로 바뀌었다.

## 0. 결론

같은 영상과 ONNX 모델을 OpenCV DNN / TensorRT FP32 / TensorRT FP16으로 각각 실행했다. 각 방식이 남긴 FCW 결과 CSV를 항목별로 비교했다.

* FCW 판정(`riskLevel`)은 1252프레임 모두 세 방식에서 같았다. SAFE·DANGER로 판단한 결과가 전부 일치했다.
* 검출한 차량 박스의 개수는 FP32→FP16에서 21프레임(1.7%), OpenCV→FP32에서 4프레임(0.3%) 달라졌다.
* 충돌까지 남은 예상 시간인 TTC는 FP32와 FP16이 116프레임에서 달랐다. TTC가 2초 이내인 구간에서는 차이가 0.01~0.05초(1~3%)로 작았고, 시간이 많이 남은 구간에서는 8~18초까지 벌어졌다.
* 먼 차량은 화면 속 박스 높이가 1픽셀만 달라져도 TTC 계산값이 크게 바뀐다. Q1에서 확인한 현상이 이번에도 나타났다. 다만 값이 크게 달라진 프레임도 양쪽 모두 SAFE였다.

이 영상에서는 FP16으로 바꿔도 최종 경고 판정이 달라지지 않았다. 경고가 나오는 구간이 한 곳뿐이므로 평가셋에서도 같은 결과가 나오는지 확인해야 한다.

INT8은 아직 비교하지 않았다. INT8 계산에 필요한 보정 기능(calibrator)을 구현한 뒤 같은 방법으로 비교할 예정이다.

## 1. 실행 조건

| 항목         | 값                                                            |
| ---------- | ------------------------------------------------------------ |
| 측정일        | FP16 2026-09-17, FP32 2026-09-18                             |
| 장비         | Jetson Orin Nano Super, JetPack 7, CUDA 13.2, TensorRT 10.16 |
| 빌드         | Release, `-DENABLE_TENSORRT=ON`                              |
| 입력 영상 / 모델 | `input.mp4` 1252프레임 / `yolov8n.onnx` — 세 방식 모두 동일            |
| 실행 조건      | 클럭 고정, 영상 저장 끄기(`--clocks on --video off`), 각각 5회 반복         |
| TTC 계산     | 기존 TTC-P — 차량 박스 높이의 변화를 이용한다. 호모그래피 적용 전                     |

각 방식 안에서는 5번 모두 같은 결과가 나왔다. 결과 파일의 MD5를 비교했으며, 5회 전부 일치했다.

| 실행 방식         | MD5         | 뒤쪽 20% 구간의 처리 시간 중앙값(p50) |
| ------------- | ----------- | ------------------------: |
| OpenCV DNN    | `8afab132…` |                     237ms |
| TensorRT FP32 | `f3c3eaa6…` |                    38.7ms |
| TensorRT FP16 | `e3f69892…` |                    32.3ms |

같은 방식으로 다시 실행한 결과는 같았지만, 세 방식끼리 비교하면 MD5가 달랐다. 어떤 항목에서 차이가 났는지 CSV 내용을 확인했다.

## 2. 비교 방법

세 방식의 기준 결과 파일(golden CSV)을 프레임별로 나란히 놓고, 항목마다 값이 다른 프레임 수를 셌다. MD5로는 파일이 같은지 다른지만 알 수 있다. 실제 경고가 달라졌는지는 CSV 내용을 직접 비교해야 한다.

다음 세 조합을 비교했다.

* OpenCV → FP32: 같은 FP32 설정에서 추론 엔진을 바꿨을 때의 차이.
* FP32 → FP16: 같은 TensorRT에서 정밀도 설정을 바꿨을 때의 차이.
* OpenCV → FP16: 추론 엔진과 정밀도 설정을 함께 바꿨을 때의 차이.

FP16 설정이 미친 영향은 FP32→FP16 비교에서 확인해야 한다. OpenCV→FP16에는 엔진을 바꾼 영향도 섞여 있으므로, 여기서 생긴 차이를 모두 FP16 때문이라고 볼 수는 없다.

## 3. 무엇이 달랐는가

아래 숫자는 전체 1252프레임 중 해당 항목의 값이 달랐던 프레임 수다. 오검출이나 오판정의 횟수는 아니다.

| --------------- | ----------: | --------: | ----------: | ----------------- |
| `detections`    |        1055 |      1091 |        1087 | 검출 박스 정보와 점수      |
| `numDetections` |       **4** |    **21** |          17 | 검출 박스 개수          |
| `numTracks`     |           4 |        24 |          24 | 추적 중인 차량 수        |

| `activeLeadId`  |          19 |     **0** |          19 | 선행차로 선택한 차량의 ID   |

총 1252프레임을 비교했으며, 표에 없는 항목에서는 차이가 없었다.

## 4. 각 차이가 무슨 뜻인가

차량 검출 → 차량 추적 → 선행차 선택 → TTC 계산 → 경고 판정 순서로 처리한다. 이번 비교에서는 앞단의 검출·추적 결과가 달랐지만, 그 차이가 최종 경고 판정까지 바꾸지는 않았다.

**검출 박스 정보는 약 84~87%에서 달랐다.** 검출 점수를 소수 넷째 자리까지 기록하므로 `0.9123`과 `0.9124`처럼 작은 차이도 집계된다. 이 비율이 높다고 차량 검출이 대부분 달라졌다는 뜻은 아니다. 이런 작은 차이로도 결과 파일의 MD5가 달라진다.

**검출 박스 개수는 0.3% / 1.7%에서 달랐다.** OpenCV→FP32에서는 4프레임, FP32→FP16에서는 21프레임에서 개수가 달랐다. 검출 기준인 점수 0.25 근처의 박스가 포함되거나 제외된 것으로 추정한다. FP16 설정을 바꾼 쪽에서 개수 차이가 약 5배 자주 나타났지만, 둘 다 전체 프레임의 2% 미만이었다.

**선행차 ID는 FP32와 FP16에서 모두 같았다.** OpenCV와 TensorRT는 19프레임에서 달랐다. 추적기가 차량에 번호를 붙이는 순서에 따라 같은 차량에도 다른 ID가 붙을 수 있다. 실제로 다른 차량을 골랐는지, 번호만 달라졌는지는 아직 확인하지 않았다.

**TTC는 약 5~9%에서 달랐다.** 차량 박스 높이가 조금 달라지면서 TTC 계산값도 바뀌었다. 이번에는 이 차이가 최종 경고 판정으로 이어지지는 않았다. 구체적인 차이는 5절에 정리했다.

**최종 판정에는 차이가 없었다.** 중간 계산값은 달랐지만, 모든 프레임에서 SAFE·DANGER 판정이 같았다.

## 5. TTC 차이는 어디서 났는가

FP32와 FP16의 TTC가 달랐던 116프레임은 다음과 같이 나뉜다.

* 27프레임: 한쪽은 `inf`, 다른 쪽은 숫자였다.
* 89프레임: 양쪽 모두 숫자였지만 값이 달랐다.

**`inf`가 나온 경우**

박스가 커지는 움직임을 잡지 못하면 유한한 충돌 시간을 계산할 수 없어 `inf`가 나올 수 있다. 예를 들어 한쪽에서는 박스가 조금 커져 TTC 31초가 나오고, 다른 쪽에서는 크기 증가가 잡히지 않아 `inf`가 나온다. 두 값의 의미는 다르지만, 이번에는 최종 경고 판정이 같았다.

**양쪽 모두 숫자인 경우 — 차이가 큰 사례**

| 프레임 |   FP32 |   FP16 |     차이 | 공통 판정 |
| --- | -----: | -----: | -----: | ----- |
| 522 | 21.30초 | 39.84초 | 18.54초 | SAFE  |
| 317 | 21.49초 | 39.32초 | 17.83초 | SAFE  |
| 476 | 39.70초 | 23.82초 | 15.88초 | SAFE  |
| 84  | 16.28초 | 25.22초 |  8.94초 | SAFE  |

차이가 크게 벌어진 사례는 충돌까지 시간이 많이 남은 구간에 있었다. 계산값은 8~18초씩 달랐지만, 양쪽 모두 경고를 낼 정도로 TTC가 짧지는 않았다.

**양쪽 모두 숫자인 경우 — TTC가 짧은 사례**

| 프레임  |  FP32 |  FP16 |    차이 | 공통 판정  |
| ---- | ----: | ----: | ----: | ------ |
| 1057 | 1.36초 | 1.36초 | 0.01초 | DANGER |
| 1054 | 1.55초 | 1.52초 | 0.03초 | DANGER |
| 1053 | 1.61초 | 1.56초 | 0.04초 | DANGER |
| 1052 | 1.68초 | 1.65초 | 0.03초 | DANGER |
| 1051 | 1.90초 | 1.84초 | 0.05초 | SAFE   |
| 713  | 5.97초 | 5.71초 | 0.26초 | SAFE   |
| 715  | 5.94초 | 5.78초 | 0.16초 | SAFE   |

표의 값은 소수 둘째 자리로 반올림했다. 따라서 표시된 두 값을 직접 뺀 결과가 원래 값으로 계산한 차이와 다를 수 있다.

TTC 2초 이내에서는 차이가 약 0.01~0.05초(1~3%)였다. 6초 근처에서는 약 0.16~0.26초(3~4%)로 더 커졌다. 이 비율은 FP32와 FP16의 계산값이 서로 얼마나 다른지를 나타낸다. 실제 충돌 시간과 비교한 오차는 아니다.

## 6. 왜 가까운 차량에서는 차이가 작았는가

TTC-P는 차량 박스 높이가 커지는 속도로 충돌까지 남은 시간을 계산한다. 멀리 있는 차량은 박스가 작고 크기 변화도 적다. 그래서 높이 1픽셀 차이도 계산에 큰 영향을 준다.

예를 들어 같은 시간 동안 박스가 0.5픽셀 커졌다고 추정했는데 1픽셀 차이가 생기면, 오차가 원래 증가량보다 커진다. 박스가 20픽셀 커지는 상황이라면 1픽셀 차이는 증가량의 5%다. 같은 1픽셀 차이라도 박스가 빠르게 커질수록 계산에 미치는 영향은 작아진다.

| TTC 구간            |       FP32↔FP16 차이 | 이번 결과의 의미                |
| ----------------- | -----------------: | ------------------------ |
| 약 1.4~1.9초        | 약 0.01~0.05초(1~3%) | 두 설정의 계산값이 가까웠다.          |
| 약 5.7~6.0초        | 약 0.16~0.26초(3~4%) | 차이가 조금 더 커졌다.               |
| 약 16~47초의 큰 차이 사례 |            약 8~18초 | 작은 박스 변화가 큰 TTC 차이로 이어졌다. |

이번 영상에서는 가까이 접근하는 차량의 TTC가 먼 차량보다 정밀도 변경에 덜 민감했다. Q1에서 다룬 TTC-P의 1픽셀 민감도가 차량의 거리와 접근 상태에 따라 다르게 나타났다.

## 7. Q1과 비교하면 무엇이 달라졌는가

Q1에서는 "FP16/INT8로 가면 박스 변화가 TTC에 더 크게 영향을 줄 수 있으니, 정밀도 실험 전에 TTC를 먼저 바꿔야 한다"고 봤다. 이번 비교에서도 중간 계산값은 달라졌지만, 최종 경고 판정은 유지됐다.

* 확인된 것: FP32와 FP16의 검출 박스 개수가 21프레임에서 달랐고, 시간이 많이 남은 구간에서는 TTC 차이가 8~18초까지 벌어졌다.
* 예상과 달랐던 것: 이 차이가 최종 경고 판정을 바꾸지는 않았다. TTC 2초 이내 구간에서는 두 설정의 차이가 약 1~3%였다.

따라서 호모그래피를 병행하려는 목적도 구분해서 볼 필요가 있다.

| 목적                            | 이번 결과로 본 판단              |
| ----------------------------- | ------------------------ |
| FP16을 적용해도 기존 경고 판정을 유지하기     | 이 영상에서는 기존 TTC-P로도 유지됐다.  |
| 더 먼 거리부터 접근 상태를 파악하고 경고를 앞당기기 | 호모그래피를 병행했을 때의 효과를 추가로 확인해야 한다. |

현재 설계는 박스 높이 36픽셀 조건을 두어 작은 박스를 경고 대상에서 제외한다. 이 때문에 먼 차량의 TTC가 흔들려도 경고에는 반영되지 않을 수 있다. 호모그래피 병행은 경고를 더 일찍 내기 위한 방법으로 검토하고, 실제 개선 정도는 평가셋에서 확인한다.

## 8. 확인할 부분 — 프레임 1056

| 프레임  |  FP32 |  FP16 | 공통 판정    |
| ---- | ----: | ----: | -------- |
| 1054 | 1.55초 | 1.52초 | DANGER   |
| 1056 | 1.54초 | 1.53초 | **SAFE** |
| 1057 | 1.36초 | 1.36초 | DANGER   |

1056프레임은 TTC가 약 1.5초인데도 SAFE다. 주변 프레임에서는 DANGER로 판정했으므로, 도중에 경고가 빠진 이유를 확인해야 한다. FP32와 FP16이 모두 SAFE였으니 FP16으로 바꿔서 생긴 차이는 아니다.

Q1에는 DANGER 기준을 2.5초로 적었다. 이 기준 하나로는 1051프레임과 1056프레임이 SAFE인 이유를 설명할 수 없다. 실제 기준값이 바뀌었거나, 박스 높이·선행차 상태·연속 프레임 조건 등이 함께 적용되는 것으로 보인다. 정확한 원인은 아직 확인하지 않았다.

`RiskAnalyzer`와 `WarningPolicy` 코드에서 실제 TTC 기준과 추가 조건을 확인한 뒤 이 문서에 기록해야 한다. 경고가 얼마나 자주 끊기는지, 그 끊김이 경고 누락으로 이어지는지는 평가셋에서도 확인한다.

## 9. 이번 결과로 아직 알 수 없는 것

* 다른 영상에서도 판정이 같은지: 이번 영상의 경고 구간은 1051~1057 근처 한 곳뿐이다. 경고 상황이 다양한 평가셋에서도 비교해야 한다.
* 실제 상황에 맞게 경고했는지: 세 방식의 판정이 같다는 점은 확인했다. 그 판정이 정답인지는 별도의 평가가 필요하다.
* TTC 방식을 바꿔도 결과가 같은지: 이번 결과는 기존 TTC-P를 기준으로 했다. 호모그래피를 적용하면 다시 비교해야 한다.
* INT8에서도 판정이 유지되는지: 아직 실험하지 않았다.
* 선행차 ID가 다른 19프레임에서 실제로 다른 차량을 골랐는지: 번호만 달라진 것인지는 아직 확인하지 않았다.
* Detection/Tracking 자체의 정확도: 이번에는 세 방식의 결과가 서로 같은지만 비교했다. 정답 라벨과의 비교는 AI Hub 융합센서 데이터로 11월에 진행한다.

## 10. Golden 기준 정리

Golden CSV는 다시 실행했을 때 결과가 바뀌었는지 확인하는 기준 파일이다. 같은 플랫폼과 설정에서는 MD5로 파일 전체의 일치 여부를 확인한다. 플랫폼이나 정밀도 설정이 다를 때는 경고 결과와 항목별 값을 비교한다.

| 플랫폼 / 실행 방식             | 기준 파일                                       | MD5         |
| ----------------------- | ------------------------------------------- | ----------- |
| x86_64 / OpenCV DNN     | `golden_baseline.csv`                       | `a0006c4a…` |
| aarch64 / OpenCV DNN    | `golden_baseline_aarch64.csv`               | `8afab132…` |
| aarch64 / TensorRT FP32 | `golden_baseline_aarch64_tensorrt_fp32.csv` | `f3c3eaa6…` |
| aarch64 / TensorRT FP16 | `golden_baseline_aarch64_tensorrt_fp16.csv` | `e3f69892…` |

자동 실행 스크립트는 `uname -m`으로 플랫폼을 확인하고 `--backend`로 실행 방식을 확인해 알맞은 기준 파일을 고른다. 이번 Jetson 실험에서는 세 방식 각각 5회 모두 MD5가 일치했다. 방식 간 차이는 MD5의 일치 여부로 판단하지 않고, 이 문서처럼 CSV 내용을 비교해 확인한다.

## 11. 확인한 것

* 같은 FP32여도 OpenCV와 TensorRT의 결과는 달랐다. 엔진의 계산 방식이 다르므로 FP16 설정의 영향을 볼 때는 TensorRT FP32를 기준으로 비교해야 한다.
* 검출 박스 개수가 다른 프레임은 OpenCV→FP32에서 4개, FP32→FP16에서 21개였다. FP16 설정을 바꾼 쪽에서 약 5배 자주 나타났지만, 둘 다 전체의 2% 미만이었다.
* TTC 차이가 크게 나타난 곳은 충돌까지 시간이 많이 남은 구간이었다. TTC 2초 이내에서는 차이가 약 1~3%였고, 최종 경고 판정은 모든 프레임에서 같았다.
* FP32→FP16의 처리 시간은 38.7→32.3ms로 약 16.5% 줄었고, 처리 속도는 약 1.2배가 됐다. FP16의 단계별 시간은 추론이 약 16ms, 나머지 CPU 처리가 약 22ms였다. CPU 처리 시간은 정밀도 설정과 무관하므로 추론만 빨라져서는 전체 시간이 크게 줄지 않는다. 다음에는 전처리·후처리와 CPU↔GPU 데이터 이동도 확인해야 한다. FP32의 단계별 시간은 아직 추출하지 않았다.

**다음 확인**

* `RiskAnalyzer` / `WarningPolicy`의 실제 경고 기준과 추가 조건을 확인해 1056프레임이 SAFE인 이유를 찾는다.
* 선행차 ID가 다른 19프레임에서 같은 차량에 번호만 다르게 붙은 것인지 확인한다.
* FP32의 단계별 처리 시간을 측정해 FP16과 나란히 비교한다.
* INT8 보정 기능(calibrator)을 구현한 뒤 같은 방법으로 FP32→INT8을 비교한다.
* 평가셋 40개에서 다시 비교해 경고 누락, 불필요한 경고, 충돌 전에 얼마나 일찍 경고했는지 확인한다.

FP16으로 바꾸면서 일부 검출 결과와 TTC는 달라졌다. 하지만 이 영상의 1252프레임에서는 세 방식의 최종 경고 판정이 모두 같았다.
