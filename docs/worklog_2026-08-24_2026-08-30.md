### 3. 프레임별 CSV 로그 추가 및 기준 결과 저장
**작업 내용**
- 영상마다 결과 파일이 따로 저장되도록 출력 파일명을 입력 영상 이름 기준으로 변경함
  - 영상 결과: `results/<영상이름>_output.avi`
  - CSV 결과: `results/<영상이름>_frames.csv`

- 각 프레임마다 다음 정보를 CSV에 기록하도록 추가함
    - 프레임 번호 (`frame`)
    - 장면 전환 여부 (`sceneChanged`)
    - YOLO가 검출한 객체 개수 (`numDetections`)
    - YOLO가 검출한 객체 정보 (`detections`)
    - 트래커가 추적 중인 객체 개수 (`numTracks`)
    - 트래커가 추적 중인 객체 정보 (`tracks`)
    - 현재 선행 차량 ID (`activeLeadId`)
    - 위험 단계 (`riskLevel`)
    - TTC (`ttc`)

**로그 형식**
#### `detections`

```text
2 : 400 : 250 : 80 : 60 : 0.9123
│    │     │     │    │      │
종류  x     y    너비  높이   신뢰도
```

- 종류(`classId`): YOLO가 판단한 객체 종류
- `x`, `y`: 객체를 둘러싼 박스의 왼쪽 위 좌표
- 너비, 높이: 객체 박스의 크기
- 신뢰도: YOLO가 해당 객체라고 판단한 확신 정도
  - 예: `0.9123` → 약 91.23%

현재 사용하는 COCO 기준 주요 `classId`:

| classId | 객체 |
| ---: | --- |
| `2` | car |
| `5` | bus |
| `6` | train |
| `7` | truck |

객체가 여러 개 검출되면 `;`로 구분함.

#### `tracks`

```text
51 : 2 : 400 : 250 : 80 : 60
│    │    │     │     │    │
ID  종류   x     y    너비  높이
```

- ID: 트래커가 객체에 부여한 고유 번호
- 종류: 객체의 `classId`
- `x`, `y`: 객체 박스의 왼쪽 위 좌표
- 너비, 높이: 객체 박스의 크기

객체가 여러 개 존재하면 `;`로 구분함.

> **Detection과 Track의 차이**
>
> `Detection`은 YOLO가 현재 프레임만 보고 새로 검출한 객체이고,  
> `Track`은 여러 프레임을 이어서 보면서 동일한 객체라고 판단해 계속 추적한 결과임.

**검증 결과**
- 같은 영상을 2회 실행한 결과 CSV 내용이 완전히 동일하게 나옴
- 현재 결과를 기준값으로 저장함
- 이후 코드 구조를 변경한 뒤 기준 CSV와 비교하여 결과가 달라졌는지 확인할 수 있게 됨

**알게 된 점**
- 탱크로리는 YOLO가 중간중간 `car`, `bus`, `truck`으로 다르게 인식했지만 같은 ID로 계속 추적됨
- 즉 YOLO가 차종을 일시적으로 다르게 판단하더라도 트래커가 바로 다른 차량으로 취급하지는 않음
- 현재 영상에서는 `CAUTION`이 한 번도 발생하지 않았고 `DANGER`는 2프레임에서만 발생함
- 따라서 다른 영상도 사용하여 위험 단계가 제대로 구분되는지 확인할 필요가 있음
- 전체 1252프레임 중 650프레임에서는 선행 차량이 선택되지 않았음
- 이후 자차선 영역(ROI)을 조정할 때 선행 차량 선택 범위도 함께 확인할 필요가 있음

### 4. 경고 판단 로직을 `adas`로 이동 (`WarningPolicy` 분리)
- `main.cpp`에 마지막으로 남아 있던 FCW 경고 관련 코드를 `adas/`로 이동
- 경고를 화면에 띄우는 조건을 `WarningPolicy` 클래스로 분리
  - CAUTION은 8프레임 연속 확인 후 표시
  - DANGER는 3프레임 연속 확인 후 표시
  - 한 번 표시된 경고는 0.25초 동안 유지
  - LEAD 차량이 바뀌면 이전 차량의 경고 카운트를 이어받지 않음
- 차량 위치와 추월 여부를 보고 경고를 제한하는 조건도 `WarningPolicy`로 이동
- 장면이 바뀔 때 여러 경고 상태를 각각 초기화하던 코드를 `warningPolicy.reset()`으로 정리
- `main.cpp`에서는 경고 조건을 직접 계산하지 않고 `WarningPolicy`의 결과만 사용하도록 변경
- baseline MD5 일치 확인
  - `a0006c4a16dbe3f69c178fbc5c1b6b8e`
- 분리 작업 후 `main.cpp`가 약 1,130줄에서 606줄로 감소
- FCW 판단 흐름을 다음과 같이 정리
  - `LeadSelector` → 선행 차량 선택
  - `RiskAnalyzer` → 충돌 위험 판단
  - `WarningPolicy` → 실제 경고 표시 여부 결정

### 이 작업을 한 이유
- 위험도 계산과 실제 경고 표시 조건을 서로 다른 역할로 분리하기 위해
- `RiskAnalyzer`는 현재 차량이 얼마나 위험한지를 판단하고, `WarningPolicy`는 그 결과를 언제 실제 경고로 표시할지 담당하도록 하기 위해
- 마지막으로 남아 있던 FCW 판단 코드를 `adas`로 이동해, `main.cpp`에는 영상 입력·화면 출력·각 모듈 연결 같은 실행 코드만 남기기 위해

### 2. Golden CSV MD5 자동 검증
**작업 내용**
- Golden CSV 검증을 Harness 안에 넣음
- 측정 시작 전에 Golden CSV 자체의 MD5를 먼저 확인함
  - `a0006c4a16dbe3f69c178fbc5c1b6b8e`
- 각 Run에서 생성된 FCW 결과 CSV도 같은 MD5와 비교함
- 판정 결과를 `session_summary.csv`에 조건별 컬럼으로 기록함

**PASS 조건**

```text
ADAS 종료 코드 0
FCW 결과 CSV 존재
FCW 결과 CSV MD5 일치
raw_frame_log.csv 존재
run_summary.json 존재
```

- 다섯 조건을 모두 만족해야 PASS임

**이 작업을 한 이유**
- Golden 파일 자체가 잘못된 상태에서 측정을 시작하는 것을 막기 위해
- 코드가 잘못된 것인지 기준 파일이 잘못된 것인지 구분하기 위해
- FCW 결과가 기존 기준과 동일한지 자동으로 확인하기 위해

**검증 결과**
- Smoke Test에서 실행한 모든 Run의 FCW 결과 MD5가 Golden과 일치함
- `session_summary.csv`에 PASS 조건이 정상적으로 기록되는 것 확인함

**알게 된 점**
- MD5는 파일 이름이 아니라 **파일 내용이 같은지 확인하는 값**으로 사용할 수 있음
- 실행이 실패했는데 이전 Run의 CSV가 남아 있으면 그 파일을 새 결과로 착각할 수 있음
  - 그래서 Run 시작 전에 이전 결과 CSV를 삭제해야 함
- PASS / FAIL 이유를 긴 문장으로 저장하기보다 조건별 컬럼으로 나누면 어느 조건이 실패했는지 바로 확인할 수 있음

### 3. Jetson 진단 스크립트에 TensorRT major version 추가
**작업 내용**
- `scripts/jetson_diagnose.sh`의 `[7]` 섹션에 TensorRT major version 확인 기능 추가함
- Jetson과 x86에서 설치 경로가 다를 수 있어 여러 헤더 경로를 확인함
- 찾은 값이 숫자가 아니면 사용하지 않고 다음 방법으로 넘어가도록 함
- 헤더에서 찾을 경우 MAJOR / MINOR / PATCH / BUILD도 같이 출력함

**버전을 찾는 순서**

```text
1. NvInferVersion.h 의 NV_TENSORRT_MAJOR
2. libnvinfer.so.N 의 N
3. dpkg 패키지 버전의 첫 숫자
```

**이 작업을 한 이유**
- TensorRT major version에 따라 사용하는 C++ API가 달라질 수 있기 때문임
- 9월에 `TensorRTBackend`를 만들기 전에 설치된 TensorRT 버전을 먼저 확인하기 위해

**검증 결과**
- `bash -n` 문법 검사 통과함
- x86에서는 TensorRT major가 `NOT FOUND`로 나옴
- TensorRT가 없어도 스크립트가 중단되지 않고 마지막 진단 항목까지 실행됨

**알게 된 점**
- 라이브러리 버전은 환경에 따라 확인할 수 있는 위치가 다를 수 있음
  - 개발용 헤더가 없을 수도 있고
  - 헤더가 없어도 실행용 라이브러리는 설치되어 있을 수 있음
  - 그래서 헤더 → 라이브러리 → 패키지 순서로 확인함
- 진단 스크립트는 한 항목을 찾지 못했다고 전체가 멈추면 안 됨
  - `NOT FOUND`로 남기고 다음 항목을 계속 확인하는 방식이 맞음
