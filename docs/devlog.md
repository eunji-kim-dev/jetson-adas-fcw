## 2. 영상 입출력 파이프라인

가장 먼저 `VideoCapture`와 `VideoWriter`로 프레임 단위 입출력 구조부터 잡았습니다.

```
입력 영상 경로 확인
→ 영상 열기
→ 해상도와 FPS 확인
→ 프레임 반복 처리
→ 결과 영상 저장
→ 처리 프레임 수와 평균 속도 출력
```

처리 시간은 `std::chrono::steady_clock`으로 측정했습니다.

```cpp
const auto processingStart =
    std::chrono::steady_clock::now();

// 프레임 처리

const auto processingEnd =
    std::chrono::steady_clock::now();
```

원본 영상의 재생 FPS와 프로그램이 실제로 처리하는 FPS는 다른 값이라서 따로 관리했습니다. 원본 FPS는 결과 영상 저장과 시간 계산에 쓰고, 처리 FPS는 지금 CPU 환경에서 파이프라인이 얼마나 빠르게 도는지 보는 용도로 뒀습니다.

그리고 출력 파일이 아예 생성이 안 되거나 짧게 잘려 저장되는 걸 막으려고, 프로그램 종료 전에 `capture.release()`와 `writer.release()`를 명시적으로 호출하도록 했습니다.

## 3. 주행 경로 ROI

화면에 보이는 모든 객체를 다 위험 객체로 취급하면 아무 의미가 없어서, 차량이 실제로 지나갈 가능성이 높은 영역을 사다리꼴 ROI로 정의했습니다.

좌표는 고정 픽셀 대신 영상 너비와 높이 비율로 계산했습니다.

```cpp
const std::vector<cv::Point> drivingRoi = {
    cv::Point(
        static_cast<int>(width * 0.40),
        static_cast<int>(height * 0.65)
    ),
    cv::Point(
        static_cast<int>(width * 0.60),
        static_cast<int>(height * 0.65)
    ),
    cv::Point(
        static_cast<int>(width * 0.90),
        static_cast<int>(height * 0.95)
    ),
    cv::Point(
        static_cast<int>(width * 0.10),
        static_cast<int>(height * 0.95)
    )
};
```

이렇게 하면 입력 해상도가 달라져도 비슷한 비율의 ROI를 유지할 수 있습니다.

시각화는 원본 프레임을 완전히 가리지 않도록 반투명 오버레이로 처리했습니다.

```
ROI 오버레이
+
원본 프레임
→ addWeighted()로 합성
```

처음엔 ROI 윗변이 지평선 가까이까지 올라가 있어서 너무 많은 원거리 차량이 위험 영역에 잡혔습니다. 영상의 카메라 시점에 맞춰 윗변을 아래로 내려서 조정했습니다.

## 5. Letterbox 전처리와 좌표 복원

블랙박스 영상은 보통 가로가 긴 비율인데 YOLO 입력은 640×640 정사각형입니다. 원본을 그냥 resize하면 차량 가로세로 비율이 왜곡되기 때문에, 비율은 유지한 채 크기만 줄이고 남는 공간에 패딩을 채우는 Letterbox 방식을 썼습니다.

```
원본 영상 크기 확인
→ 가로세로 비율을 유지한 채 축소
→ 남는 영역에 114 색상 패딩
→ 640×640 입력 생성
```

전처리 결과에는 좌표를 되돌리는 데 필요한 정보도 같이 저장해뒀습니다.

```cpp
struct LetterboxResult {
    cv::Mat image;
    float scale;
    int padX;
    int padY;
};
```

YOLO 출력 좌표는 이 순서로 원본 영상 좌표로 복원합니다.

```
YOLO 출력 좌표
→ Letterbox 패딩 제거
→ resize 배율로 나누기
→ 원본 영상 좌표로 복원
→ 프레임 범위 안으로 clamp
```

영상 밖으로 나가는 좌표는 `std::clamp()`로 잘랐고, 복원한 뒤 너비나 높이가 0 이하가 된 박스는 그냥 버렸습니다.

## 6. 차량 그룹 단위 NMS

처음에는 클래스별로 NMS를 돌렸습니다. car는 car끼리, truck은 truck끼리, bus는 bus끼리.

그런데 YOLO가 같은 차량을 car와 truck으로 동시에 검출해버리면, 서로 다른 클래스라서 박스가 두 개 다 남는 문제가 있었습니다. 추적기 쪽에서는 car, bus, truck을 전부 같은 사륜차 그룹으로 취급하고 있었으니, 검출 단계와 추적 단계의 기준이 어긋나 있었던 셈입니다.

그래서 NMS 기준도 추적 기준에 맞춰 그룹으로 묶었습니다.

- 사륜차 그룹: car, bus, truck
- 이륜차 그룹: bicycle, motorcycle
- 보행자 그룹: person

```
검출 결과
→ NMS 그룹 분리
→ 그룹별 중복 제거
→ 최종 Detection 목록 생성
```

각 그룹별로 `NMSBoxes()`를 따로 돌린 뒤 결과를 하나의 Detection 목록으로 합쳤습니다. 이 뒤로는 같은 차량에 서로 다른 클래스 박스가 겹쳐 남고 별도 Track이 생기는 문제가 줄었습니다.

## 7. 검출과 ROI 시각화 순서 조정

초기에는 ROI 오버레이를 프레임에 먼저 그린 다음 YOLO 추론을 돌렸습니다.

```
ROI 오버레이
→ YOLO 추론
```

이러면 ROI 안쪽 픽셀 색이 초록색과 섞인 상태로 모델에 들어가서, 정면 차량 검출 성능이 떨어졌습니다. 순서를 뒤집었습니다.

```
원본 프레임으로 YOLO 추론
→ Detection 생성
→ 출력용 프레임에 ROI 오버레이
→ 검출 결과 시각화
```

```cpp
detections = detectObjects(
    net,
    frame,
    detectorThreshold,
    nmsThreshold
);

// 추론이 끝난 뒤 시각화
cv::Mat overlay = frame.clone();
```

그 뒤부터는 추론 입력용 원본 프레임과 화면 표시용 프레임을 아예 분리해서 관리했습니다.

## 8. 원거리 차량 검출 보완

초기 confidence threshold는 0.40이었습니다.

```cpp
constexpr float confidenceThreshold = 0.40F;
```

원거리 차량은 화면에서 차지하는 픽셀 수가 적고 특징도 약해서 confidence가 낮게 나왔고, 이 기준에서 자주 걸러졌습니다. 일단 0.25로 낮췄고,

```cpp
constexpr float confidenceThreshold = 0.25F;
```

여기서 추적 안정성을 더 높이려고 검출 하한선을 0.10까지 내리고 Detection을 두 등급으로 나눴습니다.

```cpp
constexpr float detectorThreshold = 0.10F;
```

- 고신뢰도 Detection (confidence ≥ 0.25): 기존 Track 매칭에 쓰고, 신규 Track 생성도 가능
- 저신뢰도 Detection (0.10 ≤ confidence < 0.25): 기존 Track 재연결에만 쓰고, 신규 생성은 불가

저신뢰도 후보를 완전히 버리지는 않되, 그걸로 새 ID가 만들어져서 오검출이 새 차량으로 둔갑하는 건 막고 싶어서 이렇게 나눴습니다.

## 9. ROI 내부 판정 방식

바운딩 박스가 ROI와 조금이라도 겹치면 내부로 판정하는 건 너무 느슨했습니다. 그래서 객체가 실제로 도로에 닿는 위치에 가까운, 바운딩 박스 하단 중앙점을 접지점으로 썼습니다.

```cpp
const cv::Point groundPoint(
    box.x + box.width / 2,
    box.y + box.height
);
```

접지점이 ROI 안에 있는지는 `pointPolygonTest()`로 확인했습니다.

```cpp
const bool insideRoi =
    cv::pointPolygonTest(
        drivingRoi,
        groundPoint,
        false
    ) >= 0.0;
```

초기 단계 시각화는 이렇게 구분했습니다.

- ROI 외부 객체: 주황색 박스
- ROI 내부 객체: 빨간색 박스 + IN ROI 라벨 + 주행 경로 진입 경고

여기서 말하는 경고는 충돌 위험이 아니라, 객체가 설정한 주행 경로 안으로 들어왔다는 1차 이벤트일 뿐입니다.

## 11. Kalman Filter 기반 다중 객체 추적

YOLO는 매 프레임을 독립적으로 검출하기 때문에, 지금 잡힌 차량이 이전 프레임 차량과 같은 객체인지는 알 방법이 없습니다. 이걸 해결하려고 `MultiObjectTracker` 클래스를 따로 만들었습니다.

```
include/
├── Detection.hpp
├── MultiObjectTracker.hpp
└── RiskAnalyzer.hpp

src/
├── main.cpp
├── MultiObjectTracker.cpp
└── RiskAnalyzer.cpp
```

초기 Kalman Filter 상태는 6개(중심 x, 중심 y, x 방향 속도, y 방향 속도, 박스 너비, 박스 높이)였고, YOLO에서 직접 얻는 측정값은 중심 x, 중심 y, 박스 너비, 박스 높이 4개였습니다. Kalman Filter는 이전 위치와 속도로 다음 프레임 박스를 예측하고, 실제 YOLO Detection으로 그 예측값을 보정하는 구조입니다.

## 12. IoU와 중심 거리 기반 매칭

초기 추적기는 Kalman Filter가 예측한 박스와 현재 Detection 박스의 IoU만으로 동일 객체를 판단했습니다.

```
이전 Track 위치 예측
→ 현재 Detection과 IoU 계산
→ IoU가 높은 조합부터 매칭
→ 연결되지 않은 Detection에 새 ID 발급
```

문제는 원거리 차량이었습니다. 박스가 작으니 몇 픽셀만 이동해도 IoU가 확 떨어졌습니다. IoU 하나로는 부족해서 다음 정보를 같이 봤습니다.

- 박스 IoU
- 중심점 거리
- 박스 대각선 크기에 따른 허용 이동 거리
- 박스 면적 변화
- 클래스 그룹
- 검출 신뢰도
- Track 누락 프레임 수

판정 방식은 이렇게 바꿨습니다. IoU가 충분히 높으면 바로 동일 객체 후보로 두고, IoU가 낮더라도 중심 거리가 허용 범위 안이면 추가 조건을 확인한 뒤 동일 객체 후보로 인정했습니다.

허용 이동 거리는 객체 크기에 따라 달라지게 계산했습니다.

```cpp
return std::clamp(
    largestDiagonal * 0.85F + 8.0F,
    16.0F,
    320.0F
);
```

큰 차량은 프레임 사이에 더 많이 움직여도 봐주고, 작은 차량은 허용 거리를 좁게 유지하는 식입니다.

## 13. 초기 Track 완화 매칭

새로 생긴 Track은 아직 속도 정보가 없습니다.

```
새 Track 생성
→ x/y 속도 0
→ 다음 위치를 제자리로 예측
→ 실제 Detection은 이동
→ 매칭 실패
→ 또 새 Track 생성
```

Kalman Filter가 속도를 배우려면 최소 몇 프레임은 Detection이 이어져야 하는데, 기존 매칭 조건은 마치 이미 정확한 속도를 알고 있다는 전제처럼 너무 엄격하게 짜여 있었습니다.

그래서 초기 Track에는 완화된 조건을 적용했습니다. hits가 적은 초기 Track은 중심 거리와 면적 변화 허용 범위를 넓혀주고, 최소 2~3프레임 동안은 속도를 학습할 기회를 줬습니다. 이 뒤로 같은 차량에 매 프레임 새 ID가 생기는 현상이 크게 줄었습니다.

## 14. Tracking ID 가로채기 문제 개선

YOLO가 잠시 놓친 Track도 일정 프레임 동안은 목록에 남아 있습니다. 문제는 오래 놓친 Track과 직전 프레임까지 정상적으로 이어진 Track이 똑같은 우선순위로 현재 Detection을 두고 경쟁했다는 점입니다. 오래된 Track의 예측 위치가 우연히 현재 차량 근처로 오면, 정상 ID 대신 예전 ID가 Detection을 가져가 버렸습니다.

매칭 단계를 나눴습니다.

1. **1차 매칭**: 최근까지 정상적으로 이어진 Track + 고신뢰도 Detection
2. **2차 매칭**: 1차에서 연결 안 된 최근 Track + 저신뢰도 Detection
3. **3차 복구 매칭**: 여러 프레임 놓친 Track + 남은 고신뢰도 Detection

오래 놓친 Track에는 누락 프레임 수에 따른 페널티도 추가했습니다.

```
누락 프레임 증가
→ 매칭 비용 증가
→ 정상 Track보다 우선순위 감소
```

그 외에 중심점 거리 제한, 박스 면적 변화 제한, 복구 가능한 누락 프레임 수 제한, 같은 클래스 그룹 가산점, 오래 놓친 Track일수록 추가 감점 같은 조건도 함께 걸었습니다. 이후로 정상적으로 유지되던 ID가 과거 ID에 가로채이는 경우가 줄었습니다.

## 15. Kalman Filter 상태 확장

차량이 카메라 쪽으로 다가오면 중심 위치뿐 아니라 박스 너비와 높이도 계속 커집니다. 기존 Kalman Filter는 너비·높이 값 자체는 알고 있었지만, 그게 얼마나 빠르게 변하는지는 상태에 포함하지 않고 있었습니다.

상태값을 6개에서 8개로 늘렸습니다: 중심 x, 중심 y, x 방향 속도, y 방향 속도, 박스 너비, 박스 높이, 너비 변화속도, 높이 변화속도. 박스 크기 변화속도까지 상태에 넣어서, 차량이 접근하거나 멀어질 때 다음 프레임의 크기 변화도 예측에 반영되도록 했습니다.

## 16. ByteTrack 방식의 고·저신뢰도 매칭

confidence가 0.41 → 0.28 → 0.18 → 0.33처럼 프레임마다 흔들리는 경우가 있었습니다. 0.25 하나만 기준으로 쓰면 0.18이 나온 프레임에서 Detection이 사라지고, 이게 반복되면 Track이 삭제됩니다.

ByteTrack 방식을 참고해서 Detection을 두 단계로 나눠 썼습니다.

```cpp
MultiObjectTracker tracker(
    0.25F,  // 고신뢰도 기준
    0.10F,  // 저신뢰도 최저 기준
    3,      // ID 확정에 필요한 매칭 횟수
    20      // 확정 Track 보관 프레임
);
```

저신뢰도 Detection은 신규 Track을 만들지 않고 기존 Track을 이어주는 데만 썼습니다. 새 Track도 일정 횟수 이상 연결된 뒤에야 정식 ID로 확정되게 해서, 한 프레임짜리 오검출이 바로 새 객체로 잡히는 문제도 함께 줄였습니다.

## 17. 위험 분석 영역을 ego lane으로 분리

초기에는 넓은 driving ROI 안의 모든 객체를 위험 대상으로 분석했습니다. 그런데 옆 차선 차량이 카메라 가까이 지나가면 화면에서 박스가 빠르게 커지기 때문에, 실제 충돌 가능성과 무관하게 위험으로 오판할 수 있었습니다.

넓은 ROI 안에서 중앙 부분만 다시 좁혀 ego lane 영역을 만들었습니다.

```
driving ROI → 넓은 도로 관심 영역
ego lane ROI → 실제 선행 차량을 선택할 중앙 차선 영역
```

옆 차선 차량은 계속 검출하고 추적은 하되, 위험 분석 대상에서만 뺐습니다. ego lane 내부 차량은 선행 차량 후보로 두고, driving ROI 안이지만 ego lane 밖이면 SIDE 객체로 분류했습니다. 이 변경으로 측면의 대형 트럭이나 인접 차선 차량이 위험 경고를 일으키는 문제가 줄었습니다.

## 18. 선행 차량 LEAD 선택

ego lane 안에 차량이 여러 대 있을 수 있어서, 위험 분석 대상 한 대를 고르는 로직을 추가했습니다. 각 후보에 대해 ego lane 내부 여부, 박스 하단 중앙점 위치, 화면 아래쪽에 얼마나 가까운지, 차선 중심선과 얼마나 가까운지, 현재 Track ID의 연속성을 봤습니다. 화면 아래쪽에 있고 차선 중앙에 가까운 차량일수록 높은 점수를 받습니다.

프레임마다 후보가 조금씩 흔들려서 LEAD ID가 계속 바뀌는 걸 막으려고 히스테리시스를 넣었습니다. 기존 LEAD가 계속 보이면 기본적으로 유지하고, 새 후보가 나타나도 기존 후보보다 점수가 충분히 높을 때만 교체합니다. 위험 분석 대상이 한 대로 좁혀지면서 화면 정보도 단순해지고 경고 기준도 더 명확해졌습니다.

## 19. TTC-P 설계

단안 블랙박스 영상만으로는 차량까지의 실제 거리나 실제 상대속도를 정확히 알 수 없습니다. 카메라 내부 파라미터, 차량 실제 크기, 도로 기하 정보가 없기 때문에, 결과를 실제 TTC라고 부르지 않고 **TTC-P(TTC Proxy)**라고 이름 붙였습니다.

선행 차량의 바운딩 박스 높이가 시간에 따라 얼마나 빠르게 커지는지를 이용했습니다.

```
차량이 가까워짐
→ 화면에서 박스 높이 증가
→ log(box height)의 증가율 계산
→ 증가율이 클수록 TTC-P 감소
```

한두 프레임의 박스 흔들림에 결과가 휘둘리지 않도록, 최근 여러 샘플에 선형회귀를 적용했습니다. `RiskAnalyzer`가 관리하는 주요 정보는 프레임 번호, 박스 높이, 박스 하단 y좌표, 최근 샘플 수, log-height 회귀 기울기, 하단점 y방향 이동 속도, 박스 높이 증가 비율, TTC-P, 위험 단계 정도입니다.

TTC-P는 실제 거리 기반 충돌 시간이 아니라, 영상 속 크기 변화로 계산한 접근 위험 지표라는 점을 계속 염두에 뒀습니다.

## 20. 위험 단계 시간 안정화

검출 박스는 매 프레임 조금씩 흔들리기 때문에 TTC-P도, 위험 단계도 순간적으로 왔다 갔다 할 수 있습니다.

```
SAFE → CAUTION → SAFE → CAUTION
```

이 상태를 그대로 화면에 내보내면 경고가 계속 깜빡입니다. `RiskAnalyzer` 안에 안정화 로직을 넣었습니다. 새 위험 단계가 일정 프레임 이상 유지돼야 단계 변경을 확정하고, 위험 단계가 낮아지는 방향이면 즉시 낮추지 않고 일정 시간 더 확인합니다. Track이 LEAD에서 빠지면 그 Track의 위험 이력은 초기화합니다. 상단 경고 배너도 일정 시간 유지해서 한두 프레임 누락만으로 바로 사라지지 않게 했습니다.

## 21. 경고 단계와 TTC-P 숫자 표시 분리

위험 단계는 안정화 때문에 잠시 유지되는데, TTC-P 숫자는 매 프레임 갱신됩니다. 이 때문에 다음처럼 모순돼 보이는 표시가 나왔습니다.

```
CAUTION: CLOSING LEAD 17.5s
```

이전 프레임에서 TTC-P가 낮아 CAUTION이 확정된 뒤, 다음 프레임에서 TTC-P는 올라갔지만 위험 단계는 안정화 로직 때문에 잠시 유지되고 있던 상황이었습니다.

상단 배너에서는 TTC-P 숫자를 뺐습니다.

```
CAUTION: CLOSING LEAD
DANGER: LOW TTC-P
```

현재 TTC-P는 선행 차량 라벨과 왼쪽 상태 정보에서만 보여주기로 했습니다. 상단 배너는 현재 위험 단계를, 선행 차량 라벨과 상태창은 현재 TTC-P 수치를 각각 맡는 식으로 역할을 나누고 나니, 경고와 수치가 서로 모순처럼 보이는 문제는 사라졌습니다.

## 22. 우측 탱크로리 원시 후보 진단

19초부터 화면 오른쪽에 탱크로리가 보이는데, 22초가 지나야 truck 박스가 생기는 문제가 있었습니다.

처음엔 입력 해상도 문제라고 생각해서 우측 영역을 Crop한 뒤 추가 추론하는 방식도 시험해봤습니다.

```
전체 프레임 YOLO 추론
→ 우측 영역 Crop
→ Crop을 640×640으로 확대
→ 추가 YOLO 추론
→ 원본 좌표로 복원
```

그런데 처리 시간만 늘고 검출 시점은 거의 나아지지 않았습니다. 원인을 정확히 보려고 18~24초 구간의 필터링 전 YOLO 후보를 CSV로 저장해봤습니다. frame, time, 상위 1·2·3순위 클래스, car / bus / train / truck / boat 점수, 박스 좌표와 크기, confidence 통과 여부, 대상 클래스 통과 여부, 최종 필터 통과 여부까지 기록했습니다.

결과를 보니 문제의 큰 박스는 21.9초부터 이미 생성되고 있었는데, 클래스가 계속 train(6)으로 분류되고 있었습니다.

```
21.922초  train 0.768
21.989초  train 0.886
22.055초  train 0.904
22.122초  train 0.914
22.289초  truck 0.607
```

즉 검출 위치를 못 찾은 게 아니라, 클래스 오분류와 후처리 필터의 문제였던 겁니다.

## 23. train으로 오분류된 탱크로리 제한적 복구

기존 검출 코드는 최고 점수 클래스가 ADAS 대상이 아니면 후보를 바로 지워버렸습니다.

```
탱크로리 박스 생성
→ 최고 클래스 train
→ isTargetClass(6) == false
→ Detection 삭제
→ Tracker에 전달되지 않음
```

모든 train을 truck으로 바꿔버리면 다른 장면에서 오검출이 늘어날 위험이 있어서, 조건을 제한했습니다. 원래 최고 클래스가 train이고, 신뢰도 0.25 이상이고, 화면 오른쪽에 위치하고, 박스가 충분히 크고, 박스 하단이 도로 영역까지 내려오는 경우에만 truck(7)으로 재해석해서 기존 차량 NMS와 Tracker에 넘기도록 했습니다.

이 방식으로 21.9초 이후의 큰 탱크로리 박스는 기존 파이프라인 안에서 계속 추적할 수 있게 됐습니다. 다만 19~21초 초반에는 유효한 후보 자체가 거의 없었기 때문에, 이 구간은 지금 모델의 한계로 남겨뒀습니다.

## 24. 원거리 작은 차량 오경고 필터링

멀리 있는 작은 선행 차량은 바운딩 박스 높이가 몇 픽셀만 바뀌어도 비율상 큰 변화로 계산됩니다. 그래서 실제로는 급접근하는 게 아닌데 TTC-P가 순간적으로 작아지면서 CAUTION이 뜨는 문제가 있었습니다.

TTC-P 임계값 하나만 보지 않고 다음 조건을 같이 확인하도록 했습니다.

- TTC-P 계산이 유효함
- 관찰 샘플 수가 충분함
- 선행 차량 박스 높이가 일정 이상
- 차량 하단점이 화면에서 충분히 가까움
- 박스 높이가 관찰 구간에서 의미 있게 증가함
- 하단점이 화면 아래 방향으로 이동함

```
원시 RiskAnalyzer 결과
→ 경고 신뢰성 조건 검사
→ 조건 부족 시 화면 경고 차단
```

이 조건을 통과하지 못한 위험 결과는 내부 계산값이 있더라도 화면에서는 SAFE로 처리했습니다. 이후로 작은 원거리 박스의 검출 흔들림 때문에 생기던 오경고가 줄었습니다.

## 25. 장면 전환 감지와 상태 초기화

입력 영상은 하나의 연속 주행 영상이 아니라 여러 도로 장면이 편집되어 이어진 영상입니다. 약 10초 구간에서 장면이 갑자기 바뀌는데, 이전 장면의 경고 유지 카운터가 다음 장면까지 그대로 남는 문제가 있었습니다.

장면 전환 감지기를 추가했습니다.

```
프레임을 320×180 회색 영상으로 축소
→ 이전 프레임과 평균 절대 차이 계산
→ 밝기 히스토그램 상관계수 계산
→ 전체 변화량이 크면 장면 전환 판단
```

장면 전환이 감지되면 상단 경고 유지 카운터, CAUTION/DANGER 후보 프레임 수, 현재 LEAD ID, TTC-P 분석 상태를 전부 초기화합니다. 새 장면 직후에는 약 0.5초 동안 위험 분석을 멈춰서, 검출과 Tracking이 안정화된 뒤에 LEAD를 다시 고르도록 했습니다.

상단 배너도 위험 상태가 연속으로 관찰될 때만 뜨도록 확인 프레임을 뒀습니다(CAUTION은 8프레임, DANGER는 3프레임 연속 확인). 이 뒤로는 차량이 없는 새 장면에 이전 장면의 경고가 잠깐 남는 현상이 사라졌습니다.

## 26. 한국어 UI와 결과 화면 정리

OpenCV 기본 Hershey 글꼴은 한글을 지원하지 않아서, OpenCV FreeType과 시스템 한글 글꼴(NanumGothic 또는 Noto Sans CJK)을 같이 썼습니다.

최종 결과 화면은 다음 기준으로 정리했습니다.

- 객체 클래스명: car, truck, person 등 영어 유지
- 왼쪽 상태 정보: 한국어
- 상단 경고 배너: 한국어
- 진단용 원시 후보: 최종 영상에서 제거
- 핑크색 디버그 ROI: 제거
- 왼쪽 아래 설명 문구: 제거

디버깅 버전과 포트폴리오용 결과 버전을 분리해서, 화면에는 필요한 정보만 남겼습니다.

## 현재 구현 상태

```
블랙박스 영상 입력
→ 영상 정보 확인
→ Letterbox 전처리
```

## 남아 있는 한계

**1. 실제 거리 기반 TTC가 아님**

현재 TTC-P는 바운딩 박스 높이 증가율을 이용한 Proxy입니다. 정확한 거리 기반 TTC를 계산하려면 카메라 내부 파라미터, 카메라 설치 높이와 각도, 차량 실제 크기 추정, 차선과 도로 기하 정보, 카메라 자체 움직임 보정이 필요합니다.

**2. 장시간 재식별 불가**

Track 보관 시간보다 오래 YOLO 검출이 끊기면 새 ID가 생성됩니다. 지금 추적기는 위치와 크기 중심이라 이전 차량의 색상이나 외형을 비교할 수 없습니다. 장시간 동일 차량 여부를 판단하려면 Re-ID 특징이 필요합니다.

**3. 부분 노출 객체 조기 검출 한계**

오른쪽 탱크로리는 21.9초 이후의 train 오분류는 복구할 수 있었지만, 19~21초에는 의미 있는 YOLO 후보 자체가 거의 없었습니다. 이 구간을 풀려면 YOLOv8s 이상 모델 사용, 입력 해상도 확대, 부분 노출·역광 탱크로리 데이터 파인튜닝, 전역 카메라 모션 보정, 우측 경계 이동 객체 감지, Edge 후보와 정식 YOLO Track 연결 같은 방법을 검토해야 합니다.

**4. 특정 테스트 영상에 맞춘 Rule-based 조건**

train 오분류 복구 조건과 장면 전환 임계값은 지금 테스트 영상의 특성을 기반으로 조정한 값입니다. 다양한 영상에 적용하려면 여러 도로 환경에서 정량 평가와 재조정이 필요합니다.
