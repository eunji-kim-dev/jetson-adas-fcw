### 2. FP32 / FP16 / INT8 288×640 속도 표 확정

**작업 내용**
- FP32, FP16, INT8 각 5회 측정 결과를 `analyze_runs.py`로 정리함

**검증 결과**
- 프레임 전체 처리시간 p50: FP32 31.1ms / FP16 26.1ms / INT8 23.9ms
- Full 640×640 추론: FP32 9.1ms / FP16 5.8ms / INT8 4.3ms
- Crop 288×640 추론: FP32 5.0ms / FP16 3.1ms / INT8 2.5ms
- 정밀도와 관계없이 남는 시간: 전처리 약 5.7ms + 후처리 약 5.3ms + 추적·FCW 판단 약 5.9ms = 약 17ms

**알게 된 점**
- INT8은 FP16보다 프레임당 약 2.2ms(약 8%) 빠름
- 이전에 기록한 3.6ms 차이는 1회 평균값이었고, 반복 측정 p50 기준으로는 2.2ms가 정확함
- FP16 288×640 기준 p50은 26.1ms로 확정함
- 정밀도를 더 낮춰도 약 17ms는 그대로 남음. 현재 구조에서는 GPU 추론만 더 빠르게 해도 전체 처리시간이 크게 안 줄어드는 구간에 들어감

### 3. `fp32head` 엔진 빌드 오류 수정

**작업 내용**
- 검출 헤드를 FP32로 강제할 때 정수형 출력을 가진 층까지 같이 선택돼 엔진 생성이 실패하던 문제를 고침
- 출력 텐서가 FP32·FP16 계열이 아닌 층은 FP32 강제 대상에서 제외하도록 수정함. 검출 헤드 전체(`/model.22/`)를 보호하는 범위는 그대로 둠
- 수정 후 `fp32head`, `minmax + fp32head` 엔진 2개를 다시 생성함
- `compare_precision.py`에 FP32 기준 쪽에만 confidence 조건을 거는 옵션(`--min-conf-a`)과 검출 소실 비율 열을 추가함

**검증 결과**
- 두 엔진 모두 정상 빌드됨. 헤드에서 약 70개 층을 FP32로 강제했고 정수 출력층 3개는 제외됨
- 수정한 바이너리로 정식 INT8 엔진을 실행했을 때 기존 골든과 동일함

### 4. INT8 검출 손실 원인 분석

**작업 내용**
- FP32 288×640 기준으로 INT8 엔진 5종을 박스 단위로 비교함: 정식 Entropy, MinMax, calibration 이미지 순서 섞기, Entropy + 헤드 FP32, MinMax + 헤드 FP32

**검증 결과**

| INT8 방식 | 대응된 박스 | confidence 차이 중앙값 | FP32 conf≥0.4 중 소실 | 높이 차 ±2px 이내 |
|---|---:|---:|---:|---:|
| Entropy (정식) | 6,657 | −0.170 | 25.2% | 58% |
| MinMax | 14,596 | −0.013 | 2.4% | 71% |
| Shuffle | 5,441 | −0.183 | 34.9% | 55% |
| Entropy + 헤드 FP32 | 7,095 | −0.123 | 22.8% | 59% |
| MinMax + 헤드 FP32 | 15,166 | −0.003 | 2.4% | 73% |

- 참고: FP16은 대응 박스 18,232개, 높이 차 ±2px 이내 99.7%

**알게 된 점**
- 가장 큰 원인은 Entropy calibration 방식임. MinMax로 바꾸면 confidence와 검출 개수가 FP32에 가까워짐
- calibration 이미지 순서를 섞는 것은 효과 없음
- 검출 헤드를 FP32로 강제해도 Entropy·MinMax 모두 큰 개선 없음. 검출 손실은 헤드보다 앞쪽 백본·Neck의 INT8 양자화에서 생기는 것으로 보임
- MinMax를 써도 박스 좌표는 FP16보다 흔들림. 대응된 박스 중 약 27%는 높이가 FP32와 2px 넘게 차이남
- TTC-P는 박스 높이에 민감하므로 이 좌표 차이가 실제 TTC에 영향을 주는지 추가 확인이 필요함
- TOPST 등 INT8 적용 시 Entropy는 쓰지 않고 MinMax 계열을 우선 쓰는 방향으로 정리함

### 1. LEAD 규칙 개선 기능 적용

**작업 내용**
- 9/28에 정한 설계대로 `--lead-rule` 옵션을 추가함
- 옵션을 켜면 기존 LEAD 선택 규칙에 5가지를 더할 수 있음
- `overlap`: 차선 안에 완전히 안 들어왔어도 차선과 겹치기 시작한 차량을 LEAD 후보로 봄
- `history`: 차량이 차선에 들어오기 전부터 추적 이력을 쌓아 둠
- `gap`: 중간에 몇 프레임 검출이 끊겨도 이전 추적 기록을 바로 버리지 않음
- `passby`: 옆으로 지나가는 차량인지 판단할 때 차선과 겹치는 정도의 변화를 같이 봄
- `gate`: 위험 판정이 DANGER이고 차선과 절반 이상 겹치면 접지점 위치 조건을 면제함
- 총 12개 파일, 37곳 수정함
- 옵션을 켜지 않으면 기존 코드와 똑같이 동작하게 만듦. 기존 결과를 망가뜨리지 않기 위해서임
- `run_summary.json`에 어떤 LEAD 규칙을 썼는지 `lead_rule` 항목을 추가하고 형식 버전을 v6으로 올림
- `analyze_runs.py`에 `lead rule` 열을 추가함
- `run_eval_set.sh`에서 `LEAD_RULE` 환경변수로 옵션을 넘길 수 있게 함
- 커밋 `2ff16a8`
- 코드를 만든 뒤 외부 검토를 4번 받았고 그때마다 코드를 고침. 지적받은 문제는 전부 실제로 고쳐야 하는 문제였음

**검증 결과**
- 옵션을 켜고 실행하면 로그에 `[INFO] LEAD 규칙: overlap,history,gap,passby,gate`가 찍힘
- `run_summary.json`에 `"lead_rule"`과 `"schema_version": 6`이 저장됨
- 기존 `LeadSelector`와 새 `LeadSelector`를 새 옵션을 모두 끈 상태에서 비교함. 의사난수 트랙 5세트를 각각 600프레임씩 돌렸고 모든 프레임에서 결과가 완전히 같았음
- 옵션 없이 돌려 골든 일치 확인함. x86 `87453f9c`, Jetson `4681f432`. 오늘 커밋 3개(LEAD 코드, 초록 제거, ROI) 뒤에도 같음

**알게 된 점**
- `gap`으로 추적 기록을 보존하자 횡이동 속도가 과대평가됨. 예전 코드는 속도를 관측한 데이터 개수로 나눴는데, 중간 프레임이 비어 있으면 실제로는 시간이 많이 지났는데 개수는 적어서 옆으로 훨씬 빠르게 움직인 것처럼 계산됨 → 기록에 프레임 번호를 같이 저장하고 실제로 몇 프레임이 지났는지로 나누게 고침
- 유예 프레임 처리 순서에도 문제가 있었음. 유예 횟수를 먼저 줄이고 판단하면 유예가 1프레임 남았을 때 추적 기록이 먼저 끊김 → `overlap`에서는 줄이기 전 값으로 판단하게 고침
- `overlap,`처럼 마지막에 쉼표만 붙은 입력이 통과되고 있었음 → 빈 항목은 오류로 처리함
- 박스 높이가 갑자기 변하면 이력을 리셋하는 기능은 40% 고정으로는 안 됨. 충돌 직전처럼 아주 빠르게 가까워지면 4프레임 사이에 높이가 50% 넘게 커지는 것도 정상임. DANGER는 TTC 2.5초 근처가 아니라 2.5초 이하 전체 구간이라는 걸 제가 잘못 봤음
- 미래 높이 예측도 고침. 처음엔 박스 높이의 log 값이 평균적으로 얼마나 늘어나는지로 예상했는데 차량이 가까워질수록 예상값이 실제보다 작아짐 → `1 ÷ 차량 높이`가 시간에 따라 어떻게 변하는지를 직선으로 맞춰 미래 높이를 직접 예측하게 바꿈
- `boxHeight`는 화면에 보이는 높이가 아니라 차량 아래쪽이 잘렸을 때 폭으로 보정한 높이라 화면 높이보다 커질 수 있음. 여기에 화면 높이 상한을 씌워서 정상 접근을 이상값으로 처리하고 있었음 → 상한을 삭제하고, 예측이 안 되는 상황에서는 높이가 갑자기 줄어드는 경우만 검사함
- `git checkout -- .`은 작업 트리 전체 변경을 날림. 특정 파일만 되돌릴 땐 파일 경로를 지정한 stash를 씀
- 기존 코드에 원래 있던 경계 문제는 새 옵션을 켰을 때만 고침. 그래야 기존 골든이 그대로 유지됨

### 3. 카메라 동기 방식과 스레드 분리 방식 비교

**작업 내용**
- probe로 카메라가 30fps인지 먼저 확인함. 프레임 간격 중앙값 약 32.0ms
- FP32 640 동기 / FP32 640 스레드 분리 / FP16 288 동기 / FP16 288 스레드 분리 4조합을 각각 900프레임씩 측정함
- 처음 4개 결과를 보다가 Jetson 클럭이 고정되지 않은 것을 발견함. `jetson_clocks --show`에서 GPU가 최저 306MHz까지 내려가 있었음
- `sudo jetson_clocks`를 켠 뒤 4조합을 다시 측정함. 재측정 결과가 `cam0929c_*`이고 이게 정식값임

**검증 결과**
- 클럭 고정 정식값. FP32 640은 프레임 하나 처리에 약 35.5ms가 걸려 카메라 간격 33.3ms보다 약간 느림
- FP32 640 동기: Frame Age 163ms, 카메라 쪽 drop 72. 스레드 분리: Frame Age 84ms, 프로그램 쪽 drop 64
- FP16 288은 처리 22.9ms로 카메라보다 충분히 빨라서 동기·분리 모두 Frame Age 약 55ms, drop 0
- 클럭을 안 고정한 참고값. FP32 640 동기 Frame Age 215ms·drop 352, 분리 94ms·drop 346. FP16 288 처리 동기 30.3ms, 분리 36.9ms

**알게 된 점**
- 처리 시간이 카메라 간격 33.3ms보다 느리면 동기 방식은 V4L2 버퍼(4장)에 프레임이 쌓여 카메라가 지금 보는 것보다 훨씬 늦은 영상을 처리하게 됨. 그래서 Frame Age가 163ms까지 올라감
- 스레드를 분리하면 항상 최신 프레임을 가져와서 Frame Age가 84ms로 줄어듦. 대신 처리 못 한 오래된 프레임을 프로그램이 직접 버림
- 버리는 양 자체가 크게 줄어드는 건 아니고, 카메라 드라이버가 버리느냐 프로그램이 버리느냐의 차이임
- FP16 288처럼 처리가 카메라보다 충분히 빠르면 두 방식 차이가 거의 없음. 스레드 분리는 처리가 느려졌을 때 지연이 누적되는 걸 막는 보험이고, 최종 FP16 288 구조에서는 이득이 없음 → 기본 설정은 계속 꺼 둠
- `adas`를 직접 실행하면 `jetson_clocks`가 자동으로 안 켜짐. benchmark harness만 자동으로 켬. 앞으로 Jetson에서 직접 측정하기 전엔 `sudo jetson_clocks`를 먼저 실행해야 함
- `run_summary.json`에 기록되는 온도와 `jetson_clocks` 상태가 Jetson에서 `null`로 나옴. `jetson_env`가 JetPack 7 시스템 경로를 못 읽는 것으로 보임
- 9/27 카메라 값(처리 31.5ms, Frame Age 64ms)도 클럭을 안 고정한 상태에서 잰 값으로 봐야 함
- 카메라 입력(640×480)과 파일 입력(1280×720)은 처리 시간을 직접 비교하면 안 됨. 카메라 22.9ms, 파일 26.1ms는 입력 크기 자체가 다름

### 4. 호모그래피 TTC 설계 → TTR-H 독립 실험으로 변경

**작업 내용**
- 원래는 호모그래피로 새 TTC를 계산하려 했는데 외부 검토 3번을 거치면서 실험 목적을 바꿈
- 가장 큰 문제는 화면 안에서 자차 앞범퍼 위치를 알 수 없다는 것임. 호모그래피로 도로 위 거리는 계산할 수 있어도 "우리 차 범퍼까지 몇 m 남았는가"를 몰라서 충돌까지 남은 시간은 계산할 수 없음
- 그래서 이 값을 TTC라고 부르지 않고 `TTR-H`로 따로 정의함. 상대 차량이 화면 중앙에서 보이는 도로의 마지막 지점까지 도달하는 데 걸릴 것으로 예상되는 시간임
- TTC-P와 TTR-H는 서로 다른 것을 재므로 당장 합치지 않고, 둘을 따로 기록해서 어떤 차이가 있는지 비교하는 실험으로 범위를 줄임
- 기준 거리 `Z_c`는 화면 중앙 x = (frameWidth − 1) / 2.0 에서 보닛 선과 만나는 한 점을 호모그래피로 변환해 계산함
- 거리 이력은 같은 차량 트랙, 최근 최대 15개, 최대 1초 이내, 마지막 정상 샘플 뒤 최대 5프레임 공백까지만 씀
- TTR-H 쪽 위험 단계는 TTC-P와 독립으로 관리함. H 쪽 자체 안정화와 배너 연속 카운터를 따로 가짐
- `h_valid=false`이면 새 H 경고 후보의 연속 카운트를 끊음
- 박스 아래쪽이 `bottom_y >= frameHeight − 2`이거나 `bottom_y >= bonnet_y − 4`이면 거리 계산에서 제외함
- `videos.csv`에 도로 평면 4점, 실제 도로 폭, 실제 도로 길이, 기준 프레임, 영상 해상도, 보닛 선, 보정 상태를 기록하기로 함
- `_banner.csv`에 `p_banner`, `h_banner`, `ttc_p`, `ttr_h`, `h_state`를 추가하기로 함. 원시 프레임 로그에는 `distance_m`, `ttr_h`, `h_valid`, `h_level`, `p_level`
- TTR-H 코드 전에 `--diag-log`를 먼저 넣기로 함. 원래 박스 높이, 절단 보정 높이, 종횡비, 잘림 여부, 게이트 통과 전 내부 상태, TTC-P를 기록함
- 미결: TTC-P와 TTR-H를 나중에 어떻게 결합할지, TTC-P를 언제 무효로 볼지, TTR-H를 충돌 시간에 가깝게 보정할 `d0`

**알게 된 점**
- 호모그래피 거리가 실제의 2배처럼 일정 비율로 틀려도 TTC에는 문제없다고 생각했는데, 이건 거리의 원점이 정확할 때만 맞음. 거리와 속도가 같이 2배면 약분되지만 시작점이 범퍼 위치와 다르면 그 오차는 안 사라짐
- TTC-P와 TTR-H가 다르다고 둘 중 하나가 틀린 게 아님. 처음부터 재는 대상이 다름. 둘 중 작은 값을 쓰거나 차이가 크면 이상이라고 보는 건 근거가 없음
- 지금 코드는 박스가 화면 아래에서 잘리면 폭을 종횡비로 나눠 원래 높이를 추정하고 접지 관련 조건도 일부 면제함. "잘리면 높이가 포화돼서 끝"이라는 예전 설명은 정확하지 않았음
- 박스 아래쪽이 화면 안에 있어도 실제 타이어 접지점이 보인다고 볼 수 없음. 보닛이 가릴 수 있음
- 거리 눈금이 검증되지 않은 상태에서는 m/s 단위 기준을 쓸 수 없음
- 속도 계산은 영상의 실제 fps를 받아 쓰므로 15fps가 코드에 박혀 있진 않음. 다만 최근 10프레임, 연속 3프레임 같은 프레임 개수 기준은 그대로라 10fps 영상에서는 실제 시간 기준 반응이 달라짐
- `_frames.csv`에는 절단 보정된 높이가 저장되지 않음. 03·07·08을 정확히 보려면 `diag-log`가 필요함

### 5. 결과 영상 확인 및 lane ROI 수정

**작업 내용**
- 센터 PC에서 새 LEAD 규칙을 켠 결과 영상 21개를 만듦 (`results/lead_on/`)

**검증 결과**

- 검출 뒤 오토바이를 따로 제거하는 로직은 없음. 포함 관계 박스 제거도 같은 NMS 그룹 안에서만 동작함 → LEAD 규칙 문제가 아니라 모델 출력·FP32/FP16 계산·색 캐스트 차이에 따른 검출 문제로 봄. 원시 신뢰도는 센터 PC에서 확인 예정

### 3. `bonnet`, `hold` 규칙 추가

커밋:

```text
57410ed
```

#### `--lead-rule bonnet`

보닛 또는 보닛 반사로 의심되는 박스를 다음 조건으로 판정함.

```text
박스 아래 변 >= 화면 높이의 95%
박스 위 변 >= 화면 높이의 55%
폭 / 높이 >= 2.5
```

조건을 만족하면 첫 프레임부터 바로 정상 관측으로 사용하지 않고 **비정상 관측 후보**로 처리함.

동작 방식:

1. 최대 3프레임까지 기존 상태를 보존
2. 3프레임을 넘겨 계속 같은 모양이면 보닛으로 확정
3. 확정된 박스는 LEAD 후보 및 위험 분석에서 제외
4. 관련 이력은 리셋
5. 정상적인 차량 모양이 1프레임이라도 들어오면 즉시 해제

즉, “이 모양이면 무조건 차량이 아니다”가 아니라 **보닛일 가능성이 높은 일시적 비정상 관측으로 먼저 처리**함.

#### `--lead-rule hold`

기존 `history`는 차량 높이가 40% 이상 급변하면 즉시 이력을 리셋했음.

`hold`에서는 이를 바로 리셋하지 않고 **최대 3프레임 동안 일시적 관측 오류로 보존**함.

보존 중에는:

- 새 샘플을 이력에 추가하지 않음
- 기존 위험 단계 유지
- 기존 LEAD 유지
- 해당 객체를 새로운 LEAD 후보로 사용하지 않음
- LeadSelector의 체류·횡이동·겹침 이력을 동결
- DANGER 배너 카운터는 증가시키지도, 초기화하지도 않음

또한 보존 중 들어온 샘플은 `heldSamples`에 따로 저장함.

3프레임을 넘어 실제 리셋이 필요한 상황이 되면 이 샘플을 새 이력의 시작점으로 승계함.

이 처리가 없으면 08에서 기존 `history`보다 다시 3프레임을 더 기다리게 되어 DANGER가 사라지는 문제가 발생했음.

### 4. `rank` 규칙 추가 및 대상 기준 채점

`rank`는 현재 기본 LEAD 규칙 조합에는 포함하지 않고 별도 실험 중임.

#### `--lead-rule rank`

접지점 자체는 lane 밖이지만, 박스 일부가 lane과 겹쳐서 후보가 된 차량에 다음 감점을 줌.

```text
감점 = (1 - overlap) × 400
```

중요한 점은 `rank`가 해당 차량을 후보에서 제거하는 규칙은 아니라는 것임.

**여러 후보가 경쟁할 때 우선순위만 낮춤.**

따라서 해당 차량이 유일한 후보라면 그대로 LEAD가 될 수 있음.

#### 선정 로그 추가

--lead-select-log
```

1. 감점 계수를 약 150으로 감소
2. overlap >= 0.30이면 감점하지 않음
```

하지만 03에서는 두 방식 모두 후보 사이 점수 차이가 약 `4점 / 0.016` 수준으로 매우 작음.

따라서 **10번 컷인 로그를 먼저 확인한 뒤 계수와 문턱을 결정하기로 함.**

그전까지 `rank`는 기본 규칙 조합에 넣지 않음.

### 5. 외부 검토 반영

아스트라 검토를 총 3회 반영함.

주요 반영 사항은 다음과 같음.

1. 기존 차량 ID가 갑자기 보닛 박스로 옮겨 붙는 경우에도 첫 프레임부터 비정상 관측으로 처리
2. 보닛 조건을 “차량 아님” 확정 조건이 아니라 “보닛 의심 조건”으로 수정
3. 검증 범위를 현재 LEAD뿐 아니라 실제 충돌 대상 차량 전체로 확대
4. `hold` 상태에서 LeadSelector의 체류·횡이동·겹침 이력을 모두 동결
5. 기존 LEAD 유지와 새로운 후보 승격을 분리
6. `rank`를 차량 제거 규칙이 아닌 후보 간 경쟁 우선순위 규칙으로 명확히 정의
7. 선정 로그에 후보·체류·자격 여부를 추가

### 4. Jetson FP16 확정, INT8 개선 보류

**작업 내용**

**검증 결과**
- FP16은 21개 영상에서 FP32와 경고 판정·첫 경고 시점이 같았음.

| 방식 | 확인한 결과 |
|---|---|
| Entropy INT8 | 2.2ms 빨라졌지만 FP32가 확실히 잡은 박스의 25.2%를 놓침 |
| MinMax INT8 | 놓치는 비율은 2.4%로 줄었지만 박스 높이가 2px 넘게 달라지는 경우가 27~29% 남음. 속도는 아직 안 잼 |

**알게 된 점**

- 그래서 추가 검증에 시간을 쓰기보다 FP16으로 마무리하기로 함.
- TOPST에서는 그쪽 도구로 다시 비교함. 가져가는 것은 Jetson 엔진이 아니라 원본 모델·보정 이미지·기준 출력·비교 방법임.

### 5. 충돌 프레임 21개 직접 확인

**작업 내용**
- 충돌 시점이 추정값인 영상 8개와 18번(17번과 같은 값이라 다시 봄), 모두 9개를 다시 보고 확인할 장면을 영상별 시트로 만듦.

- 이 프로그램으로 21개 영상을 직접 보며 충돌 프레임을 다시 정함.
- 바뀐 값: 01 104→101, 04 111→110, 05 139→138, 11 73→74, 13 87→85, 14 84→85, 16 77→76, 19 72→69, 21 81→76.
- 02·06·08은 150프레임 안에 충돌이 없었음 → 충돌 프레임을 비워 둠.
- 02·06·08은 충돌은 없어도 충분히 가까워졌으므로 경고는 있어야 하는 영상으로 둠.
- 06번은 경고가 두 번 있어야 함 → 검은 승용차에 한 번, 갈색 SUV에 한 번.
- 바꾼 값을 `eval/videos.csv`에 반영함.

**검증 결과**

- 영상 단위 선행시간(첫 경고가 충돌보다 얼마나 먼저 떴는지): 평균 1.24초 → 1.12초, 중앙값 1.13초 → 1.03초.

**알게 된 점**
- 이제 21개 전부 직접 본 값임 → 충돌 있음 18개, 충돌 없음 3개.
- 시트에서 제안한 값과 다르게 정한 것: 08(149 → 충돌 없음), 10(109 → 107), 12(119 → 118).
- 충돌 프레임이 1~5프레임만 움직여서 판정이 바뀌는 경계를 넘은 영상이 없었음.

### 6. 영상 유형 다시 분류

**작업 내용**

### 7. 06번 두 번째 경고가 안 나온 이유 확인

**작업 내용**
- 06번의 두 차를 추적 번호로 맞춤 → 검은 승용차 2번, 갈색 SUV 6번.
- 두 차 모두에 경고가 떠야 맞은 것으로 셈.
- 앞차를 잡은 뒤 경고가 켜지기까지 몇 초가 걸려서 두 번째 경고가 안 나온 것인지 확인함.

**검증 결과**
- 앞차로 잡은 차가 이미 위험한 상태면 경고까지 3프레임(0.2초)이면 됨. 03·07·10·11·18·21번 모두 3프레임이었음.
- 기존 규칙: 검은 승용차 경고(43~58프레임)만 있고, 갈색 SUV 경고는 영상 끝까지 없음.
- `rank`: 갈색 SUV 경고가 K70 66프레임(다시 계산한 값), K400 60프레임에 뜸.

**알게 된 점**
- 경고가 늦어 보이는 건 앞차로 잡은 뒤 그 차가 위험해질 때까지 기다리는 경우임 → 06번 검은 승용차도 10프레임에 앞차가 됐지만 40프레임에 위험해졌고, 43프레임에 경고가 뜸.
- 기존 규칙은 57~72프레임에 검은 승용차와 오른쪽 옆 차를 앞차로 골랐음. 갈색 SUV는 그동안 이미 위험으로 계산되고 있었음(남은 시간 약 1.0~1.4초).
- 73프레임에 갈색 SUV가 앞차가 됐지만, 74~76프레임에 박스가 무너지고 77·78프레임에 판단 자료가 지워짐.
- 자료가 다시 쌓인 86프레임에는 박스 높이가 380px 안팎에서 그대로라 위험으로 계산되지 않았음.
- 즉 문제는 "경고까지 오래 걸림"이 아니라 "앞차를 넘겨받는 게 늦음"임 → `rank`가 고치는 자리임.
- `rank`에서는 박스가 무너지는 71프레임 전에 경고가 켜져서, 무너진 동안에도 경고가 76프레임까지 유지됨.
- 채점 프로그램(`evaluate_fcw.py`)은 06번을 첫 경고(43프레임)만 보고 OK로 셈 → 두 번째 차 문제는 충돌 대상 기준 채점에서만 보임.

### 8. 오토바이 검출 확인 (YOLO 원시 박스)

**작업 내용**
- YOLO가 낸 점수를 앱이 거르기 전에 직접 보는 프로그램(`raw_box_viewer.py`, 저장소 밖)을 만듦.
- 아래 그래프에 프레임별 최고 점수와 앱이 거르는 기준값(0.10·0.20·0.25·0.30)을 같이 그림.
- 12·13·14번 원본 영상에서 오토바이 점수를 프레임별로 봄.

**검증 결과**
- 프로그램이 앱과 같은 계산을 하는지 먼저 확인함 → 같은 YOLO 출력을 넣었을 때 최종 박스가 저장소 C++ 코드와 5개 영상 656개 전부 같았음.
- 12번: 오토바이를 잡긴 하지만 띄엄띄엄임 (0.4~0.6 점수 사이사이 0.1 아래로 떨어짐).
- 13번: 71프레임부터 거의 매 프레임 잡고, 77~80프레임은 0.5 안팎임. 먼 구간은 화면 일부를 확대해 따로 검사하는 추론(Crop)이 먼저 잡음.
- 14번: 오토바이로는 거의 못 봄(0.15 미만). 대신 배달통을 트럭(truck) 0.43으로 잡음.

**알게 된 점**
- "YOLO가 오토바이를 아예 못 잡는다"는 아니었음.
- 앱은 0.30 이상이어야 추적을 시작하고, 0.25 이상이 3프레임 연속이어야 번호를 줌. 앞차 후보가 되려면 8프레임을 더 머물러야 함.
- 12번은 검출이 끊겨서, 앱이 기다려 줘도 위험 계산에 필요한 자료 8개가 충돌(118프레임) 전에 안 모임 → 모델 쪽 문제임.
- 13번은 추적이 5프레임 늦게 시작되고 6프레임만 이어져 앞차 후보 조건(8프레임)에 걸림 → 앱 쪽 문제임.
- 13번은 82프레임부터 오토바이 대신 운전자가 사람(person)으로 잡힘.
- 14번 트럭 박스는 차량이라 경고 대상이 될 수 있음 → 몇 프레임 이어지는지는 아직 안 봄.
- 앱 조건을 풀면 정상 주행에서 잠깐 잘못 잡힌 것도 같이 통과함 → 정상 주행 영상으로 함께 봐야 함.
- 결과 영상(avi)으로는 이 확인을 못 함 → 그려진 박스·글자 때문에 13번 오토바이 점수가 0.52 → 0.00으로 떨어지고, 승용차가 버스로 잡힘. 원본 mp4로 봐야 함.
