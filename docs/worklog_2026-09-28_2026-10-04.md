### 1. 야간 INT8 실험 결과 확인

**작업 내용**
- 9/27 밤에 걸어 둔 INT8 실험 엔진 3종과 속도 측정 3세션 결과를 확인함
- 실험 엔진이 실제로 새로 만들어졌는지, calibration 이미지 250장을 정상적으로 읽었는지도 같이 확인함

**검증 결과**
- `minmax`, `shuffle` 엔진 정상 생성됨. Full·Crop 모두 calibration 250장 사용함
- 평가 영상 21개 각각 150프레임 끝까지 정상 처리됨
- `fp32head` 엔진은 빌드 실패함. 오류는 `cannot use precision Float with weights of type Int64`
- 정식 INT8 엔진 파일은 수정되지 않아 실험 엔진과 분리된 상태 유지함
- FP32 / FP16 / INT8 속도 측정 15회 모두 각 정밀도의 골든 MD5와 일치함

**알게 된 점**
- 검출 헤드를 FP32로 강제하려고 `/model.22/` 이름으로 층을 고르면 실제 연산층뿐 아니라 Reshape에 쓰는 정수 상수층까지 들어감
- 정수형 출력이나 가중치를 가진 층에는 FP32를 지정할 수 없어 TensorRT 빌드가 실패함
- 평가 결과 파일이 생겼다는 것만으로 실행 완료를 판단하면 안 됨. 영상마다 150프레임을 끝까지 처리했는지 따로 확인해야 함

### 2. FP32 / FP16 / INT8 288×640 속도 표 확정

**작업 내용**
- FP32, FP16, INT8 각 5회 측정 결과를 `analyze_runs.py`로 정리함

**검증 결과**
- 프레임 전체 처리시간 p50: FP32 31.1ms / FP16 26.1ms / INT8 23.9ms
- Full 640×640 추론: FP32 9.1ms / FP16 5.8ms / INT8 4.3ms
- Crop 288×640 추론: FP32 5.0ms / FP16 3.1ms / INT8 2.5ms
- 정밀도와 관계없이 남는 시간: 전처리 약 5.7ms + 후처리 약 5.3ms + 추적·FCW 판단 약 5.9ms = 약 17ms

**알게 된 점**
- INT8은 FP16보다 프레임당 약 2.2ms(약 8%) 빠름
- 이전에 기록한 3.6ms 차이는 1회 평균값이었고, 반복 측정 p50 기준으로는 2.2ms가 정확함
- FP16 288×640 기준 p50은 26.1ms로 확정함
- 정밀도를 더 낮춰도 약 17ms는 그대로 남음. 현재 구조에서는 GPU 추론만 더 빠르게 해도 전체 처리시간이 크게 안 줄어드는 구간에 들어감

### 3. `fp32head` 엔진 빌드 오류 수정

**작업 내용**
- 검출 헤드를 FP32로 강제할 때 정수형 출력을 가진 층까지 같이 선택돼 엔진 생성이 실패하던 문제를 고침
- 출력 텐서가 FP32·FP16 계열이 아닌 층은 FP32 강제 대상에서 제외하도록 수정함. 검출 헤드 전체(`/model.22/`)를 보호하는 범위는 그대로 둠
- 수정 후 `fp32head`, `minmax + fp32head` 엔진 2개를 다시 생성함
- `compare_precision.py`에 FP32 기준 쪽에만 confidence 조건을 거는 옵션(`--min-conf-a`)과 검출 소실 비율 열을 추가함

**검증 결과**
- 두 엔진 모두 정상 빌드됨. 헤드에서 약 70개 층을 FP32로 강제했고 정수 출력층 3개는 제외됨
- 수정한 바이너리로 정식 INT8 엔진을 실행했을 때 기존 골든과 동일함

### 4. INT8 검출 손실 원인 분석

**작업 내용**
- FP32 288×640 기준으로 INT8 엔진 5종을 박스 단위로 비교함: 정식 Entropy, MinMax, calibration 이미지 순서 섞기, Entropy + 헤드 FP32, MinMax + 헤드 FP32

**검증 결과**

| INT8 방식 | 대응된 박스 | confidence 차이 중앙값 | FP32 conf≥0.4 중 소실 | 높이 차 ±2px 이내 |
|---|---:|---:|---:|---:|
| Entropy (정식) | 6,657 | −0.170 | 25.2% | 58% |
| MinMax | 14,596 | −0.013 | 2.4% | 71% |
| Shuffle | 5,441 | −0.183 | 34.9% | 55% |
| Entropy + 헤드 FP32 | 7,095 | −0.123 | 22.8% | 59% |
| MinMax + 헤드 FP32 | 15,166 | −0.003 | 2.4% | 73% |

- 참고: FP16은 대응 박스 18,232개, 높이 차 ±2px 이내 99.7%

**알게 된 점**
- 가장 큰 원인은 Entropy calibration 방식임. MinMax로 바꾸면 confidence와 검출 개수가 FP32에 가까워짐
- calibration 이미지 순서를 섞는 것은 효과 없음
- 검출 헤드를 FP32로 강제해도 Entropy·MinMax 모두 큰 개선 없음. 검출 손실은 헤드보다 앞쪽 백본·Neck의 INT8 양자화에서 생기는 것으로 보임
- MinMax를 써도 박스 좌표는 FP16보다 흔들림. 대응된 박스 중 약 27%는 높이가 FP32와 2px 넘게 차이남
- TTC-P는 박스 높이에 민감하므로 이 좌표 차이가 실제 TTC에 영향을 주는지 추가 확인이 필요함
- TOPST 등 INT8 적용 시 Entropy는 쓰지 않고 MinMax 계열을 우선 쓰는 방향으로 정리함

### 5. LEAD 선택 실패 영상 분석

**작업 내용**
- Warning Miss 중 객체는 검출됐지만 LEAD가 제대로 선택되지 않은 영상 6개(01·08·10·11·12·14)의 원인을 Jetson 로그와 결과 영상으로 확인함
- 21개 영상 전체를 x86에서 결과 영상으로 뽑아 차선 ROI가 맞게 그려졌는지 확인함

**검증 결과**
- 10·11(컷인): 충돌 차량의 접지점이 차선 ROI 안으로 들어오는 시점은 충돌 6·15프레임 전임. 박스 자체는 25·29프레임 전부터 차선과 겹치기 시작함. 차량이 들어오는 동안 박스는 차선과 점점 많이 겹치지만 접지점은 오히려 바깥쪽에 남아 있음
- 01(눈길 대형차): f44~61에 LEAD가 잡혔고 TTC도 약 3초까지 계산됨. 이후 경고 조건과 passing-by 판단에 막혔고, 자차가 회전하면서 차량이 ROI 밖으로 빠짐
- 08(야간 정지차): 기존 ROI가 회전 이전 장면 기준이라 충돌 구간의 차선과 안 맞았음. 회전 이후 기준으로 ROI를 다시 잡자 f125~146에 LEAD가 잡히고 f145부터 DANGER가 나옴. 하지만 경고 조건을 만족한 시간이 짧아 배너 조건을 못 채움
- 21개 중 ROI 자체가 잘못된 영상은 08 하나임
- 12(주간 이륜차): 오토바이 검출이 4프레임뿐임. 14(야간 이륜차): 150프레임 동안 `motorcycle` 검출이 한 번도 없음. 코드에 motorcycle을 제외하는 클래스 필터는 없음
- x86 결과 영상에서 04·07은 보닛 반사가 차량으로 검출됨. 07에서는 이 박스가 차선 안 아래쪽에 있어 LEAD를 차지함. Jetson에서도 같은지는 추가 확인 필요

**알게 된 점**
- 박스 아래 중앙점 하나만 기준으로 LEAD 후보를 고르면 컷인 차량을 너무 늦게 잡음. 박스와 차선이 얼마나 겹치는지를 같이 봐야 함
- 이전에 생각한 "접지점이 차선 가운데 방향으로 이동해야 한다"는 조건은 맞지 않았음
- 01은 LEAD를 못 잡은 영상이 아니라 이후 경고 조건 때문에 경고가 안 나온 영상임. 08은 ROI 문제와 경고 조건 문제가 같이 있었음
- 01·08은 화면 세로 60% 아래에 있어야 경고할 수 있는 조건과 DANGER 연속 조건의 영향을 크게 받음. 큰 차량은 이미 충분히 가까운데도 접지점 위치 때문에 경고가 막힐 수 있음
- 11처럼 추적이 1~2프레임 끊겼다가 다시 잡히면 LEAD 체류 카운터가 초기화됨. 컷인처럼 시간이 짧은 상황에서는 이 초기화가 경고 지연에 크게 영향을 줌
- 12·14는 LEAD 규칙이 아니라 검출 문제임. 뒤에서 본 배달 오토바이와 역광 이륜차를 COCO 기반 YOLOv8n이 못 잡아서 모델 fine-tuning 없이는 해결이 어려움

### 6. 평가 라벨 기준 수정

- 이 영상들은 위험하지 않은 장면이 아니라 현재 구현이 처리하지 못하는 위험 장면이므로 09·13·16·17·18·19·21을 경고 대상(`should_warn=1`)으로 다시 정의함

- 9/24~9/27에 기록한 Miss / False Alarm 수치는 이전 라벨 기준임. 라벨 변경 후에는 평가 결과를 다시 계산해야 함
- 비경고 영상이 2개뿐이라 현재 평가셋만으로는 False Alarm 성능을 제대로 평가할 수 없음. 별도의 정상주행 음성 영상이 필요함

### 7. 현재 규칙으로 처리하기 어려운 장면 확인

**작업 내용**
- 횡단·맞은편 차량 영상(09·13·16·17·18)이 현재 구조로 경고가 가능한지 확인함

**알게 된 점**
- 차량이 차선 ROI에 들어온 뒤 현재 경고 조건(LEAD 체류 → TTC 샘플 → DANGER 연속 확인)을 모두 통과하기까지 최소 약 15프레임이 필요함
- 횡단·맞은편 차량은 충돌까지 남은 시간이 짧아 이 구조로는 제때 경고하기 어려움
- 별도의 빠른 경고 경로가 필요한 유형으로 판단함. 현재 일정에서는 추가하지 않고 별도 개선 항목으로 남김

### 8. 오늘 결론

**알게 된 점**
- INT8 검출 손실의 주요 원인은 Entropy calibration 방식임. MinMax로 바꾸자 confidence와 검출 개수가 크게 회복됐고, 검출 헤드를 FP32로 보호하는 것보다 효과가 훨씬 컸음. MinMax에서도 박스 좌표 흔들림은 남아 있어 TTC-P에 실제 영향을 주는지는 추가 확인이 필요함
- FCW Warning Miss의 원인은 한 가지가 아니라 여러 종류로 나뉨. 컷인은 접지점 기반 LEAD 규칙 문제, 01·08은 경고 게이트와 연속 조건 문제, 12·14는 YOLO 검출 실패, 횡단·맞은편은 현재 구조의 반응 시간 문제임
- 이후에는 모든 Miss를 하나의 규칙으로 해결하려 하지 않고 원인별로 분리해 수정하기로 함
