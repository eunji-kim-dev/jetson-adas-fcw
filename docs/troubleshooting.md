# Troubleshooting

Step 6(multi-object tracking) 진행하면서 만난 문제들 기록. 시간순으로 정리했고, 7번은 아직 완전히 못 풀고 한계로 남겨둠.

---

## 1. ROI 안쪽 차량이 오히려 안 잡히는 문제

바깥쪽 차선의 차량은 잘 잡히는데 정작 주행 중인 ROI 안쪽 정면 차량이 자주 빠졌다. 처음엔 YOLO 모델 자체 문제인가 싶어서 confidence threshold부터 만졌는데 별 차이가 없었다.

원인은 코드 순서였다. 원본 프레임에 반투명 초록색으로 ROI를 먼저 칠하고, 그 프레임을 그대로 YOLO에 넣고 있었다. 즉 모델이 보는 이미지 자체가 이미 오염된 상태였던 것. ROI 밖 차량은 원본 색을 유지하니 상대적으로 더 잘 잡히고, ROI 안쪽은 픽셀 값이 달라져서 검출이 흔들렸다.

검출과 시각화 순서를 뒤집었다.

```cpp
detections = detectObjects(
    net,
    frame,
    detectorThreshold,
    nmsThreshold
);

// 검출이 끝난 뒤에만 ROI를 그린다
cv::Mat overlay = frame.clone();

cv::fillConvexPoly(
    overlay,
    drivingRoi,
    cv::Scalar(0, 255, 0)
);
```

수정 후 다시 돌려보니 ROI 안쪽 정면 차량과 바깥쪽 차량이 모두 잡혔다. 시각화용으로 넣은 오버레이가 검출 입력 자체를 건드리고 있었다는 게 핵심이고, 이후로는 원본 프레임과 화면 출력용 프레임을 아예 분리해서 관리한다.

## 2. 멀리 있는 차량이 잘 안 잡히는 문제

가까이 있는 큰 차량은 문제없는데, 화면 저 끝에서 작게 보이는 원거리 차량은 프레임마다 잡혔다 안 잡혔다 했다.

confidence threshold가 0.40으로 걸려 있었는데, 원거리 차량은 픽셀 수 자체가 적어서 YOLO가 뽑는 confidence 값도 낮게 나온다. 그러니 0.40 기준에 걸려서 목록에서 잘려나갔다.

일단 threshold를 낮췄다.

```cpp
constexpr float confidenceThreshold = 0.25F;
```

그런데 이러면 애매한 것들이 남는다. 그래서 YOLO 자체 검출 하한선을 0.10까지 열어두고, 등급은 추적기 안에서 나누는 쪽으로 바꿨다.

```cpp
constexpr float detectorThreshold = 0.10F;
```

- 0.25 이상: 고신뢰도. 기존 Track 매칭에도 쓰고 새 Track도 만든다.
- 0.10~0.25: 저신뢰도. 기존 Track을 이어주는 용도로만 쓴다.

낮은 confidence를 그대로 신뢰해서 새 ID를 만들면 오검출이 새 차량으로 둔갑할 수 있어서, 저신뢰도 쪽에는 신규 생성 권한을 주지 않았다. 이후로 예전에 누락되던 작은 원거리 차량들이 눈에 띄게 더 자주 잡혔다.

## 3. 같은 차량인데 ID가 프레임마다 바뀌는 문제

정면 차량 하나가 `ID:1` → `ID:8` → `ID:13` 식으로 몇 초 사이에 계속 새 번호를 받았다. 특히 거리가 있는 차량일수록 심했다.

**IoU 게이트가 너무 빡빡했다**

기존 추적기는 이전 Track의 예측 박스와 이번 프레임 Detection의 IoU만 보고 동일 객체인지 판단했다. 원거리 차량은 박스 자체가 작아서 몇 픽셀만 움직여도 IoU가 확 떨어진다.

거기다 새로 생긴 Track은 속도 정보가 전부 0으로 시작한다(x/y속도, 너비/높이 변화속도). Kalman Filter가 다음 프레임 위치를 사실상 제자리로 예측하는 셈인데, 실제 차량은 카메라 상대 움직임 때문에 다음 프레임에 이미 수십 픽셀 이동해 있다.

```text
새 Track 생성 → 속도 없음 → 제자리로 예측 → 실제는 이미 이동 → 매칭 실패 → 속도 학습 기회 상실 → 또 새 Track
```

속도를 배우려면 최소 2~3프레임은 이어붙어야 하는데, 매칭 조건 자체가 "이미 정확한 속도를 안다"는 전제로 너무 타이트하게 짜여 있었다.

**거리 게이트도 따로 놀았다**

IoU를 통과해도 중심점 거리 조건이 독립적으로 다시 걸러냈다.

```cpp
if (
    centerDistance >
    allowedDistance * 1.25F
) {
    continue;
}
```

허용 거리 상한도 100px로 막혀 있어서, 화면 가까이서 빠르게 움직이는 큰 차량이 이 조건에 자주 걸렸다.

**고친 부분**

1. IoU가 충분하면 거리 조건이 다시 탈락시키지 않도록 순서를 바꿨다. 거리는 IoU가 애매할 때만 보조로 쓴다.
2. 갓 생긴 Track(hits 적은 것)은 완화된 거리·면적 조건을 쓰게 했다. 2~3프레임은 좀 널널하게 봐줘야 Kalman Filter가 속도를 배울 시간이 생긴다.
3. 허용 이동 거리 계산식을 바꿨다.

```cpp
return std::clamp(
    largestDiagonal * 0.85F + 8.0F,
    16.0F,
    320.0F
);
```

박스가 클수록 더 크게 움직여도 봐주되, 다른 차량과 엉키지 않게 상한(320px)은 남겨뒀다.

4. Kalman Filter 상태를 6개(중심 x/y, x/y속도, 너비, 높이)에서 8개로 늘려서 너비·높이 변화속도도 추적하게 했다. 차량이 가까워지거나 멀어질 때 박스 크기가 변하는 것도 예측에 반영하기 위해서다.

다시 돌려보니 같은 차량에 매 프레임 새 ID가 붙는 현상은 없어졌고, 정면·측면 차량 모두 몇 초씩 같은 ID를 유지했다.

## 4. 예전에 놓친 ID가 지금 차량을 가로채는 문제

`ID 1 → ID 17 → ID 23`까지 바뀌었다가, 어느 순간 다시 `ID 17`이 튀어나오는 경우가 있었다.

YOLO가 잠깐 놓쳐도 기존 Track은 몇 프레임 동안 리스트에 남아있는 구조였는데, 문제는 "방금까지 잘 이어지던 Track"과 "몇 프레임째 안 잡히고 있는 오래된 Track"이 똑같은 우선순위로 이번 프레임 Detection을 두고 경쟁했다는 점이다. 오래된 Track의 예측 위치가 우연히 지금 차량 근처로 오면, 정상적으로 이어지던 ID 대신 죽어가던 옛날 ID가 낚아채갔다.

매칭을 단계별로 나눴다.

- **1차**: 직전 프레임까지 멀쩡히 이어진 Track + 고신뢰도 Detection. 제일 믿을 만한 조합부터 먼저 붙인다.
- **2차**: 1차에서 떨어진 최근 Track + 저신뢰도 Detection. 신뢰도가 잠깐 낮아진 것뿐인 차량이 ID를 잃지 않게 하는 용도. 여기서는 저신뢰도로 새 Track을 만들지 않는다.
- **3차**: 여러 프레임 놓친 Track은, 1·2차가 다 끝나고 남은 고신뢰도 Detection에만 붙는다. 놓친 프레임 수만큼 매칭 비용에 페널티를 줬다.

그 외에: 아직 확정 안 된 Track에도 저신뢰도로 재시도할 기회를 주고, 놓친 Track이 복구될 수 있는 프레임 수에 제한을 두고, 박스 면적이 갑자기 너무 크게 바뀌면 다른 객체로 간주하고, 같은 클래스면 매칭에 약간 가산점을 주고, 오래 놓친 Track일수록 매칭 비용을 더 얹었다.

이후로는 정상적으로 이어지던 ID가 과거 ID한테 뺏기는 경우가 눈에 띄게 줄었다.

## 5. 같은 차량에 car 박스랑 truck 박스가 동시에 뜨는 문제

YOLO가 같은 차량을 `car`로도 `truck`으로도 동시에 인식해버리면 박스 두 개, Track 두 개가 따로 생길 수 있었다.

원인은 NMS를 클래스별로 따로 돌리고 있었다는 것 — car는 car끼리, truck은 truck끼리. 같은 차량 위에 car 박스와 truck 박스가 같이 남아도 서로 다른 클래스라서 NMS가 중복으로 안 봤다. 그런데 정작 추적기 쪽에서는 car/bus/truck을 전부 "사륜차"로 묶어서 처리하고 있었으니, 검출 단계와 추적 단계의 클래스 기준이 서로 안 맞았던 셈.

그래서 NMS도 추적기 기준에 맞춰 그룹으로 묶었다.

- 사륜차: car, bus, truck
- 이륜차: bicycle, motorcycle
- 보행자: person

그룹별로 `NMSBoxes()`를 따로 돌려서, 겹치는 박스 중 confidence가 제일 높은 것만 남기게 했다. 이후로 같은 차량이 서로 다른 클래스로 중복 검출돼서 별도 Track이 생기는 경우가 줄었다.

## 6. confidence가 잠깐 낮아지기만 해도 ID가 끊기는 문제

같은 차량인데 confidence가 `0.41 → 0.28 → 0.18 → 0.33`처럼 프레임마다 출렁였다. 기준을 0.25로 잡아두면 0.18이 나온 프레임에서는 그 차량이 Detection 목록에서 통째로 빠진다. 이게 몇 프레임 반복되면 Track이 삭제되고, 다시 잡혔을 때는 새 ID가 나갔다.

ByteTrack 방식을 참고해서 Detection을 두 등급으로 나눴다.

- 고신뢰도: 기존 Track 매칭 1순위, 신규 Track 생성도 가능
- 저신뢰도: 1차 매칭에서 떨어진 기존 Track하고만 재매칭, 신규 생성은 불가

```cpp
MultiObjectTracker tracker(
    0.25F,  // 고신뢰도 기준
    0.10F,  // 저신뢰도 최저 기준
    3,      // ID 확정에 필요한 매칭 횟수
    20      // 확정 Track 보관 프레임
);
```

새 Track이 바로 정식 ID를 받지 않고 몇 번은 이어져야 확정되게 해서, 순간적인 오검출 하나 때문에 새 ID가 튀어나오는 것도 줄였다. 결과적으로 confidence가 잠깐 흔들려도 Track이 끊기지 않고, 불필요한 신규 ID 발급도 줄었다.

## 7. 오래 놓치면 결국 새 ID가 나가는 문제 (한계로 남김)

역광이 심하거나, 차량이 너무 멀어서 작거나, 다른 차에 가려서 YOLO가 한동안 아예 못 잡는 구간이 있으면 — 다시 나타났을 때 새 ID가 발급된다.

지금 추적기는 박스 위치, 중심점 이동, 크기 변화, Kalman Filter 예측, 클래스만 보고 판단한다. 확정 Track은 최대 20프레임까지 들고 있는데, 30FPS 기준이면 대략 0.67초다(20/30). 그보다 오래 놓치면 Track이 지워지고, 다시 나타나도 이전 차량과 같은 차인지 확인할 방법이 없다 — 색이나 외형을 전혀 비교하지 않기 때문이다.

보관 프레임 수를 무작정 늘리는 것도 답은 아니다. 그러면 이번엔 엉뚱한 다른 차량한테 오래된 ID가 붙을 위험이 커진다. 그래서 `maxMissedFrames`는 건드리지 않기로 했다.

진짜로 풀려면 외형 특징 비교, Re-ID, 카메라 움직임 보정, 전역 모션 추정 같은 게 필요한데, 이번 단계(Step 6) 목표는 "연속으로 잡히는 동안 ID를 안정적으로 유지하는 것"까지였고, 장시간 재식별은 다음 과제로 넘겼다.

---

## Step 6 정리

이번 단계에서 구현한 파이프라인: YOLOv8 ONNX 검출 → 고/저신뢰도 분리 → 차량 그룹 단위 NMS → Kalman Filter로 위치·크기 예측 → 초기 Track 완화 매칭 → 고신뢰도 1차 매칭 → 저신뢰도 2차 매칭 → 놓친 Track 복구 매칭 → 일정 횟수 이어진 Track에만 ID 확정 → ROI 내부 판정 → 결과 저장.

동일 차량에 매 프레임 새 ID가 붙던 현상은 사라졌고, 연속으로 잡히는 정면·측면 차량은 몇 초씩 같은 ID를 유지한다. 다만 Track 보관 시간보다 오래 검출이 끊기면 여전히 새 ID가 나간다 — 위치·크기 기반 추적의 구조적 한계이고, 장시간 재식별은 이후 과제로 남긴다.
