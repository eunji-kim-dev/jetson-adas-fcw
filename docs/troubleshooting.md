# Troubleshooting

Step 6(다중 객체 추적)과 Step 7(TTC-P 기반 위험 분석)을 진행하면서 부딪힌 문제들을 시간순으로 남긴다. 7번과 15번은 지금 구조에서는 어쩔 수 없는 한계로 남겨뒀다.

## 1. ROI 안쪽 차량이 오히려 안 잡힘

이상하게 바깥쪽 차선 차량은 잘 잡히는데, 정작 지금 달리고 있는 ROI 안쪽 정면 차량이 자꾸 빠졌다. 처음엔 당연히 YOLO 모델 문제라고 생각해서 confidence threshold부터 만졌는데 별 차이가 없었다.

한참 뒤에야 코드 순서가 문제라는 걸 알았다. 원본 프레임에 반투명 초록색으로 ROI를 먼저 칠하고, 그 프레임을 그대로 YOLO에 넣고 있었다. 모델이 보는 이미지 자체가 이미 오염돼 있었던 것이다. ROI 밖 차량은 원본 색을 유지하니 상대적으로 더 잘 잡히고, 안쪽은 픽셀 값이 달라져서 검출이 흔들렸던 거다.

검출과 시각화 순서를 뒤집었다.

```cpp
detections = detectObjects(
    net,
    frame,
    detectorThreshold,
    nmsThreshold
);

// 검출이 끝난 뒤에만 ROI를 그린다
cv::Mat overlay = frame.clone();

cv::fillConvexPoly(
    overlay,
    drivingRoi,
    cv::Scalar(0, 255, 0)
);
```

다시 돌려보니 안쪽 정면 차량과 바깥쪽 차량이 다 잡혔다. 시각화용으로 넣은 오버레이가 검출 입력 자체를 건드리고 있었던 게 핵심이었고, 그 뒤로는 원본 프레임과 화면 출력용 프레임을 아예 분리해서 관리하기로 했다.

## 2. 멀리 있는 차량이 잘 안 잡힘

가까이 있는 큰 차량은 문제없는데, 화면 저 끝에서 작게 보이는 원거리 차량은 프레임마다 잡혔다 안 잡혔다 했다.

confidence threshold가 0.40으로 걸려 있었는데, 원거리 차량은 픽셀 수 자체가 적으니 YOLO가 뽑는 confidence도 낮게 나온다. 그러니 0.40 기준에서 매번 잘려나간 거였다.

일단 threshold를 낮췄다.

```cpp
constexpr float confidenceThreshold = 0.25F;
```

근데 이러면 애매한 것들이 같이 남는다. 그래서 YOLO 자체 검출 하한선은 0.10까지 열어두고, 등급 나누는 건 추적기 쪽으로 넘겼다.

```cpp
constexpr float detectorThreshold = 0.10F;
```

- 0.25 이상: 고신뢰도. 기존 Track 매칭에도 쓰고 새 Track도 만든다.
- 0.10~0.25: 저신뢰도. 기존 Track을 이어주는 용도로만 쓴다.

낮은 confidence를 곧이곧대로 믿고 새 ID를 만들면 오검출이 새 차량으로 둔갑할 수 있어서, 저신뢰도 쪽에는 신규 생성 권한을 안 줬다. 그랬더니 예전엔 놓치던 작은 원거리 차량들이 눈에 띄게 자주 잡히기 시작했다.

## 3. 같은 차량인데 ID가 프레임마다 바뀜

정면 차량 하나가 ID:1 → ID:8 → ID:13 식으로 몇 초 사이에 계속 새 번호를 받았다. 거리가 있는 차량일수록 특히 심했다.

**IoU 게이트가 너무 빡빡했다.** 기존 추적기는 이전 Track의 예측 박스와 이번 프레임 Detection의 IoU만 보고 동일 객체인지 판단했는데, 원거리 차량은 박스 자체가 작아서 몇 픽셀만 움직여도 IoU가 확 떨어진다.

거기다 더 근본적인 문제가 있었다. 새로 생긴 Track은 속도 정보(x/y속도, 너비/높이 변화속도)가 전부 0으로 시작한다. Kalman Filter가 다음 프레임 위치를 사실상 제자리로 예측하는 셈인데, 실제 차량은 카메라 상대 움직임 때문에 다음 프레임에 이미 수십 픽셀 이동해 있다. 그러니 이런 악순환이 생긴다.

새 Track 생성 → 속도 없음 → 제자리로 예측 → 실제는 이미 이동 → 매칭 실패 → 속도 학습 기회 상실 → 또 새 Track

속도를 배우려면 최소 2~3프레임은 이어붙어야 하는데, 매칭 조건 자체가 "이미 정확한 속도를 안다"는 전제로 너무 타이트하게 짜여 있었던 셈이다.

**거리 게이트도 따로 놀았다.** IoU를 통과해도 중심점 거리 조건이 독립적으로 다시 걸러냈다.

```cpp
if (
    centerDistance >
    allowedDistance * 1.25F
) {
    continue;
}
```

허용 거리 상한도 100px로 막혀 있어서, 화면 가까이서 빠르게 움직이는 큰 차량이 여기 자주 걸렸다.

고친 부분은 이랬다.

- IoU가 충분하면 거리 조건이 다시 탈락시키지 않도록 순서를 바꿨다. 거리는 IoU가 애매할 때만 보조로 쓴다.
- 갓 생긴 Track(hits 적은 것)은 완화된 거리·면적 조건을 쓰게 했다. 2~3프레임은 좀 널널하게 봐줘야 Kalman Filter가 속도를 배울 시간이 생긴다.
- 허용 이동 거리 계산식을 바꿨다.

```cpp
return std::clamp(
    largestDiagonal * 0.85F + 8.0F,
    16.0F,
    320.0F
);
```

박스가 클수록 더 크게 움직여도 봐주되, 다른 차량과 엉키지 않게 상한(320px)은 남겨뒀다.

- Kalman Filter 상태를 6개(중심 x/y, x/y속도, 너비, 높이)에서 8개로 늘려서 너비·높이 변화속도도 추적하게 했다. 차량이 가까워지거나 멀어질 때 박스 크기가 변하는 것도 예측에 반영하려고 넣었다.

다시 돌려보니 같은 차량에 매 프레임 새 ID가 붙는 현상은 사라졌고, 정면·측면 차량 모두 몇 초씩 같은 ID를 유지했다.

## 4. 예전에 놓친 ID가 지금 차량을 가로챔

ID 1 → ID 17 → ID 23까지 바뀌었다가, 어느 순간 다시 ID 17이 튀어나오는 일이 있었다.

YOLO가 잠깐 놓쳐도 기존 Track은 몇 프레임 동안 리스트에 남아있는 구조였다. 문제는 "방금까지 잘 이어지던 Track"과 "몇 프레임째 안 잡히고 있는 오래된 Track"이 똑같은 우선순위로 이번 프레임 Detection을 두고 경쟁했다는 점이다. 오래된 Track의 예측 위치가 우연히 지금 차량 근처로 오면, 정상적으로 이어지던 ID 대신 죽어가던 옛날 ID가 낚아채가는 식이었다.

그래서 매칭을 단계별로 나눴다.

1. **1차**: 직전 프레임까지 멀쩡히 이어진 Track + 고신뢰도 Detection. 제일 믿을 만한 조합부터 먼저 붙인다.
2. **2차**: 1차에서 떨어진 최근 Track + 저신뢰도 Detection. 신뢰도가 잠깐 낮아진 것뿐인 차량이 ID를 잃지 않게 하는 용도다. 여기선 저신뢰도로 새 Track을 만들지 않는다.
3. **3차**: 여러 프레임 놓친 Track은, 1·2차가 다 끝나고 남은 고신뢰도 Detection에만 붙는다. 놓친 프레임 수만큼 매칭 비용에 페널티를 줬다.

그 외에도 몇 가지를 더 손봤다. 아직 확정 안 된 Track에도 저신뢰도로 재시도할 기회를 줬고, 놓친 Track이 복구될 수 있는 프레임 수에 제한을 뒀고, 박스 면적이 갑자기 너무 크게 바뀌면 다른 객체로 간주하게 했다. 같은 클래스면 매칭에 약간 가산점을 주고, 오래 놓친 Track일수록 매칭 비용을 더 얹었다.

이후로는 정상적으로 이어지던 ID가 과거 ID한테 뺏기는 경우가 눈에 띄게 줄었다.

## 5. 같은 차량에 car 박스랑 truck 박스가 동시에 뜸

YOLO가 같은 차량을 car로도 truck으로도 동시에 인식해버리면 박스 두 개, Track 두 개가 따로 생길 수 있었다.

원인은 NMS를 클래스별로 따로 돌리고 있었다는 것. car는 car끼리, truck은 truck끼리만 비교하니, 같은 차량 위에 car 박스와 truck 박스가 같이 남아도 서로 다른 클래스라서 NMS는 중복으로 안 봤다. 그런데 정작 추적기 쪽에서는 car/bus/truck을 전부 "사륜차"로 묶어서 처리하고 있었으니, 검출 단계와 추적 단계의 클래스 기준이 서로 안 맞았던 셈이다.

그래서 NMS도 추적기 기준에 맞춰 그룹으로 묶었다.

- 사륜차: car, bus, truck
- 이륜차: bicycle, motorcycle
- 보행자: person

그룹별로 `NMSBoxes()`를 따로 돌려서, 겹치는 박스 중 confidence가 제일 높은 것만 남기게 했다. 이후로 같은 차량이 서로 다른 클래스로 중복 검출돼서 별도 Track이 생기는 경우가 줄었다.

## 6. confidence가 잠깐 낮아지기만 해도 ID가 끊김

같은 차량인데 confidence가 0.41 → 0.28 → 0.18 → 0.33처럼 프레임마다 출렁였다. 기준을 0.25로 잡아두면 0.18이 나온 프레임에서는 그 차량이 Detection 목록에서 통째로 빠진다. 이게 몇 프레임 반복되면 Track이 삭제되고, 다시 잡혔을 때는 새 ID가 나갔다.

ByteTrack 방식을 참고해서 Detection을 두 등급으로 나눴다.

- 고신뢰도: 기존 Track 매칭 1순위, 신규 Track 생성도 가능
- 저신뢰도: 1차 매칭에서 떨어진 기존 Track하고만 재매칭, 신규 생성은 불가

```cpp
MultiObjectTracker tracker(
    0.25F,  // 고신뢰도 기준
    0.10F,  // 저신뢰도 최저 기준
    3,      // ID 확정에 필요한 매칭 횟수
    20      // 확정 Track 보관 프레임
);
```

새 Track이 바로 정식 ID를 받지 않고 몇 번은 이어져야 확정되게 해서, 순간적인 오검출 하나 때문에 새 ID가 튀어나오는 것도 줄였다. 결과적으로 confidence가 잠깐 흔들려도 Track이 끊기지 않고, 불필요한 신규 ID 발급도 줄었다.

## 7. 오래 놓치면 결국 새 ID가 나감 (한계로 남김)

역광이 심하거나, 차량이 너무 멀어서 작거나, 다른 차에 가려서 YOLO가 한동안 아예 못 잡는 구간이 있으면, 다시 나타났을 때 새 ID가 발급된다.

지금 추적기는 박스 위치, 중심점 이동, 크기 변화, Kalman Filter 예측, 클래스만 보고 판단한다. 확정 Track은 최대 20프레임까지 들고 있는데, 30FPS 기준이면 대략 0.67초(20/30)다. 그보다 오래 놓치면 Track이 지워지고, 다시 나타나도 이전 차량과 같은 차인지 확인할 방법이 없다 — 색이나 외형을 전혀 비교하지 않기 때문이다.

보관 프레임 수를 무작정 늘리는 것도 답은 아니다. 그러면 이번엔 엉뚱한 다른 차량한테 오래된 ID가 붙을 위험이 커진다. 그래서 `maxMissedFrames`는 건드리지 않기로 했다.

진짜로 풀려면 외형 특징 비교, Re-ID, 카메라 움직임 보정, 전역 모션 추정 같은 게 필요하다. 다만 이번 단계(Step 6)의 목표는 "연속으로 잡히는 동안 ID를 안정적으로 유지하는 것"까지였고, 장시간 재식별은 다음 과제로 넘겼다.

### Step 6 정리

이번 단계에서 구현한 파이프라인은 다음과 같다.

```
YOLOv8 ONNX 검출
→ 고/저신뢰도 분리
→ 차량 그룹 단위 NMS
→ Kalman Filter로 위치·크기 예측
→ 초기 Track 완화 매칭
→ 고신뢰도 1차 매칭
→ 저신뢰도 2차 매칭
→ 놓친 Track 복구 매칭
→ 일정 횟수 이어진 Track에만 ID 확정
→ ROI 내부 판정
→ 결과 저장
```

동일 차량에 매 프레임 새 ID가 붙던 현상은 사라졌고, 연속으로 잡히는 정면·측면 차량은 몇 초씩 같은 ID를 유지한다. 다만 Track 보관 시간보다 오래 검출이 끊기면 여전히 새 ID가 나간다. 위치·크기 기반 추적의 구조적 한계이고, 장시간 재식별은 이후 과제로 남긴다.

# Step 7 — TTC-P 기반 선행 차량 위험 분석

## 8. ROI 안의 모든 차량을 위험 대상으로 보면서 오경고 발생

초기 위험 분석은 ROI 안에 들어온 모든 차량의 박스 크기와 위치 변화를 계산했다. 그런데 이 영상은 고정 CCTV가 아니라 이동 중인 블랙박스 영상이라, 화면 속 차량 크기 변화에는 상대 차량의 움직임뿐 아니라 내 차량과 카메라의 움직임도 함께 섞인다.

특히 옆 차선 차량이 화면 가까이 크게 지나갈 때, 실제 충돌 위험과 관계없이 박스 면적이 빠르게 커져 CAUTION이나 DANGER가 뜰 수 있었다.

고정 카메라를 전제로 한 화면 좌표 기반 거리나 단순 Homography 방식은 이 입력 영상에 안 맞았다. 그래서 위험 분석 대상을 ROI 안의 모든 차량이 아니라 현재 내 차선의 선행 차량 한 대로 제한하기로 했다.

처리 순서는 다음과 같다.

```
검출·추적된 차량
→ 차량 하단 중앙점 계산
→ ego lane ROI 내부 여부 확인
→ 화면 중앙과의 거리, 하단 위치를 이용해 선행 차량 후보 점수 계산
→ 가장 적합한 차량 한 대를 LEAD로 선택
→ 해당 차량에 대해서만 TTC-P 계산
```

선행 차량이 프레임마다 바뀌는 것을 줄이기 위해 기존 `activeLeadId`를 바로 교체하지 않고, 새로운 후보의 점수가 일정 수준 이상 더 좋을 때만 교체하는 히스테리시스도 추가했다.

수정 후 옆 차선에서 크게 지나가는 트럭은 SIDE로 표시되고, 실제 중앙 선행 차량만 위험 분석 대상으로 남았다.

## 9. 실제 거리가 없는데 TTC를 어떻게 계산할지

단안 블랙박스 영상만으로는 차량의 실제 거리와 실제 상대속도를 바로 알 수 없다. 카메라 내부 파라미터, 차량 실제 크기, 도로 기하 정보가 없기 때문에, 초 단위의 정확한 TTC라고 주장하면 안 된다고 생각했다.

그래서 결과 이름을 **TTC-P(TTC Proxy)**로 명확히 구분했다.

선행 차량의 바운딩 박스 높이가 시간에 따라 얼마나 빠르게 증가하는지를 이용했다.

```
차량이 가까워짐
→ 영상에서 박스 높이가 증가
→ log(박스 높이)의 증가율 계산
→ 증가율이 클수록 TTC-P가 작아짐
```

단순히 첫 프레임과 마지막 프레임만 비교하면 검출 박스가 한 번 흔들렸을 때 결과가 크게 튀기 때문에, 최근 여러 프레임의 log(boxHeight)에 선형회귀를 적용했다. 박스 하단 중앙점의 y축 이동 속도도 함께 계산해서, 실제로 차량이 화면 아래쪽으로 접근하고 있는지 보조 지표로 썼다.

TTC-P는 실제 거리 기반 충돌 시간의 대체값이 아니라, 영상 스케일 변화 기반 접근 위험 지표로 정의했다.

## 10. 경고 단계는 유지되는데 화면의 TTC-P 숫자는 계속 바뀜

경고 깜빡임을 막기 위해 CAUTION이나 DANGER 상태를 일정 시간 유지하도록 했는데, 상단 경고 문구에는 매 프레임 새로 계산된 TTC-P 숫자를 붙이고 있었다.

그래서 다음처럼 모순되어 보이는 장면이 생겼다.

```
이전 프레임: TTC-P 4.0초 → CAUTION 확정
다음 프레임: TTC-P 17.5초 → 안정화를 위해 CAUTION은 잠시 유지
화면 표시: CAUTION: CLOSING LEAD 17.5s
```

위험 단계 유지 자체는 의도한 동작이지만, 유지 중인 경고 단계와 현재 프레임 TTC-P를 한 문장에 넣은 게 문제였다.

상단 경고 배너에서는 숫자를 뺐다.

```
CAUTION: CLOSING LEAD
DANGER: LOW TTC-P
```

현재 TTC-P 숫자는 선행 차량 라벨과 왼쪽 상태창에서만 보이도록 역할을 분리했다. 그 뒤로는 상단 경고와 TTC-P 수치가 서로 모순되어 보이는 현상이 사라졌다.

## 11. 오른쪽 탱크로리가 19초부터 보이는데 22초가 지나야 잡힘

화면 오른쪽에서 탱크로리가 들어오는데, 차체가 이미 보이는 19초대부터는 박스가 없고 약 22초 이후에야 truck으로 잡혔다.

처음엔 전체 프레임을 640×640으로 줄이면서 부분 노출된 트럭이 너무 작아진 게 원인이라고 생각했다. 그래서 우측 영역을 Crop해 확대 추론하는 방식도 시험해봤는데, 추론 시간만 늘고 검출 시점은 거의 개선되지 않았다.

여기서 추측으로 계속 수정하는 대신, 18~24초 구간의 필터링 전 YOLO 원시 후보를 CSV로 기록해보기로 했다.

기록 항목:
- frame, time
- 상위 1·2·3순위 클래스와 점수
- car, bus, train, truck, boat 점수
- 박스 위치와 크기
- confidence 통과 여부
- ADAS 대상 클래스 통과 여부
- 최종 필터 통과 여부

진단 결과, 문제의 큰 박스는 21.9초부터 이미 생성되고 있었다.

```
21.922초  train 0.768 / truck 0.012
21.989초  train 0.886 / truck 0.002
22.055초  train 0.904 / truck 0.001
22.122초  train 0.914 / truck 0.000
22.289초  truck 0.607로 전환
```

즉 위치를 못 찾은 게 아니었다. 탱크로리 후면의 둥근 형태를 train(6)으로 강하게 오분류하고 있었고, `isTargetClass()` 필터가 train을 제거하면서 화면에 표시되지 않았던 것이다.

```
실제 탱크로리
→ YOLO 박스 생성
→ 최고 클래스 train
→ ADAS 대상 클래스 아님
→ Detection 삭제
→ Tracker에 전달되지 않음
```

모든 train을 truck으로 바꾸면 다른 장면의 오검출까지 차량으로 받아들일 수 있으니, 다음 조건을 모두 만족하는 후보만 제한적으로 복구하기로 했다.

- 원래 최고 클래스가 train(6)
- 신뢰도 0.25 이상
- 화면 오른쪽에 위치
- 박스가 충분히 큼
- 박스 하단이 도로 영역까지 내려옴

조건을 만족하면 truck(7)으로 재해석한 뒤 기존 차량 그룹 NMS와 Tracker에 전달했다. 이번 문제를 통해 threshold만 낮추기 전에 모델의 원시 출력과 필터링 과정을 먼저 확인해야 한다는 걸 다시 확인했다.

## 12. 원인 분석용 표시가 최종 영상에 남음

탱크로리 오분류를 확인하려고 18~24초 구간에 우측 진단 영역과 원시 후보를 표시했다. 원시 클래스가 train이면 자홍색 박스와 텍스트를 출력하도록 만들었는데, 진단이 끝난 뒤에도 같은 코드로 결과 영상을 생성하면서 핑크색 영역과 TRAIN 글씨가 최종 영상에 그대로 남았다.

진단용 출력과 실제 결과 영상의 역할을 분리했다.

- 진단 버전: 원시 클래스, 후보 점수, 필터 통과 여부, CSV 저장
- 최종 버전: 확정된 Detection과 Track만 표시

진단용 핑크색 ROI, 원시 후보 텍스트, CSV 출력 코드는 제거했다. 객체 클래스명은 car, truck, person처럼 영어를 유지하고, 왼쪽 상태 정보와 상단 경고는 한국어로 바꿨다. 화면 왼쪽 아래 설명 문구도 지웠다.

디버깅 정보는 문제를 찾는 동안에는 유용하지만, 포트폴리오 결과물에는 필요한 정보만 남겨야 한다는 걸 새삼 느꼈다.

## 13. 멀리 있는 작은 차량의 박스 흔들림을 접근으로 오판

약 15초 구간에서 실제로 급접근하는 차량이 없는데도 CAUTION 경고가 잠깐 떴다.

원인은 멀리 있는 작은 선행 차량의 박스였다. 차량 높이가 작을 때는 검출 박스가 2~3픽셀만 변해도 비율상 큰 증가로 계산된다. TTC-P는 박스 높이 증가율을 쓰기 때문에, 이런 검출 흔들림이 급격한 접근처럼 보였던 거다.

단순 TTC-P 임계값 외에 경고 신뢰성 조건을 추가했다.

- TTC-P 계산이 유효할 것
- 관찰 샘플이 충분할 것
- 선행 차량 박스 높이가 일정 이상일 것
- 차량 하단점이 화면에서 충분히 가까운 위치일 것
- 전체 관찰 구간에서 박스 높이가 의미 있게 증가할 것
- 하단점도 화면 아래 방향으로 이동할 것

조건을 통과하지 못한 CAUTION과 DANGER는 내부 계산 결과가 있더라도 화면에서는 SAFE로 처리했다. 경고 유지 시간도 줄여서, 정상 상태로 돌아온 뒤 경고가 오래 남지 않도록 조정했다.

이후 원거리 차량 박스의 미세한 흔들림으로 발생하던 오경고가 줄었다.

## 14. 장면이 바뀐 뒤 이전 장면의 경고가 남음

입력 영상은 하나의 연속 주행 영상이 아니라 여러 도로 장면이 편집되어 이어진 영상이다. 약 10.7초에 화면이 완전히 다른 장면으로 전환되는데, 이전 장면에서 발생한 주의 경고가 새 장면까지 잠깐 남았다.

기존 코드는 위험 차량이 사라져도 경고가 한 프레임 만에 꺼지지 않도록 `warningHoldFrames` 동안 배너를 유지했다. 연속 영상에서는 유용한 동작이지만, 장면 전환에서는 이전 장면의 상태가 새 장면으로 그대로 넘어가는 문제가 됐다.

장면 전환 감지기를 추가했다.

```
현재 프레임을 320×180 회색 영상으로 축소
→ 이전 프레임과 평균 절대 차이 계산
→ 밝기 히스토그램 상관계수 계산
→ 영상 전체 변화가 크고 히스토그램도 달라지면 장면 전환
```

장면 전환이 감지되면 다음 상태를 즉시 초기화한다.

- 상단 경고 유지 카운터
- CAUTION/DANGER 연속 확인 프레임
- 현재 선행 차량 ID
- TTC-P 계산 이력

새 장면이 시작된 직후에는 약 0.5초 동안 위험 분석을 중지해서, 검출과 추적이 다시 안정화된 뒤 선행 차량을 선택하도록 했다. 또한 상단 배너는 순간적인 위험 계산만으로 바로 표시하지 않고, 같은 선행 차량에서 위험 상태가 일정 프레임 이상 연속될 때만 표시하도록 했다 (CAUTION은 8프레임, DANGER는 3프레임 연속 확인).

수정 후 장면이 바뀌었는데 차량이 없는 화면에 이전 경고가 남는 현상은 사라졌다.

## 15. 19~21초의 부분 노출 탱크로리는 여전히 바로 검출 못 함 (한계로 남김)

원시 후보 진단 결과 21.9초부터는 train으로 오분류된 큰 박스가 있었기 때문에 후처리 규칙으로 복구할 수 있었다. 하지만 19~21초 초반에는 의미 있는 차량 후보 자체가 거의 없었다. 클래스 점수도 매우 낮고 airplane, umbrella, potted plant처럼 여러 클래스로 흔들렸다. 이 구간은 threshold나 클래스 변환만으로는 해결이 안 된다.

가능한 해결 방법으로는 이런 것들을 생각해봤다.

- 우측 경계의 큰 이동 영역을 별도 영상처리로 감지
- 카메라 전역 움직임을 보정한 뒤 독립 이동 객체 탐지
- YOLOv8s 이상 모델 사용
- 입력 해상도 확대
- 역광·부분 노출 탱크로리 데이터로 파인튜닝
- Edge 후보를 임시 Track으로 만들고 정식 YOLO 검출과 연결

다만 해당 트럭은 옆 차선에 있어서 현재 영상의 선행 차량 위험 판단에는 직접 영향을 주지 않는다. 이번 프로젝트에서는 21.9초 이후의 명확한 오분류를 복구하는 수준까지 반영하고, 부분 노출 객체의 조기 탐지는 이후 과제로 남겼다.

### Step 7 정리

이번 단계에서 구현한 파이프라인은 다음과 같다.

```
YOLOv8 ONNX 차량 검출
→ train으로 오분류된 우측 대형 탱크로리 제한적 복구
→ 차량 그룹 단위 NMS
→ 다중 객체 추적 및 ID 유지
→ 도로 ROI와 중앙 ego lane 분리
→ 선행 차량 후보 점수 계산
→ 히스테리시스로 LEAD ID 유지
→ 박스 높이와 하단점 변화 이력 수집
→ 회귀 기반 TTC-P 계산
→ 위험도 시간 안정화
→ 크기·위치·샘플 수 기반 오경고 필터링
→ 장면 전환 감지 및 상태 초기화
→ 한국어 상태 정보와 경고 출력
→ 결과 영상 저장
```

Step 7에서는 ROI 안의 모든 차량을 위험 대상으로 보던 구조를 내 차선의 선행 차량 한 대 중심으로 바꾸고, 단안 영상에서 계산 가능한 TTC-P를 설계했다.

또한 결과 영상에서 발견된 탱크로리 오분류, 원거리 박스 흔들림, 장면 전환 후 경고 잔류 문제를 원시 출력과 프레임 단위 검증으로 추적해서 각각 다른 방식으로 해결했다.

현재 결과는 연속적으로 검출되는 선행 차량에 대해 ID와 접근 위험 상태를 안정적으로 표시한다. 다만 실제 거리 기반 TTC가 아니라 영상 스케일 기반 Proxy이고, YOLO가 후보 자체를 만들지 못하는 부분 노출 객체와 장시간 재식별은 이후 과제로 남는다.

## 전체 정리

이번 프로젝트에서 문제를 해결할 때 공통적으로 썼던 방법은 다음과 같다.

- 화면에 보이는 결과만 보고 threshold를 무작정 조정하지 않았다.
- 원본 프레임, YOLO 원시 후보, NMS 결과, Track 상태, Risk 결과를 단계별로 분리해서 확인했다.
- 검출 실패와 추적 실패를 구분했다.
- 디버깅용 출력과 최종 포트폴리오용 출력을 분리했다.
- 한 문제를 해결하면서 생길 수 있는 오검출·오경고 범위를 조건으로 제한했다.
- 해결하지 못한 부분은 억지로 감추지 않고, 구조적 한계와 다음 개선 방향으로 남겼다.
