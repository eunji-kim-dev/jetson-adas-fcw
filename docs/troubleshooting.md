# Step 6 — 다중 객체 추적

## 1. ROI 안쪽 차량이 오히려 검출되지 않음

바깥쪽 차선 차량은 잘 잡히는데, 정작 주행 중인 ROI 안쪽 정면 차량이 자꾸 빠졌다. 처음에는 YOLO 모델 문제라고 보고 confidence threshold부터 조정했지만 별 차이가 없었다.

원인은 코드 실행 순서였다. 원본 프레임에 반투명 초록색으로 ROI를 먼저 칠하고, 그 프레임을 그대로 YOLO에 넣고 있었다. 모델이 보는 이미지 자체가 이미 오염돼 있었던 것이다. ROI 밖 차량은 원본 색을 유지하니 상대적으로 잘 잡히고, 안쪽은 픽셀 값이 달라져 검출이 흔들렸다.

검출과 시각화 순서를 뒤집었다.

```cpp
detections = detectObjects(
    net,
    frame,
    detectorThreshold,
    nmsThreshold
);

// 검출이 끝난 뒤에만 ROI를 그린다
cv::Mat overlay = frame.clone();

cv::fillConvexPoly(
    overlay,
    drivingRoi,
    cv::Scalar(0, 255, 0)
);
```

수정 후 안쪽 정면 차량과 바깥쪽 차량이 모두 검출됐다. 시각화용 오버레이가 검출 입력 자체를 건드리고 있었던 게 핵심이었고, 이후로는 원본 프레임과 화면 출력용 프레임을 분리해서 관리하기로 했다.

## 2. 멀리 있는 차량이 잘 잡히지 않음

가까이 있는 큰 차량은 문제없는데, 화면 끝에서 작게 보이는 원거리 차량은 프레임마다 잡혔다 안 잡혔다 했다.

confidence threshold가 0.40으로 걸려 있었는데, 원거리 차량은 픽셀 수 자체가 적으니 YOLO가 뽑는 confidence도 낮게 나온다. 0.40 기준에서 매번 잘려나간 것이다.

우선 threshold를 낮췄다.

```cpp
constexpr float confidenceThreshold = 0.25F;
```

다만 이것만으로는 애매한 후보가 함께 남는다. 그래서 YOLO 자체 검출 하한선은 0.10까지 열어두고, 등급을 나누는 역할은 추적기 쪽으로 넘겼다.

```cpp
constexpr float detectorThreshold = 0.10F;
```

- **0.25 이상 (고신뢰도)**: 기존 Track 매칭에도 쓰고 신규 Track도 생성한다.
- **0.10~0.25 (저신뢰도)**: 기존 Track을 이어주는 용도로만 쓴다.

낮은 confidence를 그대로 믿고 새 ID를 만들면 오검출이 새 차량으로 둔갑할 수 있어서, 저신뢰도 쪽에는 신규 생성 권한을 주지 않았다. 이후 기존에 놓치던 작은 원거리 차량이 눈에 띄게 자주 잡히기 시작했다.

## 3. 같은 차량인데 ID가 프레임마다 바뀜

정면 차량 하나가 ID:1 → ID:8 → ID:13 식으로 몇 초 사이에 계속 새 번호를 받았다. 거리가 먼 차량일수록 특히 심했다.

**IoU 게이트가 너무 빡빡했다.** 기존 추적기는 이전 Track의 예측 박스와 이번 프레임 Detection의 IoU만 보고 동일 객체인지 판단했는데, 원거리 차량은 박스 자체가 작아서 몇 픽셀만 움직여도 IoU가 크게 떨어진다.

여기에 더 근본적인 문제가 있었다. 새로 생성된 Track은 속도 정보(x/y 속도, 너비/높이 변화 속도)가 전부 0으로 시작한다. Kalman Filter가 다음 프레임 위치를 사실상 제자리로 예측하는 셈인데, 실제 차량은 카메라 상대 움직임 때문에 다음 프레임에 이미 수십 픽셀 이동해 있다. 그 결과 다음과 같은 악순환이 생긴다.

```
새 Track 생성
→ 속도 정보 없음
→ 제자리로 예측
→ 실제 위치는 이미 이동
→ 매칭 실패
→ 속도 학습 기회 상실
→ 다시 새 Track 생성
```

속도를 학습하려면 최소 2~3프레임은 이어져야 하는데, 매칭 조건 자체가 "이미 정확한 속도를 알고 있다"는 전제로 너무 타이트하게 짜여 있었던 셈이다.

**거리 게이트도 따로 놀았다.** IoU를 통과해도 중심점 거리 조건이 독립적으로 다시 걸러냈다.

```cpp
if (
    centerDistance >
    allowedDistance * 1.25F
) {
    continue;
}
```

허용 거리 상한도 100px로 막혀 있어서, 화면 가까이서 빠르게 움직이는 큰 차량이 여기 자주 걸렸다.

수정한 부분은 다음과 같다.

- IoU가 충분하면 거리 조건이 다시 탈락시키지 않도록 판정 순서를 바꿨다. 거리는 IoU가 애매할 때만 보조로 쓴다.
- 갓 생성된 Track(hits가 적은 것)에는 완화된 거리·면적 조건을 적용했다. 2~3프레임은 여유를 줘야 Kalman Filter가 속도를 학습할 시간이 생긴다.
- 허용 이동 거리 계산식을 바꿨다.

```cpp
return std::clamp(
    largestDiagonal * 0.85F + 8.0F,
    16.0F,
    320.0F
);
```

박스가 클수록 더 크게 움직여도 허용하되, 다른 차량과 엉키지 않도록 상한(320px)은 남겨뒀다.

- Kalman Filter 상태를 6개(중심 x/y, x/y 속도, 너비, 높이)에서 8개로 늘려 너비·높이 변화 속도까지 추적하게 했다. 차량이 가까워지거나 멀어질 때 박스 크기가 변하는 것도 예측에 반영하기 위해서다.

수정 후 같은 차량에 매 프레임 새 ID가 붙는 현상은 사라졌고, 정면·측면 차량 모두 몇 초씩 같은 ID를 유지했다.

## 4. 예전에 놓친 ID가 현재 차량을 가로챔

ID 1 → ID 17 → ID 23까지 바뀌었다가, 어느 순간 다시 ID 17이 튀어나오는 일이 있었다.

YOLO가 잠깐 놓쳐도 기존 Track은 몇 프레임 동안 리스트에 남아 있는 구조였다. 문제는 "직전까지 잘 이어지던 Track"과 "몇 프레임째 검출되지 않는 오래된 Track"이 똑같은 우선순위로 이번 프레임 Detection을 두고 경쟁했다는 점이다. 오래된 Track의 예측 위치가 우연히 현재 차량 근처로 오면, 정상적으로 이어지던 ID 대신 죽어가던 옛 ID가 낚아채가는 식이었다.

그래서 매칭을 단계별로 나눴다.

1. **1차** — 직전 프레임까지 정상적으로 이어진 Track + 고신뢰도 Detection. 가장 신뢰할 만한 조합부터 먼저 붙인다.
2. **2차** — 1차에서 떨어진 최근 Track + 저신뢰도 Detection. 신뢰도가 잠깐 낮아졌을 뿐인 차량이 ID를 잃지 않게 하는 용도다. 여기서는 저신뢰도로 새 Track을 만들지 않는다.
3. **3차** — 여러 프레임 놓친 Track은 1·2차가 모두 끝나고 남은 고신뢰도 Detection에만 붙는다. 놓친 프레임 수만큼 매칭 비용에 페널티를 부여했다.

그 외에도 아직 확정되지 않은 Track에 저신뢰도로 재시도할 기회를 주고, 놓친 Track이 복구될 수 있는 프레임 수에 제한을 두고, 박스 면적이 갑자기 크게 바뀌면 다른 객체로 간주하도록 했다. 같은 클래스면 매칭에 약간 가산점을 주고, 오래 놓친 Track일수록 매칭 비용을 더 얹었다.

이후 정상적으로 이어지던 ID를 과거 ID가 가로채는 경우가 눈에 띄게 줄었다.

## 5. 같은 차량에 car 박스와 truck 박스가 동시에 표시됨

YOLO가 같은 차량을 car로도 truck으로도 동시에 인식하면 박스 두 개, Track 두 개가 따로 생길 수 있었다.

원인은 NMS를 클래스별로 따로 돌리고 있었다는 점이다. car는 car끼리, truck은 truck끼리만 비교하니 같은 차량 위에 car 박스와 truck 박스가 함께 남아도 서로 다른 클래스라서 NMS가 중복으로 보지 않았다. 그런데 정작 추적기 쪽에서는 car/bus/truck을 전부 "사륜차"로 묶어 처리하고 있었으니, 검출 단계와 추적 단계의 클래스 기준이 서로 어긋나 있었던 셈이다.

그래서 NMS도 추적기 기준에 맞춰 그룹으로 묶었다.

- **사륜차**: car, bus, truck
- **이륜차**: bicycle, motorcycle
- **보행자**: person

그룹별로 `NMSBoxes()`를 따로 돌려서, 겹치는 박스 중 confidence가 가장 높은 것만 남게 했다. 이후 같은 차량이 서로 다른 클래스로 중복 검출돼 별도 Track이 생기는 경우가 줄었다.

## 6. confidence가 잠깐 낮아지기만 해도 ID가 끊김

같은 차량인데 confidence가 0.41 → 0.28 → 0.18 → 0.33처럼 프레임마다 출렁였다. 기준을 0.25로 잡아두면 0.18이 나온 프레임에서는 그 차량이 Detection 목록에서 통째로 빠진다. 이게 몇 프레임 반복되면 Track이 삭제되고, 다시 잡혔을 때는 새 ID가 발급됐다.

ByteTrack 방식을 참고해 Detection을 두 등급으로 나눴다.

- **고신뢰도**: 기존 Track 매칭 1순위, 신규 Track 생성도 가능
- **저신뢰도**: 1차 매칭에서 떨어진 기존 Track하고만 재매칭, 신규 생성 불가

```cpp
MultiObjectTracker tracker(
    0.25F,  // 고신뢰도 기준
    0.10F,  // 저신뢰도 최저 기준
    3,      // ID 확정에 필요한 매칭 횟수
    20      // 확정 Track 보관 프레임
);
```

새 Track이 바로 정식 ID를 받지 않고 몇 번은 이어져야 확정되도록 해서, 순간적인 오검출 하나 때문에 새 ID가 튀어나오는 것도 줄였다. 결과적으로 confidence가 잠깐 흔들려도 Track이 끊기지 않고, 불필요한 신규 ID 발급도 줄었다.

## 7. 오래 놓치면 결국 새 ID가 발급됨 (한계로 남김)

역광이 심하거나, 차량이 너무 멀어 작거나, 다른 차에 가려서 YOLO가 한동안 아예 검출하지 못하는 구간이 있으면, 다시 나타났을 때 새 ID가 발급된다.

현재 추적기는 박스 위치, 중심점 이동, 크기 변화, Kalman Filter 예측, 클래스만 보고 판단한다. 확정 Track은 최대 20프레임까지 유지하는데, 30FPS 기준이면 약 0.67초(20/30)다. 그보다 오래 놓치면 Track이 삭제되고, 다시 나타나도 이전 차량과 동일한 차량인지 확인할 방법이 없다. 색이나 외형을 전혀 비교하지 않기 때문이다.

보관 프레임 수를 무작정 늘리는 것도 답은 아니다. 그러면 이번에는 엉뚱한 다른 차량에 오래된 ID가 붙을 위험이 커진다. 그래서 `maxMissedFrames`는 건드리지 않기로 했다.

제대로 풀려면 외형 특징 비교, Re-ID, 카메라 움직임 보정, 전역 모션 추정 같은 것이 필요하다. 다만 Step 6의 목표는 "연속으로 검출되는 동안 ID를 안정적으로 유지하는 것"까지였고, 장시간 재식별은 다음 과제로 넘겼다.

## Step 6 정리

이번 단계에서 구현한 파이프라인은 다음과 같다.

```
YOLOv8 ONNX 검출
→ 고/저신뢰도 분리
→ 차량 그룹 단위 NMS
→ Kalman Filter로 위치·크기 예측
→ 초기 Track 완화 매칭
→ 고신뢰도 1차 매칭
→ 저신뢰도 2차 매칭
→ 놓친 Track 복구 매칭
→ 일정 횟수 이어진 Track에만 ID 확정
→ ROI 내부 판정
→ 결과 저장
```

동일 차량에 매 프레임 새 ID가 붙던 현상은 사라졌고, 연속으로 검출되는 정면·측면 차량은 몇 초씩 같은 ID를 유지한다. 다만 Track 보관 시간보다 오래 검출이 끊기면 여전히 새 ID가 발급된다. 위치·크기 기반 추적의 구조적 한계이고, 장시간 재식별은 이후 과제로 남긴다.

# Step 7 — TTC-P 기반 선행 차량 위험 분석

## 8. ROI 안의 모든 차량을 위험 대상으로 보면서 오경고 발생

초기 위험 분석은 ROI 안에 들어온 모든 차량의 박스 크기와 위치 변화를 계산했다. 그런데 이 영상은 고정 CCTV가 아니라 이동 중인 블랙박스 영상이라, 화면 속 차량 크기 변화에는 상대 차량의 움직임뿐 아니라 자차와 카메라의 움직임도 함께 섞인다.

특히 옆 차선 차량이 화면 가까이 크게 지나갈 때, 실제 충돌 위험과 관계없이 박스 면적이 빠르게 커져 CAUTION이나 DANGER가 뜰 수 있었다.

고정 카메라를 전제로 한 화면 좌표 기반 거리나 단순 Homography 방식은 이 입력 영상에 맞지 않았다. 그래서 위험 분석 대상을 ROI 안의 모든 차량이 아니라 자차 차선의 선행 차량 한 대로 제한하기로 했다.

처리 순서는 다음과 같다.

```
검출·추적된 차량
→ 차량 하단 중앙점 계산
→ ego lane ROI 내부 여부 확인
→ 화면 중앙과의 거리, 하단 위치로 선행 차량 후보 점수 계산
→ 가장 적합한 차량 한 대를 LEAD로 선택
→ 해당 차량에 대해서만 TTC-P 계산
```

선행 차량이 프레임마다 바뀌는 것을 줄이기 위해, 기존 `activeLeadId`를 바로 교체하지 않고 새 후보의 점수가 일정 수준 이상 더 좋을 때만 교체하는 히스테리시스도 추가했다.

수정 후 옆 차선에서 크게 지나가는 트럭은 SIDE로 표시되고, 실제 중앙 선행 차량만 위험 분석 대상으로 남았다.

## 9. 실제 거리가 없는 상태에서 TTC를 계산하는 방법

단안 블랙박스 영상만으로는 차량의 실제 거리와 실제 상대속도를 바로 알 수 없다. 카메라 내부 파라미터, 차량 실제 크기, 도로 기하 정보가 없기 때문에 초 단위의 정확한 TTC라고 주장해서는 안 된다고 판단했다.

그래서 결과 이름을 **TTC-P(TTC Proxy)** 로 명확히 구분했다.

선행 차량의 바운딩 박스 높이가 시간에 따라 얼마나 빠르게 증가하는지를 지표로 사용했다.

```
차량이 가까워짐
→ 영상에서 박스 높이가 증가
→ log(박스 높이)의 증가율 계산
→ 증가율이 클수록 TTC-P가 작아짐
```

첫 프레임과 마지막 프레임만 단순 비교하면 검출 박스가 한 번 흔들렸을 때 결과가 크게 튀기 때문에, 최근 여러 프레임의 log(boxHeight)에 선형회귀를 적용했다. 박스 하단 중앙점의 y축 이동 속도도 함께 계산해, 실제로 차량이 화면 아래쪽으로 접근하고 있는지를 보조 지표로 썼다.

TTC-P는 실제 거리 기반 충돌 시간의 대체값이 아니라, 영상 스케일 변화 기반 접근 위험 지표로 정의했다.

## 10. 경고 단계는 유지되는데 화면의 TTC-P 숫자는 계속 바뀜

경고 깜빡임을 막기 위해 CAUTION이나 DANGER 상태를 일정 시간 유지하도록 했는데, 상단 경고 문구에는 매 프레임 새로 계산된 TTC-P 숫자를 붙이고 있었다.

그래서 다음처럼 모순되어 보이는 장면이 생겼다.

```
이전 프레임: TTC-P 4.0초  → CAUTION 확정
다음 프레임: TTC-P 17.5초 → 안정화를 위해 CAUTION 유지
화면 표시:  CAUTION: CLOSING LEAD 17.5s
```

위험 단계 유지 자체는 의도한 동작이지만, 유지 중인 경고 단계와 현재 프레임 TTC-P를 한 문장에 넣은 것이 문제였다.

상단 경고 배너에서는 숫자를 뺐다.

```
CAUTION: CLOSING LEAD
DANGER: LOW TTC-P
```

현재 TTC-P 숫자는 선행 차량 라벨과 왼쪽 상태창에서만 보이도록 역할을 분리했다. 이후 상단 경고와 TTC-P 수치가 서로 모순되어 보이는 현상이 사라졌다.

## 11. 오른쪽 탱크로리가 19초부터 보이는데 22초가 지나야 검출됨

화면 오른쪽에서 탱크로리가 들어오는데, 차체가 이미 보이는 19초대에는 박스가 없고 약 22초 이후에야 truck으로 잡혔다.

처음에는 전체 프레임을 640×640으로 줄이면서 부분 노출된 트럭이 너무 작아진 것이 원인이라고 봤다. 그래서 우측 영역을 crop해 확대 추론하는 방식도 시험해봤는데, 추론 시간만 늘고 검출 시점은 거의 개선되지 않았다.

추측으로 계속 수정하는 대신, 18~24초 구간의 필터링 전 YOLO 원시 후보를 CSV로 기록해보기로 했다.

기록 항목은 다음과 같다.

- frame, time
- 상위 1·2·3순위 클래스와 점수
- car, bus, train, truck, boat 점수
- 박스 위치와 크기
- confidence 통과 여부
- ADAS 대상 클래스 통과 여부
- 최종 필터 통과 여부

진단 결과, 문제의 큰 박스는 21.9초부터 이미 생성되고 있었다.

```
21.922초  train 0.768 / truck 0.012
21.989초  train 0.886 / truck 0.002
22.055초  train 0.904 / truck 0.001
22.122초  train 0.914 / truck 0.000
22.289초  truck 0.607로 전환
```

즉 위치를 찾지 못한 것이 아니었다. 탱크로리 후면의 둥근 형태를 train(6)으로 강하게 오분류하고 있었고, `isTargetClass()` 필터가 train을 제거하면서 화면에 표시되지 않았던 것이다.

```
실제 탱크로리
→ YOLO 박스 생성
→ 최고 클래스 train
→ ADAS 대상 클래스 아님
→ Detection 삭제
→ Tracker에 전달되지 않음
```

모든 train을 truck으로 바꾸면 다른 장면의 오검출까지 차량으로 받아들일 수 있으니, 다음 조건을 모두 만족하는 후보만 제한적으로 복구하기로 했다.

- 원래 최고 클래스가 train(6)
- 신뢰도 0.25 이상
- 화면 오른쪽에 위치
- 박스가 충분히 큼
- 박스 하단이 도로 영역까지 내려옴

조건을 만족하면 truck(7)으로 재해석한 뒤 기존 차량 그룹 NMS와 Tracker에 전달했다. 이번 문제를 통해 threshold만 낮추기 전에 모델의 원시 출력과 필터링 과정을 먼저 확인해야 한다는 점을 다시 확인했다.

## 12. 원인 분석용 표시가 최종 영상에 남음

탱크로리 오분류를 확인하려고 18~24초 구간에 우측 진단 영역과 원시 후보를 표시했다. 원시 클래스가 train이면 자홍색 박스와 텍스트를 출력하도록 만들었는데, 진단이 끝난 뒤에도 같은 코드로 결과 영상을 생성하면서 핑크색 영역과 TRAIN 글씨가 최종 영상에 그대로 남았다.

진단용 출력과 실제 결과 영상의 역할을 분리했다.

- **진단 버전**: 원시 클래스, 후보 점수, 필터 통과 여부, CSV 저장
- **최종 버전**: 확정된 Detection과 Track만 표시

진단용 핑크색 ROI, 원시 후보 텍스트, CSV 출력 코드는 제거했다. 객체 클래스명은 car, truck, person처럼 영어를 유지하고, 왼쪽 상태 정보와 상단 경고는 한국어로 바꿨다. 화면 왼쪽 아래 설명 문구도 지웠다.

디버깅 정보는 문제를 찾는 동안에는 유용하지만, 포트폴리오 결과물에는 필요한 정보만 남겨야 한다는 것을 새삼 느꼈다.

## 13. 멀리 있는 작은 차량의 박스 흔들림을 접근으로 오판

약 15초 구간에서 실제로 급접근하는 차량이 없는데도 CAUTION 경고가 잠깐 떴다.

원인은 멀리 있는 작은 선행 차량의 박스였다. 차량 높이가 작을 때는 검출 박스가 2~3픽셀만 변해도 비율상 큰 증가로 계산된다. TTC-P는 박스 높이 증가율을 쓰기 때문에, 이런 검출 흔들림이 급격한 접근처럼 보였던 것이다.

단순 TTC-P 임계값 외에 경고 신뢰성 조건을 추가했다.

- TTC-P 계산이 유효할 것
- 관찰 샘플이 충분할 것
- 선행 차량 박스 높이가 일정 이상일 것
- 차량 하단점이 화면에서 충분히 가까운 위치일 것
- 전체 관찰 구간에서 박스 높이가 의미 있게 증가할 것
- 하단점도 화면 아래 방향으로 이동할 것

조건을 통과하지 못한 CAUTION과 DANGER는 내부 계산 결과가 있더라도 화면에서는 SAFE로 처리했다. 경고 유지 시간도 줄여서, 정상 상태로 돌아온 뒤 경고가 오래 남지 않도록 조정했다.

이후 원거리 차량 박스의 미세한 흔들림으로 발생하던 오경고가 줄었다.

## 14. 장면이 바뀐 뒤 이전 장면의 경고가 남음

입력 영상은 하나의 연속 주행 영상이 아니라 여러 도로 장면이 편집되어 이어진 영상이다. 약 10.7초에 화면이 완전히 다른 장면으로 전환되는데, 이전 장면에서 발생한 주의 경고가 새 장면까지 잠깐 남았다.

기존 코드는 위험 차량이 사라져도 경고가 한 프레임 만에 꺼지지 않도록 `warningHoldFrames` 동안 배너를 유지했다. 연속 영상에서는 유용한 동작이지만, 장면 전환에서는 이전 장면의 상태가 새 장면으로 그대로 넘어가는 문제가 됐다.

장면 전환 감지기를 추가했다.

```
현재 프레임을 320×180 회색 영상으로 축소
→ 이전 프레임과 평균 절대 차이 계산
→ 밝기 히스토그램 상관계수 계산
→ 영상 전체 변화가 크고 히스토그램도 달라지면 장면 전환
```

장면 전환이 감지되면 다음 상태를 즉시 초기화한다.

- 상단 경고 유지 카운터
- CAUTION/DANGER 연속 확인 프레임
- 현재 선행 차량 ID
- TTC-P 계산 이력

새 장면이 시작된 직후에는 약 0.5초 동안 위험 분석을 중지해, 검출과 추적이 다시 안정화된 뒤 선행 차량을 선택하도록 했다. 또한 상단 배너는 순간적인 위험 계산만으로 바로 표시하지 않고, 같은 선행 차량에서 위험 상태가 일정 프레임 이상 연속될 때만 표시하도록 했다(CAUTION은 8프레임, DANGER는 3프레임 연속 확인).

수정 후 장면이 바뀌었는데 차량이 없는 화면에 이전 경고가 남는 현상은 사라졌다.

## 15. 19~21초의 부분 노출 탱크로리는 여전히 즉시 검출하지 못함 (한계로 남김)

원시 후보 진단 결과 21.9초부터는 train으로 오분류된 큰 박스가 있었기 때문에 후처리 규칙으로 복구할 수 있었다. 하지만 19~21초 초반에는 의미 있는 차량 후보 자체가 거의 없었다. 클래스 점수도 매우 낮고 airplane, umbrella, potted plant처럼 여러 클래스로 흔들렸다. 이 구간은 threshold 조정이나 클래스 변환만으로는 해결되지 않는다.

가능한 해결 방법으로는 다음을 생각해봤다.

- 우측 경계의 큰 이동 영역을 별도 영상처리로 감지
- 카메라 전역 움직임을 보정한 뒤 독립 이동 객체 탐지
- YOLOv8s 이상 모델 사용
- 입력 해상도 확대
- 역광·부분 노출 탱크로리 데이터로 파인튜닝
- Edge 후보를 임시 Track으로 만들고 정식 YOLO 검출과 연결

다만 해당 트럭은 옆 차선에 있어서 현재 영상의 선행 차량 위험 판단에는 직접 영향을 주지 않는다. 이번 프로젝트에서는 21.9초 이후의 명확한 오분류를 복구하는 수준까지 반영하고, 부분 노출 객체의 조기 탐지는 이후 과제로 남겼다.

## 16. 햇빛과 자동 노출 변화가 장면 전환으로 오판되는 문제

14번에서 장면 전환 감지기를 붙인 뒤, 약 13초와 17초의 **같은 도로 장면**에서도 `[SCENE CHANGE]`가 찍히는 문제가 드러났다. 실제 편집 컷이 아닌데 선행 차량 ID와 TTC-P 이력이 초기화되면서 화면에 `선행 차량: 없음`이 표시됐다.

처음 장면 전환 조건은 두 값만 봤다.

```
320×180 회색 축소
→ 이전 프레임과 평균 절대 차이(rawDiff)
→ 밝기 히스토그램 상관계수
→ rawDiff가 크고 상관계수가 낮으면 장면 전환
```

문제 구간을 프레임 단위로 다시 재보니, 13초대에는 태양이 구조물 뒤로 가려졌다 다시 나오면서 카메라의 자동 노출이 크게 움직이고 있었다. 도로 구조는 그대로인데 화면 전체가 한 번에 어두워졌다 밝아지므로 `rawDiff`와 히스토그램 변화가 실제 컷만큼 커졌다.

대표 구간을 비교하면 다음과 같다.

| 구분 | 시각 | rawDiff | 히스토그램 상관계수 | 전역 밝기 이동(dMean) | \|dMean\| / rawDiff |
|---|---:|---:|---:|---:|---:|
| 실제 컷 | 10.78s | 30.7 | 0.22 | +7.9 | 0.26 |
| 실제 컷 | 19.19s | 43.9 | 0.68 | -7.5 | 0.17 |
| 실제 컷 | 33.73s | 54.6 | 0.39 | +5.9 | 0.11 |
| 햇빛/노출 | 13.35s | 15.7 | 0.68 | -13.9 | 0.88 |
| 햇빛/노출 | 13.41s | 22.7 | 0.55 | +20.5 | 0.90 |
| 햇빛/노출 | 17.38s | 22.4 | 0.63 | +18.2 | 0.81 |

상관계수만으로는 두 현상이 갈리지 않았다. 13.41초의 햇빛 변화는 상관계수가 0.55로, 19.19초 실제 컷의 0.68보다 오히려 낮았다. 임계값을 어디로 옮기든 한쪽을 살리면 다른 쪽을 놓치는 구조였다.

그래서 **전체 변화량 중 전역 밝기 이동이 차지하는 비율**을 새로 넣었다.

```
meanShift  = 현재 프레임 평균 밝기 - 이전 프레임 평균 밝기
shiftRatio = |meanShift| / rawDiff
```

노출 변화는 화면 대부분이 같은 방향으로 밝아지거나 어두워지므로 `shiftRatio`가 높다. 반면 실제 컷은 구조 자체가 바뀌기 때문에 전체 diff에 비해 평균 밝기 이동이 차지하는 몫이 작다. 이 영상에서는 실제 컷이 0.11~0.26, 햇빛/노출 변화가 0.59~0.93으로 깔끔하게 갈렸다.

`SceneChangeDetector`의 판단은 다음처럼 바꿨다.

```cpp
const bool sceneChanged =
    frameDifference >= 20.0F &&
    correlation <= 0.78F &&
    shiftRatio < 0.50F &&
    compensatedDifference >= 16.0F;
```

`compensatedDifference`는 두 프레임의 평균 밝기 이동을 먼저 빼고 남는 구조 변화량이다. 판단의 축은 `shiftRatio`이고, compensated diff는 평균 밝기 값이 우연히 상쇄되는 경우를 잡는 보조 조건이다. 현재 구현도 `diffThreshold=20`, `histogramThreshold=0.78`, `maximumExposureShiftRatio=0.50`, `compensatedDiffThreshold=0.8×diffThreshold`를 그대로 쓴다.

임계값을 계속 눈으로 확인할 수 있도록 로그도 둘로 나눴다.

```
[SCENE CHANGE]    실제 컷으로 판단된 프레임
[EXPOSURE CHANGE] rawDiff는 크지만 shiftRatio 때문에 노출 변화로 제외된 프레임
```

이 수정의 핵심은 **"픽셀이 많이 변했는가"에서 멈추지 않고, 그 변화가 화면 구조가 바뀐 것인지 전역 노출이 움직인 것인지 성분을 갈라 본 것**이다.

## 17. 17초에 실제 차량 주변을 가로로 길게 잡는 큰 가짜 박스 문제

17초 구간에서 작은 선행 차량 주변에 `car`로 표시된 가로로 긴 박스가 별도 Track으로 생겼다. 처음에는 confidence 문제로 보고 신규 Track 기준을 높이는 쪽을 검토했지만, 이 박스는 confidence가 0.32까지 올라가기 때문에 0.30 기준으로도 막히지 않았다.

프레임 520의 두 박스를 직접 비교했다.

```
가짜 큰 박스   : 약 64×18, aspect ratio ≈ 3.56
실제 작은 박스 : 약 31×23, aspect ratio ≈ 1.35
IoU         ≈ 0.36
containment ≈ 0.70
area ratio  ≈ 1.62
```

기존 필터가 이걸 놓친 이유는 세 가지였다.

1. **NMS IoU 0.45를 통과함**
   두 박스가 같은 자리에 겹쳐도, 큰 박스가 가로로 넓고 세로로 납작해 IoU가 0.36밖에 나오지 않았다.

2. **기존 containment 0.85에 못 미침**
   가짜 박스가 작은 박스를 가로로는 감싸지만 세로로는 다 덮지 못해 containment가 0.70에 머물렀다.

3. **exact class 비교가 너무 좁음**
   화면에는 둘 다 car로 보여도 프레임별 YOLO 원시 클래스는 car/truck 사이에서 흔들린다. 기존 `classId == classId` 비교로는 이런 중복 후보가 걸러지지 않았다.

그래서 NMS 뒤에 **부분 포함형 중복 박스 전용 후처리**를 붙였다.

```
같은 exact class가 아니라 같은 NMS 그룹인지 확인 (car / bus / truck)
        ↓
containment >= 0.60
        ↓
면적비 >= 1.35
        ↓
0.85 이상이면 강한 포함으로 바로 중복 후보
또는
작은 박스 중심이 큰 박스 내부 + 큰 박스 aspect >= 2.2
        ↓
비정상적으로 납작한 큰 박스를 제거
```

현재 사용하는 기준값은 다음과 같다.

```cpp
strictContainment        = 0.85F;
looseContainment         = 0.60F;
minimumAreaRatio         = 1.35F;
largeBoxConfidenceMargin = 0.08F;
abnormalAspectRatio      = 2.20F;
```

`aspect ratio`를 넣은 이유는, 17초 가짜 박스가 **실제 차량을 감싸는 위치 관계는 갖췄지만 64×18처럼 차량으로 보기엔 지나치게 납작했기** 때문이다. containment만 0.60으로 낮추면 옆 차선에서 정상적으로 겹친 차량까지 지워버리므로, `작은 박스 중심 포함 + 비정상 종횡비`를 함께 요구했다.

큰 박스의 형태가 비정상이면 confidence가 작은 박스보다 조금 높아도 큰 쪽을 먼저 지우게 했다. 원거리 crop에서 나온 진짜 작은 차량은 confidence가 낮게 잡히기 쉬워서, confidence 하나로 남길 박스를 고르면 오히려 실제 차량을 지울 수 있다.

최종 Detection 후처리 순서는 다음과 같이 바뀌었다.

```
전체 프레임 YOLO
+ 원거리 crop YOLO
→ Detection 합치기
→ 차량 그룹 NMS
→ containment / 중심 포함 / aspect ratio 기반 중복 제거
→ Tracker
```

이번 수정은 **"NMS를 썼는데 왜 중복 박스가 남았는가"를 IoU와 박스 기하를 직접 계산해 확인한 뒤, NMS가 약한 부분 포함형 박스에 별도 기준을 붙인 사례**다.

## 18. 길가 정차 차량이 LEAD로 선택되고 추월 과정에서 DANGER 발생

34~36초 구간에서 도로 가장자리에 정차한 트럭이 순간적으로 ego lane ROI에 걸치면서, 실제 선행 차량 대신 `LEAD`로 선택됐다. 이후 자차가 그 트럭 옆을 지나가는 동안 바운딩 박스가 급격히 커지면서 TTC-P가 빠르게 감소했고, 결국 `DANGER`로 오판되는 현상까지 이어졌다.

기존 LEAD 선정 로직은 **현재 프레임에서 차량의 접지점이 ego lane 안에 있는지**만 기준으로 판단했다. 곡선 도로에서는 길가 차량의 접지점이 일시적으로 ego lane 영역에 포함될 수 있기 때문에, 실제 주행 차로의 선행 차량이 아닌 정차 차량도 단 한 프레임 만에 LEAD 후보가 될 수 있었다.

또한 추월 중인 차량은 화면상 크기가 빠르게 증가하므로, 바운딩 박스 높이 변화만으로 계산하는 TTC-P는 정면에서 급접근하는 차량과 유사한 패턴을 보였다. 즉 횡방향으로 스쳐 지나가는 상황과 종방향으로 접근하는 상황을 구분하지 못했다.

**LEAD 후보 자격에 연속 체류 조건을 추가했다.** 객체가 ego lane 안에 약 0.5초 이상 연속으로 존재해야 후보가 될 수 있도록 `egoLaneStreakById`를 넣었다.

```cpp
const int leadEligibilityFrames =
    std::max(1, static_cast<int>(std::round(sourceFps * 0.5)));
```

**추월 상황(`passingBy`) 판별 로직도 붙였다.** 객체의 ego lane 내 횡방향 위치를 여러 프레임 동안 기록하고, 차선 중앙에서 바깥쪽으로 빠르게 이동하는 차량을 추월 중으로 판단한다.

```cpp
std::unordered_map<int, std::deque<float>> lateralHistoryById;

constexpr std::size_t lateralHistorySize = 8;
constexpr float maximumLateralDriftPerFrame = 0.02F;
```

과거 위치 대비 현재 위치가 차선 중앙에서 얼마나 빠르게 멀어지는지를 프레임당 횡방향 이동량으로 계산한다.

```cpp
const float pastOffset =
    std::abs(lateralHistory.front() - 0.5F);

const float recentOffset =
    std::abs(lateralHistory.back() - 0.5F);

const float outwardDriftPerFrame =
    (recentOffset - pastOffset) /
    static_cast<float>(lateralHistory.size() - 1);
```

`passingBy`로 판단된 차량은 TTC-P 값이 낮게 계산되더라도 CAUTION/DANGER 경고 대상에서 제외했다.

```cpp
const bool hasReliableWarningEvidence =
    ...
    !geometry.passingBy;
```

수정 후 길가 차량이 ego lane을 한 프레임 침범한 것만으로 즉시 LEAD가 되는 현상이 줄었고, 정차 차량을 추월하면서 바운딩 박스가 급격히 커지는 상황을 실제 충돌 접근으로 오인해 발생하던 `DANGER` 오경고도 제거됐다.

## 19. LEAD 차량 표시가 다른 객체 박스에 가려짐

여러 객체의 바운딩 박스가 겹치는 구간에서, 현재 LEAD 차량의 박스와 라벨이 다른 객체의 박스에 가려져 식별하기 어려운 경우가 있었다.

`trackedObjects` 순서대로 객체를 즉시 렌더링하고 있었기 때문에, LEAD 차량이 먼저 그려지면 이후에 렌더링되는 객체가 그 위를 덮었다. OpenCV의 기본 drawing 함수에는 z-index 개념이 없으므로, 표시 우선순위는 전적으로 렌더링 순서에 의해 결정된다.

전체 객체 렌더링이 끝난 뒤, 현재 `activeLeadId`에 해당하는 차량의 바운딩 박스, 접지점, 라벨을 마지막에 한 번 더 렌더링하도록 변경했다. 판정 및 추적 로직은 그대로 두고 시각화 단계만 분리한 수정이다.

```cpp
if (riskAnalysisEnabled && activeLeadId >= 0 && leadRiskFound) {
    // 현재 LEAD 차량 검색

    cv::rectangle(frame, trackedObject.box, leadBoxColor, 3);
    cv::circle(frame, geometry.groundPoint, 6, leadBoxColor, -1);

    // LEAD 라벨도 마지막에 다시 출력
}
```

수정 후 다른 차량의 바운딩 박스와 겹치는 상황에서도 LEAD 차량의 박스와 상태 라벨이 항상 최상위에 표시되어, 영상에서 선행 차량과 위험 상태를 한눈에 확인할 수 있게 됐다.

## Step 7 정리

이번 단계에서 구현한 파이프라인은 다음과 같다.

```
YOLOv8 ONNX 차량 검출
→ train으로 오분류된 우측 대형 탱크로리 제한적 복구
→ 차량 그룹 단위 NMS
→ 부분 포함형 중복 박스 제거
→ 다중 객체 추적 및 ID 유지
→ 도로 ROI와 중앙 ego lane 분리
→ ego lane 연속 체류 확인
→ 선행 차량 후보 점수 계산
→ 히스테리시스로 LEAD ID 유지
→ 박스 높이와 하단점 변화 이력 수집
→ 회귀 기반 TTC-P 계산
→ 위험도 시간 안정화
→ 크기·위치·샘플 수·추월 여부 기반 오경고 필터링
→ 장면 전환 감지 및 상태 초기화
→ 한국어 상태 정보와 경고 출력
→ LEAD 차량 최상위 재렌더링
→ 결과 영상 저장
```

Step 7에서는 ROI 안의 모든 차량을 위험 대상으로 보던 구조를 자차 차선의 선행 차량 한 대 중심으로 바꾸고, 단안 영상에서 계산 가능한 TTC-P를 설계했다.

또한 결과 영상에서 발견된 탱크로리 오분류, 원거리 박스 흔들림, 장면 전환 후 경고 잔류, 노출 변화 오판, 부분 포함형 가짜 박스, 추월 차량 오경고 문제를 원시 출력과 프레임 단위 검증으로 추적해 각각 다른 방식으로 해결했다.

현재 결과는 연속적으로 검출되는 선행 차량에 대해 ID와 접근 위험 상태를 안정적으로 표시한다. 다만 실제 거리 기반 TTC가 아니라 영상 스케일 기반 Proxy이고, YOLO가 후보 자체를 만들지 못하는 부분 노출 객체와 장시간 재식별은 이후 과제로 남는다.
