# 전방 추돌 경보 시스템 (Monocular FCW)

단안 블랙박스 영상만으로 선행 차량을 추적하고 접근 위험도를 판정하는 C++ ADAS 비전 파이프라인입니다.

카메라 보정값도, 거리 센서도, 자차 속도 정보도 없이 **바운딩 박스의 화면상 크기 변화만으로** 충돌 위험을 추정합니다. YOLOv8 ONNX로 객체를 검출하고, Kalman Filter로 추적하며, 선행 차량 한 대를 골라 TTC-P(TTC Proxy)를 계산해 SAFE / CAUTION / DANGER를 판정합니다.

## 해결한 문제

네 건 모두 **가설 → 측정 → 반증 또는 확인 → 수정** 과정을 거쳤습니다.

### 탱크로리가 3초 늦게 검출되던 문제

19초부터 화면에 보이는 대형 탱크로리가 22초가 지나야 검출됐습니다. 원거리 해상도 문제로 보고 우측 영역 crop 추론을 시험했지만 처리 시간만 늘고 검출 시점은 그대로였습니다.

필터링 **이전**의 YOLO 원시 후보를 CSV로 덤프해 확인한 결과, 문제의 박스는 21.9초부터 이미 생성되고 있었고 클래스가 계속 `train`으로 분류되고 있었습니다.

```
21.922초  train 0.768
21.989초  train 0.886
22.055초  train 0.904
22.289초  truck 0.607
```

검출 실패가 아니라 클래스 오분류와 후처리 필터의 문제였습니다. 모든 `train`을 바꾸면 다른 장면에서 오검출이 늘어나므로, 위치·크기·면적 등 7개 조건을 모두 만족할 때만 `truck`으로 재해석하도록 제한했습니다.

### 역광 구간이 장면 전환으로 오검출되던 문제

프레임 차이와 히스토그램 상관도만 보던 초기 구현에서, 햇빛·자동 노출 변화가 장면 전환으로 판정됐습니다. 그때마다 추적 상태가 초기화되어 ID가 끊겼습니다.

노출 변화와 실제 컷의 차이는 **변화가 화면 전체에 균일한가**입니다. 전체 변화량 중 전역 밝기 이동이 차지하는 비율(`shiftRatio`)을 계산해 두 유형을 분리했습니다. 실행 로그에서 관측된 값은 다음과 같습니다.

```
[SCENE CHANGE]    frame=323   diff=30.93  hist=0.28  shiftRatio=0.25
[SCENE CHANGE]    frame=575   diff=44.20  hist=0.67  shiftRatio=0.18
[SCENE CHANGE]    frame=1011  diff=55.47  hist=0.55  shiftRatio=0.12

[EXPOSURE CHANGE] frame=402   diff=23.27  hist=0.72  shiftRatio=0.91
[EXPOSURE CHANGE] frame=521   diff=22.17  hist=0.67  shiftRatio=0.89
[EXPOSURE CHANGE] frame=569   diff=22.19  hist=0.83  shiftRatio=0.68
```

**노출 변화 3건 중 2건이 기존 2조건(`diff ≥ 20`, `hist ≤ 0.78`)을 그대로 통과합니다.** `shiftRatio`가 없었다면 오검출됐을 사례입니다. 실제 컷은 0.12~0.25, 노출 변화는 0.68~0.91로 분포가 겹치지 않아 0.50을 기준으로 분리했습니다. 1,252프레임에서 컷 3회를 모두 감지하고 노출 오검출은 0회였습니다.

### 검출 병목 위치를 오판하던 문제

원거리 crop 보조 추론을 추가한 뒤 처리 속도가 크게 떨어졌습니다. Detection 병합, 그룹 NMS, 중복 박스 제거 같은 후처리도 상당한 비중일 것으로 예상하고 구간별 계측을 수행했습니다.

| 측정 구간 | 평균 처리 시간 | 비중 |
|---|---:|---:|
| 전체 프레임 YOLO | 178.70 ms | 50.3% |
| 원거리 crop YOLO | 176.33 ms | 49.7% |
| Detection 후처리 | 0.022 ms | 0.01% |
| **검출 구간 합계** | **355.05 ms** | **100%** |

예상이 틀렸습니다. 후처리는 0.022 ms에 불과했고 지연의 99.99%가 두 번의 YOLO 추론에서 발생하고 있었습니다.

crop 이미지도 결국 640×640으로 letterbox되어 동일한 네트워크 전체를 통과하기 때문에, 영역이 작아도 추론 비용은 전체 프레임과 거의 같았습니다. **원거리 검출률을 얻는 대가로 처리 속도를 절반으로 지불하고 있었다**는 것을 수치로 확인했고, 이후 최적화 대상을 후처리가 아닌 추론 구조로 확정했습니다.

### LEAD가 3프레임마다 끊기던 문제

결과 영상의 오버레이를 프레임 단위로 파싱해 LEAD 연속 구간을 측정한 결과, **지정된 LEAD의 75%가 15프레임을 채우지 못하고 해제**되고 있었습니다. LEAD 안정화를 위해 넣은 `ego lane 0.5초(15프레임) 체류` 조건보다 짧게 유지된다는 뜻입니다.

원인은 진입과 이탈이 모두 즉각적이었다는 것입니다. `egoLaneRoi` 상단 폭이 화면 폭의 8%(1280 기준 102px)에 불과해, 원거리에서는 접지점이 몇 픽셀 흔들리는 것만으로 경계를 넘나듭니다. 한 프레임만 벗어나도 체류 카운터와 TTC-P 샘플 15개가 함께 삭제됐습니다.

진입은 그대로 두고 이탈에만 유예(약 0.15초)를 적용한 뒤 다시 측정했습니다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| LEAD 유지 구간 수 | 16개 | 6개 |
| 구간 길이 중앙값 | 3프레임 | 25.5프레임 |
| 구간 길이 최대 | 237프레임 | 306프레임 |
| 15프레임 미만 구간 | 12 / 16 (75%) | 3 / 6 (50%) |
| LEAD 지정 프레임 비율 | 48.8% | 48.1% |
| TTC-P 산출 비율 (전체) | 16.7% | 18.3% |
| TTC-P 산출 비율 (LEAD 중) | 34.2% | 38.0% |
| 10프레임 이상 TTC-P 구간 | 5개 | 8개 |

**LEAD 지정 비율은 48.8% → 48.1%로 거의 변하지 않았습니다.** 즉 이 수정은 LEAD를 더 많이 잡게 만든 것이 아니라, 이미 잡힌 LEAD가 잘게 끊기는 현상을 줄여 연속성을 높인 것입니다. 중앙값이 3프레임에서 25.5프레임으로 8배 이상 늘었고, TTC-P가 10프레임 이상 이어진 구간도 5개에서 8개로 늘었습니다.

## 성능 기준선

Jetson 이식 후 동일 지표로 비교하기 위해 CPU 환경의 기준선을 먼저 확정했습니다.

| 항목 | 계측값 | 66.7 ms 대비 |
|---|---:|---:|
| 최소 지연 | 141.21 ms | 2.1배 |
| 중앙값 | 334.16 ms | 5.0배 |
| **평균** | **355.05 ms** | **5.3배** |
| **P95** | **563.96 ms** | **8.5배** |
| **P99** | **701.59 ms** | **10.5배** |
| 최대 | 849.06 ms | 12.7배 |
| Deadline Miss Rate (15 FPS) | 100% | — |

평균만 보면 실시간성을 판단할 수 없습니다. 한 프레임이라도 크게 밀리면 그 프레임의 위험 판정과 경고가 함께 늦어지기 때문입니다. 그래서 **P95·P99와 Deadline Miss Rate를 주 지표로 사용**하고, 최대값은 OS 스케줄링 등 단발성 요인이 섞이므로 참고값으로만 봅니다.

### 실행 간 편차와 원인

동일 조건 4회 실행 결과입니다.

| 회차 | 추론 평균 | 전체 처리 속도 | 검출 외 오버헤드 |
|---|---:|---:|---:|
| 1 | 386.35 ms | 2.46 FPS | 20.2 ms |
| 2 | 391.16 ms | 2.43 FPS | 20.4 ms |
| 3 | 369.86 ms | 2.56 FPS | 20.8 ms |
| 4 | 355.05 ms | 2.67 FPS | 19.5 ms |

추론 시간은 4회 평균 375.6 ms, 최대-최소 차이 36.1 ms(9.6%)로 흔들립니다. 반면 **검출 외 오버헤드는 19.5~20.8 ms로 4회 모두 일정**합니다. 디코드·렌더링·인코드 비용은 프레임 내용과 무관하다는 뜻이고, 두 값이 독립적으로 측정됐음에도 차이가 일정하다는 점이 계측 정확도의 근거입니다.

실행 간 편차의 원인은 단일 실행 안에서도 관측됩니다. 50프레임 단위 구간 평균이 초반 186 ms에서 중반 440 ms까지 변동합니다. 프레임 내용이 아니라 CPU 클럭 하강에 따른 것으로, 두 YOLO가 같은 비율로 함께 느려지고 후처리 시간은 변하지 않습니다.

**성능 변화를 주장할 때는 10%를 넘는 차이만 유의미한 것으로 봅니다.** Jetson 포팅에서도 30분 연속 구동 시 thermal throttling에 따른 지연 추이를 같은 방식으로 측정할 계획입니다.

## 처리 흐름

```
블랙박스 영상 입력
→ 장면 전환 감지 (4조건 AND, 원본 프레임 기준)
→ 전환 시 Tracker · 위험 이력 · LEAD 상태 초기화 + 0.5초 분석 유예
→ Letterbox 전처리
→ YOLOv8 ONNX 전체 프레임 추론 (conf ≥ 0.10)
→ 원거리 도로 crop 보조 추론 (차량 계열만, conf ≥ 0.20)
→ 두 결과 병합
→ 차량 그룹 단위 NMS → 2차 NMS → 포함 관계 중복 제거 → 극소 박스 제거
→ Kalman Filter 위치 · 크기 · 변화속도 예측
→ 3단계 매칭 (고신뢰도 → 저신뢰도 → 복구)
→ 도로 ROI와 ego lane 판정
→ ego lane 체류 차량 중 선행 차량(LEAD) 선택, 추월 차량 제외
→ 박스 높이 변화 이력 수집 → TTC-P 계산
→ 위험 단계 시간 안정화 및 신뢰성 조건 검사
→ 한국어 상태 정보 · 경고 배너 오버레이
→ 결과 영상 저장 및 구간별 처리 시간 출력
```

## 주요 구현 내용

### TTC-P (Time-To-Collision Proxy)

단안 영상만으로는 실제 거리와 상대속도를 알 수 없습니다. 대신 전방 물체의 화면상 높이 `h`가 실제 거리 `Z`에 반비례한다는 성질을 이용했습니다.

```
h ≈ k / Z
log(h) ≈ log(k) − log(Z)
d(log h)/dt ≈ 1 / TTC
```

따라서 `TTC-P ≈ 1 / (log 높이 증가율)`이 됩니다. 카메라 보정도 자차 속도도 필요 없습니다.

한두 프레임의 박스 흔들림에 휘둘리지 않도록 첫·끝 샘플의 차분이 아니라 저장된 전체 샘플(최대 15개)에 최소제곱 선형회귀를 적용했습니다. 로그 공간에서 회귀를 돌리는 이유는, 원시 높이에 회귀를 걸면 접근 후반부에 가중치가 쏠려 기울기가 편향되기 때문입니다.

너비가 아니라 높이를 스케일 지표로 쓴 이유는, 차선 변경이나 부분 가림에서 너비가 심하게 흔들리는 데 비해 높이가 상대적으로 안정적이기 때문입니다.

선행 차량이 매우 가까워져 박스 하단이 화면 밖으로 나가면 높이 증가와 접지점 하강이 동시에 멈춥니다. 위험이 가장 큰 순간에 두 지표가 함께 죽는 구조라, 절단 직전 종횡비로 너비를 등가 높이로 환산해 시계열을 잇도록 보정했습니다.

### 다중 객체 추적

Kalman Filter 상태는 8개입니다. 중심 좌표와 속도에 더해 **박스 너비·높이의 변화속도**를 포함시켜, 차량이 접근할 때 다음 프레임의 크기 변화까지 예측에 반영합니다.

매칭 비용은 세 항의 가중합입니다.

```
cost = (1 − IoU) × 0.58 + 정규화거리 × 0.27 + 크기차이 × 0.15
```

IoU가 기준 이상이면 거리·면적 조건이 그 후보를 다시 거부하지 못하도록 순서를 잡았습니다. 거리와 면적 게이트는 IoU가 낮을 때만 보조 수단으로 동작합니다.

ByteTrack을 참고해 Detection을 신뢰도로 나눠 씁니다. 저신뢰도 검출(0.10~0.25)은 기존 Track을 이어주는 데만 쓰고 새 ID를 만들지 않으며, 정식 ID 확정에도 반영하지 않습니다. 신규 Track 생성은 별도로 더 높은 기준(0.30)을 씁니다.

오래 놓친 Track이 현재 차량의 ID를 가로채는 문제는 매칭을 3단계로 나누고 누락 프레임 수에 비례하는 비용 페널티(`(누락−1) × 0.08`)를 더해 해결했습니다.

### 선행 차량 선택

넓은 도로 ROI와 실제 위험 분석용 ego lane을 분리했습니다. 옆 차선 차량은 계속 검출·추적하되 위험 분석에서만 제외합니다.

LEAD 점수는 접지점 y좌표에서 차선 중앙 이탈 페널티를 뺀 값입니다.

```cpp
leadScore = groundPoint.y − |normalizedX − 0.5| × 90.0f
```

**진입은 엄격하게, 이탈은 관대하게** 나눠 판정합니다.

| 구분 | 조건 |
|---|---|
| 후보 등록 | ego lane 체류 0.5초 |
| 후보 등록 (컷인 차량) | 체류 약 0.15초 (최소 4프레임) |
| LEAD 교체 | 기존 LEAD보다 35점 이상 높을 때 |
| LEAD 유지 | 차선 이탈 시 약 0.15초 유예 후 해제 |
| 제외 | 차선 중앙에서 바깥으로 이탈하는 추월 차량 (횡이동 > 0.02/frame) |

체류 조건은 길가 정차 차량이 순간적으로 차선에 걸쳐 LEAD가 되는 것을 막기 위한 것입니다. 다만 옆 차선에서 파고드는 컷인 차량은 정의상 방금 진입한 차량이라 이 조건을 만족할 수 없어, 횡이동 방향이 차선 중앙을 향하는 경우 체류 요건을 단축합니다.

이탈 유예의 효과는 위 「LEAD가 3프레임마다 끊기던 문제」에 계측값으로 정리했습니다.

### 위험 단계 안정화

박스가 한 프레임 흔들릴 때마다 경고가 깜빡이지 않도록 승격과 강등을 비대칭으로 처리합니다.

| 전이 | 필요 프레임 |
|---|---|
| SAFE → CAUTION | 4 |
| → DANGER | 2 |
| DANGER → 하향 | 10 |
| CAUTION → 하향 | 6 |

상단 배너는 여기에 더해 CAUTION 8프레임 / DANGER 3프레임 연속 확인을 요구하고, 표시 후 약 0.25초 유지합니다.

경고 판정에는 TTC-P 외에 최소 박스 높이, 샘플 수, 높이 증가율, 접지점 하강 속도, 접지점 화면 위치, 추월 여부를 함께 확인합니다. 원거리 소형 박스가 2~3픽셀 흔들려 TTC-P가 4초대로 잘못 계산되던 오경고를 막기 위한 조건입니다.

시간 관련 판정은 `RiskAnalyzer`가, 화면 기하 관련 판정은 `main.cpp`가 소유하도록 나눴습니다. 두 곳에 같은 종류의 임계값이 흩어져 있으면 직렬로 걸리면서 한쪽이 도달 불가능한 죽은 값이 되기 때문입니다.

## 검증 범위와 한계

### 현재 영상으로 검증된 것

- 객체 검출 및 Tracking
- LEAD 선택과 유지 연속성 (수정 전후 정량 비교 완료)
- ego lane 이탈 유예 적용 결과
- TTC-P 샘플 축적 및 시계열 유지 정도
- 장면 전환 감지와 상태 초기화
- 정상 주행 상황에서의 오경고 억제 (1,252프레임 경고 0회)

### 별도 검증이 필요한 것

**경고 경로가 실행된 적이 없습니다.** 현재 테스트 영상 1,252프레임에서 CAUTION과 DANGER가 한 번도 발생하지 않았습니다. 위험 상황이 포함되지 않은 영상이기 때문입니다. 따라서 다음 항목은 위험 상황 영상으로 별도 측정해야 합니다.

- TTC-P 감소에 따른 CAUTION / DANGER 진입 시점
- 실제 위험 발생부터 경고까지의 지연 프레임 수
- 경고 상태 유지 시간과 위험 종료 후 SAFE 복귀 시간
- 급접근·컷인 상황에서의 경고 지연
- 위험 구간에서의 경고 누락 여부

### 구조적 한계

**박스 좌우 절단은 처리하지 못합니다.** 하단 절단은 종횡비 기반 등가 높이로 보정했으나, 차량이 더 가까워져 좌우까지 화면을 벗어나면 너비도 포화되어 스케일 추정이 불가능해집니다.

**ROI가 고정 좌표입니다.** 차선 검출을 수행하지 않으며, 두 사다리꼴은 현재 테스트 영상의 카메라 장착 위치에 맞춰 조정한 값입니다. 곡선로, 차선 변경, 다른 카메라 위치에서는 실제 주행 차선과 어긋납니다.

**실시간 처리가 불가능합니다.** 15 FPS 목표(66.7 ms) 대비 P95가 8.5배이고 Deadline Miss Rate가 100%입니다. 시간 관련 임계값이 FPS 환산 기반이라, 실행 속도가 다른 환경에 그대로 이식하면 경고 시점이 달라집니다.

**실제 거리 기반 TTC가 아닙니다.** TTC-P는 영상 스케일 변화 기반의 상대적 접근 위험 지표입니다. 실거리 TTC를 계산하려면 카메라 보정, 설치 높이·각도, 차량 실제 크기 추정, Ego-motion 보정이 필요합니다.

**장시간 재식별이 불가능합니다.** Track 보관 시간(20프레임)보다 오래 검출이 끊기면 새 ID가 생성됩니다. 위치와 크기 중심의 추적이라 외형 비교가 불가능합니다.

**일부 규칙이 특정 영상에 맞춰져 있습니다.** train 오분류 복구 조건, 장면 전환 임계값, LEAD 체류·추월 기준은 현재 테스트 영상의 개별 구간에서 역산한 값입니다. 각 값의 출처 구간은 코드 주석과 devlog에 기록해뒀습니다.

## 진행 계획

### 1단계 · 정량 평가 체계 확장

LEAD 연속성과 성능 지표는 계측 체계가 갖춰졌습니다. 남은 것은 경고 경로입니다.

- 실제 위험 상황이 포함된 영상 확보 (AI Hub 교통사고 영상 데이터)
- 경고 적시성 지표 정의 (충돌 프레임 기준 TTC 2.0초 이전 DANGER 발생 여부)
- 오경보율 정의 (위험 없는 구간 100초당 경보 횟수)
- 동일 LEAD에서 TTC-P가 연속 계산된 길이를 별도 품질 지표로 추가
- 위 지표로 경고 임계값 재조정
- 프레임별 TTC-P 시계열 CSV 출력 (FP16 포팅 시 정확도 비교용 기준선)

### 2단계 · Jetson 포팅

- ONNX → TensorRT FP16 변환
- 동일 지표로 재측정 (평균 / 중앙값 / P95 / P99 / Max / Deadline Miss Rate)
- GPU 사용률, 메모리, 소비 전력, 온도 계측
- 30분 연속 구동 시 thermal throttling에 따른 지연 추이
- **FP32 대비 FP16 정확도 검증** — 검출 수, LEAD 선정 일치율, TTC-P 평균 절대 오차, 경고 시점 차이
- 원거리 crop 추론 주기 감소 및 검출률 트레이드오프 측정
- Detection 없는 중간 프레임의 Tracking 보간
- 영상 입력·추론·렌더링 파이프라인 분리

### 3단계 · 알고리즘 개선

- 차선 검출 기반 동적 ego lane
- 박스 좌우 절단 감지
- 시간 임계값을 전부 초 단위로 정규화
- Ego-motion 보정
- Re-ID 특징을 이용한 장시간 객체 재식별
- YOLOv8n / YOLOv8s, 입력 640 / 960 비교
- 대형 차량·역광·부분 노출 데이터 파인튜닝
