# 전방 추돌 경보 시스템 (Monocular FCW)

단안 블랙박스 영상만으로 선행 차량을 추적하고 접근 위험도를 판정하는 C++ ADAS 비전 파이프라인입니다.

카메라 보정값도, 거리 센서도, 자차 속도 정보도 없습니다. **바운딩 박스의 화면상 크기 변화만으로** 충돌 위험을 추정합니다. YOLOv8 ONNX로 검출하고, Kalman Filter로 추적하고, 선행 차량 한 대를 골라 TTC-P(TTC Proxy)를 계산해 SAFE / CAUTION / DANGER를 판정합니다.

## 해결한 문제

시간을 가장 많이 쓴 세 가지입니다. 셋 다 **가설을 세우고, 측정하고, 가설이 틀린 것을 확인한 뒤 원인을 찾은** 과정을 거쳤습니다.

### 탱크로리가 3초 늦게 검출되던 문제

19초부터 화면에 보이는 대형 탱크로리가 22초가 지나야 검출됐습니다. 원거리 해상도 문제로 보고 우측 영역 crop 추론을 시험했지만, 처리 시간만 늘고 검출 시점은 그대로였습니다.

필터링 **이전**의 YOLO 원시 후보를 CSV로 덤프하자 원인이 드러났습니다. 문제의 박스는 21.9초부터 이미 생성되고 있었고, 클래스가 계속 `train`으로 분류되고 있었습니다.

```
21.922초  train 0.768
21.989초  train 0.886
22.055초  train 0.904
22.289초  truck 0.607
```

검출 실패가 아니라 클래스 오분류와 후처리 필터의 문제였습니다. 모든 `train`을 바꾸면 다른 장면에서 오검출이 늘어나므로, 위치·크기·면적 등 7개 조건을 모두 만족할 때만 `truck`으로 재해석하도록 제한했습니다.

### 역광 구간이 장면 전환으로 오검출되던 문제

프레임 차이와 히스토그램 상관도만 보던 초기 구현에서, 13초와 17초의 햇빛·자동 노출 변화가 장면 전환으로 판정됐습니다. 그때마다 추적 상태가 초기화되어 ID가 끊겼습니다.

노출 변화와 실제 컷의 차이는 **변화가 화면 전체에 균일한가**입니다. 전체 변화량 중 전역 밝기 이동이 차지하는 비율(shiftRatio)을 계산해 두 유형의 분포를 측정했습니다.

![shiftRatio 분포](docs/figs/03-shiftratio.svg)

두 분포가 겹치지 않아 0.50을 기준으로 분리할 수 있었습니다. 전역 밝기 이동을 제거한 뒤 남는 구조 변화량까지 포함해 4개 조건 AND로 판정한 결과, 1,252프레임에서 컷 3회를 모두 감지하고 노출 변화 오검출은 0회였습니다.

### 검출 병목 위치를 오판하던 문제

원거리 crop 보조 추론을 추가한 뒤 처리 속도가 크게 떨어졌습니다. Detection 병합, 그룹 NMS, 중복 박스 제거 같은 후처리도 상당한 비중을 차지할 것으로 예상하고 구간별 계측을 수행했습니다.

![검출 구간 지연 분해](docs/figs/04-latency.svg)

예상이 틀렸습니다. 후처리는 0.025 ms에 불과했고, 지연의 99.99%가 두 번의 YOLO 추론에서 발생하고 있었습니다.

crop 이미지도 결국 640×640으로 letterbox되어 동일한 네트워크 전체를 통과합니다. 영역이 작아도 추론 비용은 전체 프레임과 거의 같았습니다. **원거리 검출률을 얻는 대가로 처리 속도를 절반으로 지불하고 있었다**는 것을 수치로 확인했고, 이 값을 CPU Baseline으로 고정했습니다.

## 처리 흐름

![파이프라인](docs/figs/02-pipeline.svg)

장면 전환은 원본 프레임 기준으로 판정하며, 전환이 감지되면 Tracker·위험 이력·LEAD 상태를 초기화하고 0.5초간 분석을 유예합니다. 검출은 전체 프레임 추론(conf ≥ 0.10)과 원거리 도로 crop 보조 추론(차량 계열만, conf ≥ 0.20)을 병합한 뒤, 차량 그룹 단위 NMS → 2차 NMS → 포함 관계 중복 제거 → 극소 박스 제거를 거칩니다.

## 주요 구현 내용

### TTC-P (Time-To-Collision Proxy)

단안 영상만으로는 실제 거리와 상대속도를 알 수 없습니다. 대신 전방 물체의 화면상 높이 `h`가 실제 거리 `Z`에 반비례한다는 성질을 이용했습니다.

![TTC-P 원리](docs/figs/05-ttcp.svg)

카메라 보정도 자차 속도도 필요 없습니다. 한두 프레임의 박스 흔들림에 휘둘리지 않도록, 첫·끝 샘플의 차분이 아니라 저장된 전체 샘플(최대 15개)에 최소제곱 선형회귀를 적용했습니다. 로그 공간에서 회귀를 돌리는 이유는, 원시 높이에 회귀를 걸면 접근 후반부에 가중치가 쏠려 기울기가 편향되기 때문입니다.

너비가 아니라 높이를 스케일 지표로 쓴 이유는, 차선 변경이나 부분 가림에서 너비가 심하게 흔들리는 데 비해 높이가 상대적으로 안정적이기 때문입니다.

선행 차량이 매우 가까워져 박스 하단이 화면 밖으로 나가면 높이 증가와 접지점 하강이 동시에 멈춥니다. 위험이 가장 큰 순간에 두 지표가 함께 죽는 구조라, 절단 직전 종횡비로 너비를 등가 높이로 환산해 시계열을 잇도록 보정했습니다.

### 다중 객체 추적

Kalman Filter 상태는 8개입니다. 중심 좌표와 속도에 더해 **박스 너비·높이의 변화속도**를 포함시켜, 차량이 접근할 때 다음 프레임의 크기 변화까지 예측에 반영합니다.

매칭 비용은 세 항의 가중합입니다.

```
cost = (1 − IoU) × 0.58 + 정규화거리 × 0.27 + 크기차이 × 0.15
```

IoU가 기준 이상이면 거리·면적 조건이 그 후보를 다시 거부하지 못하도록 순서를 잡았습니다. 거리와 면적 게이트는 IoU가 낮을 때만 보조 수단으로 동작합니다.

ByteTrack을 참고해 Detection을 신뢰도로 나눠 씁니다. 저신뢰도 검출(0.10~0.25)은 기존 Track을 이어주는 데만 쓰고, 새 ID를 만들지 않으며 정식 ID 확정에도 반영하지 않습니다. 신규 Track 생성은 더 높은 기준(0.30)을 씁니다.

오래 놓친 Track이 현재 차량의 ID를 가로채는 문제는, 매칭을 3단계로 나누고 누락 프레임 수에 비례하는 비용 페널티(`(누락−1) × 0.08`)를 더해 해결했습니다.

### 선행 차량 선택

넓은 도로 ROI와 실제 위험 분석용 ego lane을 분리했습니다. 옆 차선 차량은 계속 검출·추적하되 위험 분석에서만 제외합니다.

LEAD 점수는 접지점 y좌표에서 차선 중앙 이탈 페널티를 뺀 값입니다.

```cpp
leadScore = groundPoint.y − |normalizedX − 0.5| × 90.0f
```

**진입은 엄격하게, 이탈은 관대하게** 나눠 판정합니다.

![LEAD 진입·이탈 조건](docs/figs/06-lead-gate.svg)

체류 조건은 길가 정차 차량이 순간적으로 차선에 걸쳐 LEAD가 되는 것을 막기 위한 것입니다. 다만 옆 차선에서 파고드는 컷인 차량은 정의상 방금 진입한 차량이라 이 조건을 만족할 수 없어, 횡이동 방향이 차선 중앙을 향하는 경우 체류 요건을 단축합니다.

이탈 유예는 반대 방향입니다. ego lane 사다리꼴의 상단 폭이 화면 폭의 8%에 불과해, 원거리에서는 접지점이 몇 픽셀 흔들리는 것만으로 경계를 넘나듭니다. 유예 없이는 한 프레임 이탈에 TTC-P 이력 전체가 삭제됩니다.

### 위험 단계 안정화

박스가 한 프레임 흔들릴 때마다 경고가 깜빡이지 않도록, 승격과 강등을 비대칭으로 처리합니다. 올릴 때는 빠르게, 내릴 때는 느리게입니다.

![위험 단계 전이](docs/figs/07-risk-state.svg)

경고 판정에는 TTC-P 외에 최소 박스 높이, 샘플 수, 높이 증가율, 접지점 하강 속도, 접지점 화면 위치, 추월 여부를 함께 확인합니다. 원거리 소형 박스가 2~3픽셀 흔들려 TTC-P가 4초대로 잘못 계산되던 오경고를 막기 위한 조건입니다.

시간 관련 판정은 `RiskAnalyzer`가, 화면 기하 관련 판정은 `main.cpp`가 소유하도록 나눴습니다. 두 곳에 같은 종류의 임계값이 흩어져 있으면 직렬로 걸리면서 한쪽이 도달 불가능한 죽은 값이 되기 때문입니다.

## 실행

### 의존성

```bash
sudo apt update

sudo apt install -y \
    build-essential \
    cmake \
    pkg-config \
    libopencv-dev \
    libopencv-contrib-dev \
    fonts-nanum
```

### 모델 및 입력 영상

```
models/yolov8n.onnx
videos/input.mp4
```

### 빌드

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

CMake 설정이 바뀐 경우에는 빌드 폴더를 지우고 다시 생성합니다.

```bash
rm -rf build
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

### 실행

```bash
./build/adas                                # videos/input.mp4
./build/adas videos/another_video.mp4       # 경로 지정
```

실행이 끝나면 `results/`에 결과 영상이 생성되고, 콘솔에 처리 프레임 수·평균 추론 시간·전체 처리 FPS가 출력됩니다. 결과 영상에는 객체 클래스, Tracking ID, LEAD 표시, TTC-P, 위험 상태, 프레임별 추론 시간, 현재 객체 수, 한국어 경고 메시지가 표시됩니다.

## 한계

현 시점에서 확인된 제약을 그대로 적었습니다. 상세한 원인과 재현 조건은 [devlog](docs/devlog.md)에 정리했습니다.

**경고 경로가 검증되지 않았습니다.** 테스트 영상 1,252프레임에서 CAUTION과 DANGER가 한 번도 발생하지 않았습니다. 위험 상황이 포함되지 않은 영상이기 때문입니다. 경고 관련 임계값은 실행된 적 없이 값만 정해진 상태입니다.

**박스 좌우 절단은 처리하지 못합니다.** 하단 절단은 종횡비 기반 등가 높이로 보정했으나, 차량이 더 가까워져 좌우까지 화면을 벗어나면 너비도 포화되어 스케일 추정이 불가능해집니다.

**ROI가 고정 좌표입니다.** 차선 검출을 수행하지 않으며, 두 사다리꼴은 테스트 영상의 카메라 장착 위치에 맞춰 조정한 값입니다. 곡선로, 차선 변경, 다른 카메라 위치에서는 실제 주행 차선과 어긋납니다.

**실시간 처리가 불가능합니다.** 2.45 FPS는 오프라인 후처리 속도입니다. 시간 관련 임계값이 FPS 환산 기반이라, 실행 속도가 다른 환경에 그대로 이식하면 경고 시점이 달라집니다.

**실제 거리 기반 TTC가 아닙니다.** TTC-P는 영상 스케일 변화 기반의 상대적 접근 위험 지표입니다. 실거리 TTC를 계산하려면 카메라 보정, 설치 높이·각도, 차량 실제 크기 추정, Ego-motion 보정이 필요합니다.

**장시간 재식별이 불가능합니다.** Track 보관 시간(20프레임)보다 오래 검출이 끊기면 새 ID가 생성됩니다. 위치와 크기 중심의 추적이라 외형 비교가 불가능합니다.

**일부 규칙이 특정 영상에 맞춰져 있습니다.** train 오분류 복구 조건, 장면 전환 임계값, LEAD 체류·추월 기준은 테스트 영상의 개별 구간에서 역산한 값입니다. 각 값의 출처 구간은 코드 주석과 devlog에 기록해뒀습니다.

## 진행 계획

### 1단계 · 정량 평가 체계

지금까지의 개선은 대부분 정성 관찰에 근거합니다. 이를 수치로 바꾸는 것이 우선 과제입니다.

- 프로그램 내부 카운터 추가 (신규 ID 발급 수, LEAD 유지 구간 분포, TTC-P 산출률, 경고 발생 횟수)
- 실제 위험 상황이 포함된 영상 확보 (AI Hub 교통사고 영상 데이터)
- 경고 적시성 지표 정의 (충돌 프레임 기준 TTC 2.0초 이전 DANGER 발생 여부)
- 오경보율 정의 (위험 없는 구간 100초당 경보 횟수)
- 프레임별 TTC-P 시계열 CSV 출력 (FP16 포팅 시 정확도 비교용 기준선)

### 2단계 · Jetson 포팅

- ONNX → TensorRT FP16 변환
- End-to-End 지연 측정 (p50 / p95 / p99)

- 30분 연속 구동 시 thermal throttling에 따른 지연 추이 확인
- **FP32 대비 FP16 정확도 검증** — 검출 수, LEAD 선정 일치율, TTC-P 평균 절대 오차, 경고 발생 시점 차이
- crop 보조 추론 주기 조절 및 검출률 트레이드오프 측정
